# CLS-4745 — {B} [backoffice] Pass reasonId on configurations, manual and bulk offers; open reasons list to bonus roles

Sub-task: https://celesta.atlassian.net/browse/CLS-4745 · Parent: https://celesta.atlassian.net/browse/CLS-3316 · Repository: celesta-backoffice

## Overview

The backoffice proxies reward configurations and bonus offers to promotion. Configurations are created and edited through `BonusModelController::addBonusModelAction` (`POST /api/gateway/domain/{domainId}/bonus_configuration`, and `PUT .../bonus_configuration/{id}` forwarded to it) with `RewardConfigurationType`, and gift configurations through `GiftConfigurationController` (`POST`/`PUT .../reward_configuration/gift[/{id}]`) with `GiftRewardConfigurationType`. Both forms carry the legacy `reason`, a choice of `RewardConfigurationConstants::REASONS`, which is forwarded to promotion's `POST`/`PATCH api/domain/{d}/reward-configuration[/{id}]`. The manual offer (`POST .../player/{playerId}/bonus_configuration/{id}/offer`, `BonusModelOfferType`) sends promotion's offer endpoint `sourceUserId` plus the amount or round count, and no reason. The bulk CSV offer runs in `OfferFreeBonusHandler`, one promotion offer per row with `amount` and `sourceUserId`. `BonusModelNormalizer` returns the configuration's legacy `reason` key; `BonusNormalizer` returns no reason on bonuses. The reward offering reasons list (`RewardOfferingReasonController::getReasons`, CLS-4164) is open only to `PS_GIFT_OFFER` and `PS_REWARD_OFFERING_REASON_UPDATE`.

[CLS-4743](https://celesta.atlassian.net/browse/CLS-4743) gives promotion's reward configurations and bonuses a `reasonId` that points to the brand's reward offering reasons. This sub-task carries that `reasonId` through the backoffice API: configuration create and edit (all four types) forward it, the manual offer forwards the reason the user picked, the bulk offer forwards the configuration's own reason with every row, configuration and bonus responses return the reason's id and name, and the reasons list opens to the users who need it to fill those forms. The legacy `reason` is no longer sent.

## Architecture & Design

**Promotion contract** (from [CLS-4743](https://celesta.atlassian.net/browse/CLS-4743)):

| Promotion call | Change |
|---|---|
| `POST api/domain/{d}/reward-configuration`, `PATCH .../reward-configuration/{id}` (all types, gift included) | accept optional `reasonId`; an unknown, deleted or other-brand reason is a 400 validation error on `reasonId`, except the configuration's own already-deleted reason on edit, which is kept. A key absent from the PATCH body leaves the stored reason as it is; `reasonId: null` clears it. |
| `GET .../reward-configuration/{id}`, POST/PATCH responses, `GET .../reward-configurations` items | new `reasonId` (integer or null) and `reasonName` (string or null, deleted reasons included); legacy `reason` unchanged |
| `POST api/domain/{d}/player/{p}/reward-configuration/{id}/offer` | optional `reasonId`. A call with `sourceUserId` stores the request's `reasonId`, none when absent. The configuration's own reason is accepted even after it is deleted; any other deleted, unknown or other-brand reason is a 400 validation error on `reasonId`, checked after the idempotency replay. Response unchanged. |
| `GET api/domain/{d}/bonuses` | each bonus carries its own `reasonId` and `reasonName`, deleted reasons included |

**Configuration create and edit.** `RewardConfigurationType` and `GiftRewardConfigurationType` gain `reasonId` (`IntegerType`, `empty_data` null, `Assert\Positive`), as `Promotion\Gift\OfferType` has since CLS-4164. The legacy `reason` field leaves both forms and both request schemas, so it is never forwarded; both forms keep `allow_extra_fields: true`, so a client that still sends `reason` gets a 200 and the key is ignored. `reasonId` is forwarded only when the request body carries the key, on create and on edit, in both controllers: `if (! $request->request->has('reasonId')) unset(...)`, the shape of `PaymentConfigurationController::putPaymentConfigurationAction` for `timeout`. Promotion validates the reason; the backoffice only rejects a non-integer or non-positive value before calling it.

**Manual offer.** `BonusModelOfferType` gains the same `reasonId` field; `BonusModelNormalizer::normalizeBonusModelOfferRequest()` always sends `'reasonId' => $data['reasonId'] ?? null` next to `sourceUserId`, as `GiftNormalizer::normalizeOfferRequest()` does. No reason sent means no reason on the bonus.

**Bulk offer.** `OfferFreeBonusHandler::handle()` reads the configuration with `PromotionClient::getRewardConfiguration($domainId, $bonusModelId)` before each offer, inside the existing `try`, and sends its `reasonId` (null when it has none) with `amount` and `sourceUserId`. Every row therefore gets the configuration's reason as it is when the row is offered; a configuration whose reason was deleted still passes it, which promotion accepts for the configuration's own reason. A failed read fails the row with the same message handling as a failed offer. `sourceUserId` stays, so the bonus keeps the user who launched the bulk action.

**Promotion's rejection on the forms.** All three controllers already pass promotion's 400 through `FormHelper::handleV2Exception($e, $form)`, which binds each key of promotion's error map to the form child of the same name through `setFormErrorsFromArray`. Once each form has a `reasonId` child, promotion's error on `reasonId` lands on it with no new mapping code.

**Responses.** `BonusModelNormalizer::normalize()` and `normalizeListItem()` add `reasonId` and `reasonName` right after `reason`, read from promotion with `?? null`; the `BaseBonusResponse` schema, shared by `BonusModelResponse` and `BonusModelListItem`, documents both. The legacy `reason` key stays as it is. `BonusNormalizer::normalize()` adds the bonus's own `reasonId` and `reasonName` after `promotionId`, documented in `BonusNormalized`. The bonus configuration list item is what the offer forms load configurations from, so the front end can pre-fill Reason from it.

**Reasons list access.** `RewardOfferingReasonController::getReasons` replaces its two-permission check with a private constant list of grants and a private `isGrantedAny()` copied from `AssetTagController::isGrantedAny` (same helper in `FraudProviderController`, `ProviderConfigurationController`, `GameProviderController`); `scripts/check-route-permissions` already accepts `isGrantedAny`. The list: `ROLE_OAUTH2_PS_GIFT_OFFER`, `ROLE_OAUTH2_PS_REWARD_OFFERING_REASON_UPDATE`, `ROLE_OAUTH2_PS_BONUS_OFFER`, `ROLE_OAUTH2_PS_BONUS_CONFIGURATION_CREATE`, `ROLE_OAUTH2_PS_BONUS_CONFIGURATION_EDIT`, and `ROLE_OAUTH2_ROLE_SCENARIO`, reused from the public `ScenarioController::ROLE_OAUTH2_ROLE_SCENARIO` (`Scenario/ScenarioController.php:38`). Create and delete stay on `PS_REWARD_OFFERING_REASON_UPDATE` alone, so only that permission gives access to the Administration section.

**Policy label.** `translations/messages.en.yml`, `roles.ROLE_REWARD_OFFERING_REASONS_UPDATE`: `'Update reward offering reasons'`. Cosmetic at most: nothing in this repository reads the `roles.*` translations, and the label users see comes from the front end. The policy name, its permission and the owner grant from `Version20261102000000` do not change, so no migration.

**Boundary.** No change to `PromotionClient` (every call already takes the body as an array), to `UserActivityJobManager::dispatchBonusOfferJob`, to `ScenarioNormalizer`, to the legacy `filter.reasons` on the bonus configuration list ([CLS-4748](https://celesta.atlassian.net/browse/CLS-4748)), or to celesta-fixtures.

## Edge Cases & Error Handling

- **Current front end, after this deploy and before [CLS-4746](https://celesta.atlassian.net/browse/CLS-4746):** it still sends the legacy `reason`, which is ignored, so configuration create and edit return 200 and the stored legacy key is untouched. Its edit-reason control becomes a silent no-op: the user picks a reason, saves, and nothing changes. On `reasonId` the two edits differ. The gift edit omits it (`GiftConfigurationModal.js:74-86`), so nothing is forwarded and the stored reason (backfilled by [CLS-4744](https://celesta.atlassian.net/browse/CLS-4744)) is kept. The non-gift edit echoes the whole configuration it last read (`EditRewardConfigurationModal.js:142,151,158`), so after this deploy it sends back `reasonId` and `reasonName`; `reasonId` is forwarded unchanged and `reasonName` is dropped by the form. A configuration created in that window has no reason. Manual offers carry no reason. Bulk offers already get the configuration's reason.
- **Configuration whose reason was deleted:** read and list return its id and name; an edit that sends it back is accepted by promotion; a bulk offer from it sends it and promotion stores it.
- **`reasonId` 0, negative or not an integer:** 400 on `reasonId` from the backoffice form, promotion not called.
- **Unknown, deleted (not the configuration's own) or other-brand `reasonId`:** promotion's 400 on `reasonId`, bound to the `reasonId` field; nothing saved, no bonus created.
- **`reasonId` and a legacy `reason` together:** `reasonId` forwarded, `reason` ignored.
- **Bulk row whose configuration read fails** (404 after the configuration was deleted, promotion down): the row fails with the read's error, no offer call, the other rows go on as today.
- **Bulk action running while the configuration's reason is changed:** rows offered after the change get the new reason, rows before keep the old one.
- **Promotion without CLS-4743** (deployed out of order, or rolled back): the configuration endpoints reject `reasonId` as an extra field (400); the offer endpoint ignores it (`allow_extra_fields`). `normalize()` always returns `reasonId`, and the current non-gift edit echoes it, so with promotion rolled back every non-gift configuration edit is a 400. Hence promotion first, and on rollback the backoffice goes back before promotion.
- **User with only Give bonus, only configuration create, only configuration edit, or only scenario access:** list 200; create and delete 403.
- **Rollback of the backoffice:** the previous code sends the legacy `reason` and no `reasonId`; stored reasons are untouched. Roll back the backoffice before promotion, never the other way round.

## Decisions

- **Which offer calls store the request's `reasonId`, and which copy the configuration's?** Calls with `sourceUserId` (backoffice manual offer) or `sourceScenarioId` store the request's `reasonId`, none when absent; calls with no source copy the configuration's reason. The backoffice's manual and bulk offers both send `sourceUserId`, so the bulk offer sends the configuration's `reasonId` itself to keep the user who launched it on each bonus · decided by Lucas, 2026-11-16
- **Which responses carry the reason?** Configuration GET/POST/PATCH, the configuration list and each bonus of `GET /bonuses` carry `reasonId` and `reasonName`, deleted reasons included; offer and claim responses are unchanged; the legacy `reason` key stays · decided by Lucas, 2026-11-16
- **How is an invalid reason refused?** An unknown, deleted or other-brand `reasonId` on the offer is the standard validation error on `reasonId` (400), checked after the idempotency replay; configuration create and edit refuse the same way, but keeping the configuration's own already-deleted reason succeeds, so the backoffice binds one error shape on every form · decided by Lucas, 2026-11-16

- **Q1. Is `reasonId` forwarded on a configuration edit when the request does not carry it?** Only when the body carries the key, on create and edit, in both controllers; `null` clears. Same shape as `PaymentConfigurationController::putPaymentConfigurationAction`. The current gift edit omits `reasonId` (`GiftConfigurationModal.js:74-86`); forwarding it as null whenever it is absent would clear the backfilled reason of every gift configuration edited before CLS-4746 ships, and force the backoffice and the front end to deploy together. The current non-gift edit echoes `reasonId` and `reasonName` (`EditRewardConfigurationModal.js:142,151,158`), so `reasonId` passes through unchanged · decided by Lucas, 2026-11-16
- **Q2. What happens to the legacy `reason` on configuration create and edit?** It leaves both forms and request schemas and is never forwarded. Promotion never required it (`Model/Request/RewardConfiguration.php:282-283` has only a `Choice`, the column is nullable), so new configurations get no legacy key and existing ones keep theirs, with nothing to clean up later. Accepted cost: until CLS-4746, the current front end's edit-reason control is a silent no-op and configurations created in that window have no reason · decided by Lucas, 2026-11-16
- **Q3.
