# CLS-4748 — {B} [backoffice] Cleanup: remove the legacy reason filter from the bonus-model list

Sub-task: https://celesta.atlassian.net/browse/CLS-4748 · Parent: https://celesta.atlassian.net/browse/CLS-3316 · Repository: celesta-backoffice

## Overview

`POST /api/gateway/domain/{domainId}/bonus_configurations` and `/bonus_configurations/count` (and the old alias `/bonus_configurations/search`) accept `filter.reasons`, a list of legacy reason keys (`loyalty_vip`, `other`…) plus `null` for "no reason". The field is declared in `App\GatewayBundle\Form\Type\Bonus\BonusModel\FilterType` (form field and the `reasons` property of the `BonusModelFilter` OpenAPI schema); `BonusModelNormalizer::normalizeFilterRequest()` calls `normalizeFilterReason()`, which turns each `null` into `NOREASON`, and the controller forwards the filter to promotion's `GET api/domain/{domainId}/reward-configurations[/aggregate]`.

[CLS-3316](https://celesta.atlassian.net/browse/CLS-3316) moves reasons to reward offering reasons (`reasonId`). New configurations no longer get a legacy key ([CLS-4745](https://celesta.atlassian.net/browse/CLS-4745)), so a filter on legacy keys can only match configurations created before the release, and the offer form stops filtering the bonus name list by reason ([CLS-4746](https://celesta.atlassian.net/browse/CLS-4746)). This sub-task removes the filter from the backoffice API once the front no longer sends it.

## Architecture & Design

- **Contract change.** `filter.reasons` disappears from `BonusModelFilter`. `FilterType` keeps the default `allow_extra_fields: false`, so a request that still sends `filter.reasons` gets the standard 400 validation body with `This form should not contain extra fields.` and promotion is not called. Same behaviour, and same test shape, as the removed singular `currency` filter on the bonus list (`tests/GatewayBundle/Controller/Bonus/BonusControllerTest.php::testSingularCurrencyFilterIsRejected`). PENDING Q2
- **Normalizer.** `normalizeFilterRequest()` stops calling `normalizeFilterReason()`, and the method is deleted: it has no other caller in `src/`.
- **Translations.** The repository has no translation key for the filter itself. The reason keys in `translations/messages.en.yml` are `bonus.form.reason` and `bonus.form.reasonChoices.*`, the labels of the legacy configuration reason field, with no consumer in `src/`. They are removed. PENDING Q3
- **Promotion is not touched.** Promotion keeps accepting `filter.reasons` and `NOREASON` (`RewardConfigurationRepository`, `ApiBundle\Form\Type\RewardConfiguration\FilterType`); the backoffice simply stops forwarding it. PENDING Q5
- **Callers found before removal** (`origin/master` of each repository, 2026-11-16):

  | Caller | What sends `filter.reasons` | Covered by |
  |---|---|---|
  | celesta-backoffice-front, offer bonus form | `src/components/page-components/crm/players/player/main/OfferBonusForm.js:119`, `filter: { status, reasons: [values.reason], types }` | [CLS-4746](https://celesta.atlassian.net/browse/CLS-4746) ("Reason no longer filters the Bonus name list") |
  | celesta-backoffice-front, reward configurations list search bar | `src/components/page-components/rewards/RewardConfigurationsSearchBar.js` (`reasons` field, options from `useBonusReasonsOptions`, `null` option for "no reason") and `src/utils/filterConfigs/fcRewardConfigurations.js` (`reasons`, also parsed from the URL) | not in any sub-task today. PENDING Q1 |
  | celesta-e2e-tests | `export/requests/get-bonus-configuration-list-9907cd11.json`, `get-bonus-configuration-count-cc67ff6e.json`: the OpenAPI example body, no assertions, not referenced by any test case | regenerated from the OpenAPI |
  | celesta-gateway, celesta-qaa-proteus, other services | no call to the backoffice `bonus_configurations` endpoints | n/a |
  | celesta-activity | route names only (`post_api-gateway-domain-\d+-bonus_configurations…` in the activity whitelist), not the body | unaffected |
  | celesta-backoffice internal | `BonusConfigurationAdapter` (autocomplete) calls `PromotionClient::getRewardConfigurations()` without `reasons` | unaffected |

## Edge Cases & Error Handling

- **Request still sending `filter.reasons`** (old front bundle in an open tab, a script): 400 with the standard validation body, promotion not called. Never a silently unfiltered list. PENDING Q2
- **`filter.reasons: []` or `null`**: also an extra field, also 400.
- **`/bonus_configurations/search`** (old route name `bonus_configuration_search_old`): same action, same behaviour.
- **Deploy window**: deploying before the front stops sending `reasons` turns the offer form's bonus name list (CLS-4746) and the list page reason filter (PENDING Q1) into 400s. Hence the merge and deploy order below.
- **Bookmarked list URL with a `reasons` parameter**: harmless only once the front no longer parses `reasons` from the URL (front change, PENDING Q1).

## Open questions

**Q1. The reward configurations list page also sends `filter.reasons`, and no sub-task removes it. Who does?**
Found in celesta-backoffice-front `origin/master`: `RewardConfigurationsSearchBar.js` (a `reasons` multi-select with a `null` "no reason" option) and `fcRewardConfigurations.js` (`reasons`, also read from the URL). CLS-4746's todo list only covers the offer form ("Reason no longer filters the Bonus name list"). If CLS-4748 ships as planned, the list page's reason filter returns 400.
- a) **Add "remove the Reason filter from the reward configurations list" to CLS-4746.** Same repository and team as the offer form change, already in progress, and already blocking CLS-4748. The parent puts "Filtering or reporting by reason in the BO" out of scope, and after CLS-4745 new configurations have no legacy key, so this filter would silently miss every new configuration. Con: grows a sub-task another team is already working on; needs their agreement.
- b) **A new front sub-task for the list filter, also blocking CLS-4748.** Same outcome, clean ownership, no change to CLS-4746's scope. Con: one more ticket and PR for a few lines.
- c) **Keep the list filter: CLS-4748 drops the filter removal** (and is reduced to nothing, or closed). Valid if the PO wants to keep filtering old configurations by legacy key. Con: a filter that can never match a new configuration, and the legacy key list stays in both repositories.
- **Recommended: a)**, falling back to b) if the front team declines. The filter is already wrong for new configurations the day CLS-4745 ships.

**Q2. What does the API answer to a request that still sends `filter.reasons`?**
- a) **400 `This form should not contain extra fields.`** Default of `FilterType` (no `allow_extra_fields`), same behaviour as every other removed filter, e.g. `BonusControllerTest::testSingularCurrencyFilterIsRejected`. The caller learns the filter is gone. Con: an old front tab breaks on that filter until reloaded.
- b) **Accept and ignore it** (`allow_extra_fields: true` on `FilterType`, or strip `reasons` in the controller). No 400 during the deploy window. Con: the user gets an unfiltered list while believing it is filtered, and the dead field stays in the contract.
- **Recommended: a).** A silently wrong list is worse than a visible error, and the deploy order already covers the window.

**Q3. Which translations go with the filter?**
The repository has no translation key for the filter. The only reason keys in `translations/messages.en.yml` are `bonus.form.reason` and `bonus.form.reasonChoices.*` (added in COR-73 for the old server-rendered configuration form), labels of the legacy configuration reason field, with no consumer in `src/`. `messages.fr.yml` is empty.
- a) **Delete `bonus.form.reason` and `bonus.form.reasonChoices`.** Dead keys tied to the legacy reason, which is what the todo list means by "its translations".
- b) **Delete nothing.** Strictly, none of them belongs to the filter. Con: dead legacy reason labels stay.
- **Recommended: a).**

**Q4. Do the legacy reason constants exposed by `ConstantManager` go in this sub-task?**
`ConstantManager` exposes `bonusModelConstants.reason*` and `reasons` (`BonusModelConstants::REASONS`). The front stores them as `bonusModelReasons` (`src/services/workers/global.js:289`) and reads them in `OfferBonusForm.js:50`, `OfferRewardActionModal.js:60` (scenario offer action), `MainSettingsStep.js:65` (configuration wizard) and `RewardReasons.js:11`, besides the list filter. They are not the filter, and the scenario offer action has no sub-task in this story.
- a) **Out of scope here.** The todo list names the filter only, and after CLS-4746 the front still reads the constants in at least the scenario offer action, which no sub-task changes. Removing them is a separate cleanup once the front has no reader.
- b) **Remove them here.** One cleanup PR for all legacy reason surfaces. Con: breaks every reader above that CLS-4746 does not replace, starting with `OfferRewardActionModal.js`.
- **Recommended: a)**, with a note on the parent so the leftover is tracked.

**Q5. Promotion keeps `filter.reasons` and `NOREASON`. Does it get a cleanup sub-task?**
No sub-task of CLS-3316 removes them (`RewardConfigurationRepository`, `ApiBundle\Form\Type\RewardConfiguration\FilterType`, and a Proteus payload using `NOREASON`). This does not change the tasks above.
- a) **New promotion cleanup sub-task, blocked by CLS-4748.** Removes the last reader; the Proteus payload has to change with it.
- b) **Leave it.** Harmless once no caller sends it. Con: dead filter code in promotion.
- **Recommended: a)**, low priority. Lead's call, raised on the parent.
