Recurring prod incident (Celesta Scenario Messenger Latency + CMS Latency alerts, ~21:00 nightly, first traced Jul 25-26 2026, PagerDuty #1514 area) traced to: scenario's `send_email` action calls CMS's `custom-email-template/{id}/send` once per recipient, serially (batches of up to 50, no batching). CMS synchronously calls memberzone/CRM (fetch player) then celesta-contact (`POST /emails`) before responding — every hop blocks.

**Real root cause (NOT fixed by CLS-2103/2104)**: celesta-contact's `POST /emails` dispatches its `EmailMessageJob` via `Celesta\MessengerHelperBundle\PostResponseMessageDispatcher`, which only defers publish to Symfony's `kernel.terminate` — there is no `fastcgi_finish_request()` anywhere in that bundle, so the SQS publish still blocks the HTTP response back to the caller despite being designed as "async." This was ~45% of total trace time in the traced incident. The same bundle/pattern is also what CMS's own activity-job emission (`CustomEmailTemplateManager::emitUserActivityJob`) uses.

**Fix scope**:
- **CLS-2103** (celesta-cms, ours): refactor `send` endpoint into a pure template renderer. Accepts `player` data as an **open bag** (not a whitelist — mirrors today's CRM customer shape so any `{{ player.* }}` placeholder a template already uses keeps working) in the request body instead of `playerId`. Returns `{subject, body_html, sender_email, sender_name}`. No CRM call, no Contact call, no activity-job emission (dropped entirely — "no side effects" per ticket; creates an accepted tracking gap until CLS-2104 ships).
- **CLS-2104** (celesta-scenario, NOT ours, do not implement): `SendEmailActionJobHandler` takes over orchestration — calls CMS's new render endpoint (player data fetched via scenario's own existing `MemberzoneClient::getCustomer()`, already used by 2 other handlers), then calls celesta-contact directly (needs a brand-new `ContactClient` in scenario — doesn't exist today), then emits the activity job itself (scenario already has a working dispatch pattern, `UserActivityJobDispatcher`, used today only by `TriggerWebhookActionJobHandler` — but no `EVENT_CUSTOM_EMAIL_SENT`-equivalent constant exists yet; would need adding to the shared `lancasters/job-library` vendor package, a cross-team dependency not mentioned in the ticket).

**Sufficiency verdict — important, re-check before assuming the incident is closed**: this fix pair is a real, worthwhile improvement (moves CMS's blocking activity-job SQS publish out of the per-recipient path entirely, since scenario's equivalent dispatcher batches at end-of-SQS-message via `WorkerMessageHandledEvent` rather than per-HTTP-request/`kernel.terminate`) — but it does **NOT** fix the original incident's single biggest contributor: celesta-contact's own endpoint remains untouched and will still block scenario per-recipient exactly as it blocked CMS before (same missing-`fastcgi_finish_request` issue, just experienced one hop earlier). If the nightly PagerDuty alert recurs after both tickets ship, this is why — the real fix belongs in celesta-contact itself (`fastcgi_finish_request()`, or batch the SQS publish via `SendMessageBatch`), and wasn't tracked by any ticket seen so far.

**Symfony technique used for CLS-2103's request contract**: to accept an arbitrary/open associative array as a single form field (no fixed whitelist of keys), use `'compound' => false, 'multiple' => true` on a custom `AbstractType`. Verified directly against vendored Symfony source (`symfony/form/Form.php:463`, `AbstractType.php:26-29`, `Extension/Core/Type/FormType.php:58-61`): `multiple => true` is exactly what bypasses the "array submitted to a non-compound field" rejection in `Form::submit()`, and with `compound=false` there's no `DataMapper`, so the array passes through completely untransformed (no key stripping, no coercion).

See also [[reference_db_query_from_containers]] for the local-verification approach (query CMS's `custom_email_template`/`website_asset_translations` tables via docker exec, or create fixtures via CMS's own CRUD endpoints).

**Tester-found bug, fixed 2026-08-12**: `POST /custom-email-template/{id}/render` returned `{"player":["This value should not be null."]}` when `player.language` was null/missing — useless, doesn't name the field. Root cause: `PlayerType` (`src/Form/Type/CustomEmailTemplate/PlayerType.php`) is `compound => false` (needed for the open-bag technique above), so it has no child form for `language`; any violation Symfony's `Assert\Collection` attaches at path `[language]` bubbles up with no child form to land on and gets stuck on the parent `player` form. The shared-lib `FormResponseSubscriber` (`vendor/lancasters/symfony-components`) only reads `$error->getMessage()`, never the property path, so the nested path info is silently discarded — this will bite any future `compound=false` field in this codebase, not just this one. Fix applied entirely inside `PlayerType.php` (no shared-lib change): gave `NotNull`/`Type`/`NotBlank`/`missingFieldsMessage` explicit custom messages that name `player`/`player.language` themselves, so the flattened error is self-explanatory regardless of which exact malformed-input path (missing key, null, wrong type, absent object) triggered it. Verified against real `symfony/form` + `symfony/validator` (6.4) via a standalone repro script exercising all 5 input variants before touching production code.
