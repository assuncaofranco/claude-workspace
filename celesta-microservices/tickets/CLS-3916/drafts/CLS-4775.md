# CLS-4775 — {B} [backoffice] Gift created by and gift_offered log for promotion sources

Sub-task: https://celesta.atlassian.net/browse/CLS-4775 · Parent: https://celesta.atlassian.net/browse/CLS-3916 · Repository: celesta-backoffice

## Overview

`GiftNormalizer` builds the `PromotionGiftNormalized` resource for the player gift list (`GET /api/gateway/domain/{domainId}/player/{playerId}/gifts`, `GiftController::getGifts`), the reward configuration gift list (`GET /api/gateway/domain/{domainId}/gifts`, `GiftConfigurationController::getRewardConfigurationGiftsAction`) and the offer response (`POST /api/gateway/domain/{domainId}/player/{playerId}/gift`, `GiftController::postGift`). Today `createdBy` resolves only `sourceUserId` to a BO user (`UserRepository::getUsersByIds`, one lookup per list); a scenario gift returns `createdBy: null` and its raw `sourceScenarioId`. A gift created by a promotion ([CLS-4772](https://celesta.atlassian.net/browse/CLS-4772)) carries neither: celesta-promotion ([CLS-4770](https://celesta.atlassian.net/browse/CLS-4770)) adds a nullable `source_promotion_id` column on `gift`, exposed on its gift API as `sourcePromotionId` (integer or null, after `sourceScenarioId`), holding the promotion configuration id. This sub-task resolves that id to the promotion configuration's id and name in `createdBy`, and exposes `sourcePromotionId`.

On the activity side, `LogController` returns `sourceType`, `sourceUserId` and `additionalData` of each activity unchanged, and `LogNormalizer` describes `gift_offered` from `additional_data` without looking at the source. The one thing that stops a `promotion` source today is the logs filter: `Log/FilterType` builds `filter[sourceTypes]` as a `ChoiceType` on `UserActivityJob::SOURCE_TYPES`, which has no `promotion` until [CLS-4768](https://celesta.atlassian.net/browse/CLS-4768). This sub-task requires that job-library branch.

## Architecture & Design

- **Promotion lookup, one call per list.** `GiftNormalizer` collects the distinct non-null `sourcePromotionId` of the gifts it normalizes and, when there is at least one, calls the existing `PromotionClient::getPromotionConfigurations($domainId, $query)` once with `filter.ids`, `limit` = number of ids, `offset` = 0. celesta-promotion filters `pc.id` by `ids` (`PromotionConfigurationRepository::applyPromotionConfigurationFilters`) with no status condition, so disabled configurations resolve too, and its `QueryType` puts no cap on `limit`. The result is indexed by `id`. This mirrors `resolveUsers`, which skips the lookup when no gift has a `sourceUserId`. No new client method.
- **`createdBy` shape.** Unchanged: `{id, name}`. For a BO user gift it is the user, as today. For a promotion gift it is `{id: <promotion configuration id>, name: <promotion configuration name>}`. A scenario gift keeps `createdBy: null`.
- **`sourcePromotionId`.** Added to `PromotionGiftNormalized`, after `sourceScenarioId`, `integer`, nullable, read from the promotion gift as `sourceScenarioId` is. It is how a client tells a promotion `createdBy` from a BO user `createdBy`.
- **`domainId` reaches the normalizer.** `normalizeOne` and `normalizeMany` take the domain id as first argument, because the promotion lookup is domain-scoped. Every caller already has `$domainId` in its route.
- **Unresolved or failed lookup.** A `sourcePromotionId` absent from the lookup result gives `createdBy: null` and an error log, as an unresolved `sourceUserId` does today. A `V2Exception` from the lookup is caught in the normalizer, logged as an error, and every promotion gift of that list gets `createdBy: null`; the list still answers 200.
- **Activity.** `"lancasters/job-library": "dev-CLS-4768 as 3.150"` (latest job-library tag is `v3.149`). `Log/FilterType` and the `LogFilter` OpenAPI enum read `UserActivityJob::SOURCE_TYPES`, so `promotion` is accepted on `POST /api/gateway/logs` and `POST /api/gateway/logs/count` with no source change. `LogNormalizer` needs no change: celesta-promotion sends `gift_offered` with source `promotion`, `source_user_id` the configuration id, and the `additional_data` keys of `UserActivityJobManager::dispatchGiftOfferJob` plus `player_id` and `domain_id`; with the same `name`, `value`, `currency` and `reason_name` as a manual gift it gets the same description. The tests pin this.
- **Labels.** None in this repository. The backoffice `translations/messages.{en,fr}.yml` hold no label read for a gift's creator or an activity source type (`player.logs.table.source_type` has no reader in `src/`). The six locales and the activity source column belong to celesta-backoffice-front.

## Edge Cases & Error Handling

- **Promotion not yet on CLS-4770.** Gift rows have no `sourcePromotionId`: `sourcePromotionId` is null, `createdBy` is what it is today, and no lookup runs. The backoffice can be deployed before celesta-promotion.
- **Configuration renamed after the gift.** `createdBy.name` is the configuration's current name, read at list time, as a BO user's current full name is.
- **Configuration disabled.** Resolved as any other: the lookup filters by id only.
- **Configuration deleted.** celesta-promotion has no delete route and no `deletedAt` on `PromotionConfiguration`, so it does not happen through the API. A row removed from the database falls in the unresolved case: `createdBy` null, error log, as a BO user that no longer resolves.
- **Lookup fails.** Promotion gifts get `createdBy` null, error log, list answers 200; user and scenario gifts are unaffected.
- **Several promotion gifts on one page.** One lookup per page, distinct ids only. The gift list caps `limit` at 500 (`Gift\QueryType::MAX_LIMIT`), so a lookup carries at most 500 ids.
- **Gift with both `sourceUserId` and `sourcePromotionId`.** Not produced by promotion; `sourceUserId` wins, as the first branch of `normalizeCreatedBy`.
- **Offer response.** `postGift` records a BO user gift, so `sourcePromotionId` is null and no promotion lookup runs.
- **Filter on `promotion` before celesta-activity accepts it.** The backoffice forwards the filter; activity answers 400 until [CLS-4769](https://celesta.atlassian.net/browse/CLS-4769) is deployed, and `LogController` returns that error as 400, as it does for any activity validation error.
- **Promotion `gift_offered` without `reason_name`.** The description has no reason part, as a manual gift without a reason.

## Decisions

- **Where does celesta-promotion keep the promotion that offered a gift?** — A nullable `source_promotion_id` column on `gift`, next to `source_user_id` and `source_scenario_id`, exposed as `sourcePromotionId` (integer or null, after `sourceScenarioId`) and holding the promotion configuration id; no `Source` entity. This repository reads `sourcePromotionId` — answered by Lucas Franco, 2026-11-17
- **Does this repository build editing, completing or canceling of promotion gifts?** — No; that is CLS-3865's — answered by Lucas Franco, 2026-11-17
- **What does the `gift_offered` activity sent by celesta-promotion carry?** — Source type `promotion`, `source_user_id` the configuration id, `additional_data` with the keys of `UserActivityJobManager::dispatchGiftOfferJob` plus `player_id` and `domain_id`; so `LogNormalizer` needs no change — answered by Lucas Franco, 2026-11-17
- **What does `createdBy` hold for a promotion gift, and how does a client tell it from a BO user?** — `{id, name}` of the promotion configuration, plus a top-level `sourcePromotionId`, mirroring `sourceScenarioId` · answered by Lucas Franco, 2026-11-17
- **What does the gift list do when the promotion configuration lookup fails?** — Promotion gifts get `createdBy` null with an error log, the list answers 200 · answered by Lucas Franco, 2026-11-17
- **Is a Proteus scenario added for the backoffice?** — No; HTTP tests here, end to end through CLS-4772 · answered by Lucas Franco, 2026-11-17
- **Does this repository carry labels or activity source rendering?** — No; the six locales and the activity source column are in celesta-backoffice-front · answered by Lucas Franco, 2026-11-17
- **Does the reward configuration gift list resolve promotion creators too?** — Yes, same normalizer and schema · answered by Lucas Franco, 2026-11-17
