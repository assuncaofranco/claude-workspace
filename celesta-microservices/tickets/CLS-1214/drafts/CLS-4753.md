## Contract for siblings

- **Request** (`POST /domain/{domainId}/payment-configuration/{id}/payout`): new optional `additionalData.withdrawRequestIds`, an array of positive integers, unique, no upper bound. When it is sent, `additionalData.withdrawRequestId` is required and must be one of its entries. The lead stays `withdrawRequestId`, unchanged. A single-request payout sends no list.
- **Stored** (what statistics, [CLS-4754](https://celesta.atlassian.net/browse/CLS-4754), reads): statistics reads the payment database directly, not an event. `TransactionMovementManager::getWithdrawTransactionMovements()` left-joins `transaction_additional_data` on key `withdrawRequestId`. The new row is `additional_data_key = 'withdrawRequestIds'` with `additional_data_value` = a JSON array of integers in ascending order, no spaces, e.g. `[4290150,4292746,4301966]`. The row exists only on combined payouts. Fallback: the existing `withdrawRequestId` row, which stays the lead as a string (`'4290150'`).
- **Jobs** (what wallet, [CLS-4755](https://celesta.atlassian.net/browse/CLS-4755), reads): in `TransactionCreateJob` / `TransactionUpdateJob`, `additionalData['withdrawRequestIds']` is that same JSON string (`json_decode` it), like `bonusIds` and `bank` today. `additionalData['withdrawRequestId']` stays the lead string.
- **409**: returned when any ID in the lead plus the list already has a pending or successful payout for the player, or another request for that ID is in flight. The body is unchanged: `{"errors":["Withdraw request already has a payout"]}`.
- **Bank description** (Genome `transfer_description`, My.Tu `msg`): the IDs in ascending order joined by `", "`, e.g. `4290150, 4292746, 4301966`. With no list it is the lead ID, as today; My.Tu still falls back to the transaction uid.
- **Deploy order**: payment, then statistics, then wallet, then backoffice, then front. Today's code (`PayoutType` with `allow_extra_fields`) silently drops an unknown field, so a list sent to an older payment pays the total under the lead ID only.

# CLS-4753 — {A} [payment] Pay several withdrawal requests in one Bank Transfer (auto) payout

Sub-task: https://celesta.atlassian.net/browse/CLS-4753 · Parent: https://celesta.atlassian.net/browse/CLS-1214 · Repository: celesta-payment

## Overview

`POST /domain/{domainId}/payment-configuration/{id}/payout` (`PayoutController::payout()`) names one withdraw request:
`additionalData.withdrawRequestId`, a `TextType` in `PayoutAdditionalDataType`, saved as one
`transaction_additional_data` row by `Transaction::setAdditionalData()` (non-scalar values are JSON-encoded into
`additional_data_value`, `VARCHAR(512)`). Duplicates are blocked by a lock named
`payout_withdraw_request_{playerRowId}_{withdrawRequestId}` (`WITHDRAW_REQUEST_LOCK_TTL` 120 s) and by
`TransactionRepository::hasActivePayoutForWithdrawRequest()`, which answers 409 when the player already has a
`pending` or `success` payout with the same `withdrawRequestId`. `GenomeProvider::doPayout()` sends that ID as
`transfer_description`; `MyTuProvider::doPayout()` sends it as `msg` (falling back to the transaction uid) and signs
it in `buildAuthorizationString()`. Downstream, `TransactionJobNormalizer` copies `Transaction::getAdditionalData()`
verbatim into `TransactionCreateJob` / `TransactionUpdateJob`; the wallet settles the request from
`additionalData['withdrawRequestId']`, and statistics builds the payout's transaction movement by reading this
service's database (`transaction_additional_data`, key `withdrawRequestId`).

This sub-task lets one payout carry every withdraw request it pays: a new list next to the single ID, which stays as
the lead request. The list is stored as additional data, guarded against duplicates for every ID, and written into the
Genome and My.Tu transfer description. Grouping the requests, and settling each of them, is the wallet's
([CLS-4755](https://celesta.atlassian.net/browse/CLS-4755)); exposing the list in the transaction report is
statistics' ([CLS-4754](https://celesta.atlassian.net/browse/CLS-4754)).

## Architecture & Design

**Contract.** `additionalData.withdrawRequestIds`: optional array of positive integers, unique, with no upper
bound on the number of entries. When it is non-empty,
`additionalData.withdrawRequestId` is required and must equal one of its entries; a one-entry list equal to the lead
is accepted and behaves as a single payout. A violation is a 400 through the form, like every other payout form
error. The 200 response (`id`, `uid`, `status`) is unchanged.

```json
{
  "clientId": 434714,
  "amount": 4000,
  "fee": 0,
  "payoutInformation": {},
  "additionalData": {
    "withdrawRequestId": "4290150",
    "withdrawRequestIds": [4290150, 4292746, 4301966]
  }
}
```

**Storage and propagation.** The controller sorts the list ascending and keeps it in `$additionalData` under
`withdrawRequestIds`; `Transaction::setAdditionalData()` stores it as one row with value `[4290150,4292746,4301966]`
(`json_encode` of an integer array). An empty or absent list is removed before saving, so a single-request payout
stores exactly the rows it stores today. The lead keeps its `withdrawRequestId` row. `TransactionJobNormalizer` is not
changed: the jobs carry the stored JSON string, as they already do for `bonusIds` and `bank`.

**Duplicate guard.** The ID set is the lead plus every list entry, as unique strings in ascending order. The
controller takes one lock per ID, with the existing name format and TTL, all or nothing: if one cannot be acquired,
those already held are released and the answer is 409. `TransactionRepository::hasActivePayoutForWithdrawRequests()`
then answers true when, for the same player row and among `payout` transactions in `pending` or `success`:
(1) a `withdrawRequestId` row has a value in the set (the existing `STRAIGHT_JOIN` query on `key_value_idx`, with
`IN`), or (2) a `withdrawRequestIds` row, decoded in PHP, shares an entry with the set (read from `transaction`
through `idx_player_row_id_status_type_status_set_at`, joined to `transaction_additional_data` on `transaction_id` and
key `withdrawRequestIds`). So a single payout is refused for an ID already inside an active combined payout, and the
other way round.

**Bank description.** `TransactionDataHelpersTrait::getWithdrawRequestDescription()` returns the decoded
`withdrawRequestIds` joined by `", "` when the transaction has a non-empty list, otherwise its `withdrawRequestId`
(or `null`). Genome uses it for `transfer_description`; My.Tu for `msg`, keeping the uid fallback. Because `msg` is
part of the My.Tu signature, the signed string carries the same description.

**Precedents, and choices without one.**

| Choice | Existing reference |
|---|---|
| List kept in additional data as JSON, decoded where read | `bonusIds`: `PayinAdditionalData`, `TransactionSubscriber::extractRewardIds()` |
| Integer IDs in a collection field | API guidelines ("all IDs are integer"); `Transaction\FilterType` uses an `IntegerType` collection |
| Cross-field validation in a `Callback` on the form | `Centrobill\PixType::validateField()` |
| Description built in the shared provider helper | `TransactionDataHelpersTrait::getFullNameFromTransaction()` and siblings |
| Several locks taken in one request | **No precedent**: `PayoutController`, `TransactionController` (resolve) and `AbstractProvider::getTransactionLock()` take one lock each |
| Guard matching IDs inside a JSON value | **No precedent** for a guard; decoding in PHP follows `extractRewardIds()` |
| Sorting caller input before storing it | **No precedent** |

Not abstracted: no new table, no migration, no change to `TransactionJobNormalizer`, no change to which providers
accept the list.

## Implementation Tasks

1. In `PayoutAdditionalDataType::buildForm()`, add `withdrawRequestIds` as a `CollectionType` with
   `entry_type` `IntegerType`, `allow_add` true, `required` false. Add `configureOptions()` setting `constraints` to
   `new Callback([$this, 'validateWithdrawRequestIds'])`, mirroring `Centrobill\PixType`. When the list is non-empty,
   `validateWithdrawRequestIds()` adds a violation at path `withdrawRequestIds` for each failing rule: an entry not
   greater than 0; duplicate entries; and at path `withdrawRequestId` when the lead is empty or not equal (as a
   string) to one of the entries.
2. In `PayoutController`, schema `RequestPayoutAction` → `additionalData`: add `withdrawRequestIds` (`type: array`,
   items `integer` with `minimum: 1`, `uniqueItems: true`, example `[4290150, 4292746, 4301966]`,
   description "Every withdraw request this payout pays, the lead included. When sent, withdrawRequestId is required
   and must be one of them."). Give `withdrawRequestId` the description "Lead withdraw request of the payout." Change the
   409 response description to "A withdraw request in withdrawRequestId or withdrawRequestIds already has a pending or
   successful payout, or one in progress."
3. In `PayoutController::payout()`, after `$additionalData = $payment['additionalData']`: when
   `$additionalData['withdrawRequestIds']` is empty or absent, unset it; otherwise sort it ascending and reindex it.
   Build `$withdrawRequestIds`: the lead (when not null) plus every list entry, cast to string, unique, sorted
   ascending.
4. In `PayoutController::payout()`, replace the single lock with one lock per entry of `$withdrawRequestIds`, same name
   format and `WITHDRAW_REQUEST_LOCK_TTL`. If one `acquire()` fails, release those already acquired and return
   `generateWithdrawRequestConflict()`. In the outer `finally`, release every acquired lock, logging a
   `LockReleasingException` per lock with the existing message and that lock's `withdrawRequestId`.
5. In `TransactionRepository`, replace `hasActivePayoutForWithdrawRequest(PaymentInformation, string)` with
   `hasActivePayoutForWithdrawRequests(PaymentInformation $paymentInformation, array $withdrawRequestIds): bool`.
   Query 1 is the existing SQL with `tad.additional_data_value IN (:values)` (`ArrayParameterType::STRING`). Query 2
   selects `tad.additional_data_value` from `transaction` `t` joined to `transaction_additional_data` `tad` on
   `tad.transaction_id = t.id AND tad.additional_data_key = 'withdrawRequestIds'`, where `t.player_row_id`, `t.type`
   payout and `t.status` in pending/success. It decodes each value and returns true when any entry, cast to string,
   is in `$withdrawRequestIds`; a value that does not decode to an array is skipped. Return false when the set is
   empty, without querying. In `payout()`, call it with `$withdrawRequestIds` when the set is non-empty, in place of
   the old call.
6. In `TransactionDataHelpersTrait`, add `protected function getWithdrawRequestDescription(Transaction $transaction): ?string`
   as described under Bank description.
7. In `GenomeProvider::doPayout()`, set `transfer_description` to `$this->getWithdrawRequestDescription($transaction)`.
8. In `MyTuProvider::doPayout()`, set `msg` to `(string) ($this->getWithdrawRequestDescription($transaction) ?? $transaction->getUid())`.

## Edge Cases & Error Handling

- **No list, or an empty list**: removed before saving; behaviour, stored rows, locks and guard are those of today.
- **Partial lock acquisition**: locks already held are released before the 409.
- **Overlap with a `failure` or `timeout` payout**: allowed, same statuses as today's guard.
- **A `withdrawRequestIds` value that is not a JSON array**: skipped by the guard and treated as no list by the helper.
  Only this service writes the row.
- **Rolling deploy**: old and new pods share the lead's lock name. An old pod's guard does not see non-lead IDs, so
  the wallet must not send lists until this version is fully rolled out.
- **List sent to a payment without this change**: `allow_extra_fields` drops it silently and the total is paid under
  the lead only. Hence payment deploys before the wallet, and payment is not rolled back below this version once the
  wallet sends lists.
- **Size of the list**: no cap is applied. The stored value is limited by the `additional_data_value` column
  (`VARCHAR(512)`), about 60 seven-digit IDs; no validation is added for it. A longer list fails when the
  transaction is saved, which happens before `doPayout()`, so nothing is sent to the bank. A provider that
  rejects a long description fails the payout, and every request of the group goes to error as for any rejected
  payout.
- **Genome CHF payouts**: conversion unchanged; only the description changes.

## Decisions

- **Name and type of the list?** `additionalData.withdrawRequestIds`, an array of integers: the API guidelines make
  every ID an integer, and both consumers hold the ID as an integer. Decided by Lucas.
- **How does the lead relate to the list?** The lead is required when the list is non-empty and must be one of its
  entries; a one-entry list is a single payout. The list is always the full set, so the single-ID fallback in
  statistics stays coherent and the guard checks exactly the list. Decided by Lucas.
- **Upper bound on the list?** None. No limit for Genome or My.Tu exists in the code, a player rarely has more than
  a few validated requests at once, and if a provider rejects the payout every request goes to error and is handled
  as today. Decided by Lucas.
- **Order of the IDs?** Ascending, applied by this service before storing and describing, so the description is
  deterministic. Decided by Lucas.
- **How does the guard find IDs inside existing lists?** Decoded in PHP, following `extractRewardIds()`; no JSON
  SQL, no new table. Decided by Lucas.
- **How are several IDs locked?** One lock per ID with the existing name, all or nothing, so old and new pods still
  contend on the lead's key during rollout. Decided by Lucas.
- **Shape of the list in the jobs?** The stored JSON string, normalizer unchanged, as for `bonusIds` and `bank`.
  Decided by Lucas.
- **Restrict the list to Bank Transfer (auto)?** No: the wallet decides what is grouped, and payment stays
  provider-agnostic. Decided by Lucas.
- **Deploy order?** Payment, then statistics, then wallet, then backoffice, then front. Decided by Lucas.
