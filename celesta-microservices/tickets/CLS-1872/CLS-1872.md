# CLS-1872 — How to test (Game gateway connections)

**Feature:** a brand's game gateway connections can be listed, created and edited from Backoffice, and the credentials inside them are only returned to a user who may change them.

## Setup

**Dev** — import `CLS-1872.postman_collection.json` and run with **No environment**: it ships dev defaults for every variable and is self-contained.

**preprod-1** — import the collection *and* `CLS-1872.preprod-1.postman_environment.json`, then select that environment. It overrides only the eight configuration variables; every captured value stays in the collection scope, so nothing is shadowed.

```bash
newman run CLS-1872.postman_collection.json -e CLS-1872.preprod-1.postman_environment.json \
  --env-var "BO_password=<from ~/.claude-secrets/celesta-preprod.md>" \
  --env-var "BO_oauth_client_secret=<from ~/.claude-secrets/celesta-preprod.md>"
```

The environment file ships those two **empty**: this folder lives inside the `claude-workspace` repo, whose
rule is that no secret is versioned. The values are in `~/.claude-secrets/celesta-preprod.md` (see
`context.yaml` → `secrets.files.preprod`) and enter through `--env-var` at run time — or, in the Postman
app, by filling the two secret fields after import.

Before the first preprod run, two things:

- **`BO_username_no_access` ships empty.** There is no seeded no-permission user in preprod, so steps 15-19 need a real Backoffice user whose role holds none of the three permissions. Fill it in, or run the owner half alone:
  `newman run ... -e ... --folder "Backoffice — owner (full permissions)"`.
- **`domainId` is 56 (madnix)**, the brand the other preprod collections use. The permission roles recorded below were read from **company 1**; if domain 56 belongs to another company, check that company's roles before reading anything into a 403.

The environment file holds **no** secret — only the variable names. Do not put the values back into it: the folder is versioned.

**Either way:**

- For dev, bring the stack up (`celesta-backoffice` and `celesta-game`) with both repos on the branch under test. The stack is now `CLS-2980 ← CLS-2978 ← CLS-2979`, so checking out `CLS-1872-CLS-2979` in both gives the whole epic — the separate `CLS-1872-integration` branch is no longer needed.
- For preprod, the tip of each service's `CLS-1872-CLS-2979` must be deployed, and the Backoffice migration must have run: without it the `PS_GAME_CONNECTIONS_SEE` policy does not exist. Deploy order between the two services does not matter.
- Run top-to-bottom. Steps are grouped by actor; ids chain between them.

## Steps
1. Log in as owner (BO token).
2. List the domain's game connections — every item carries `options` and `freeRoundsCancelable`.
3. Create a connection.
4. List again — the new connection is there, with the options that were sent.
5. Create a second connection of the same gateway type.
6. Update the first one: rename, disable, rotate the credential.
7. List again — all three changes are visible.
8. Update with `options` that is not an object — rejected.
9. List again — the rejected update changed nothing.
10. Update trying to change the gateway type — rejected.
11. Create with a name another connection already uses — rejected, on the `name` field, no SQL in the body.
12. Update with `enabled: null` — rejected, and the connection is not disabled.
13. Update with both booleans missing — rejected, and **both** are named in the same response.
14. List again — the three rejections changed nothing, and no `options` came back as `[]`.
15. Log in as customer support (no integrations access).
16. List — refused.
17. Create — refused.
18. Update — refused.
19. List as owner — nothing was created or changed by the refused calls.

## Variables

| Variable | Example | What it is |
|---|---|---|
| `BO_baseUrl` | `http://localhost:84` | Backoffice base url |
| `BO_username` / `BO_password` | `owner@gmail.com` / `test` | user with full integrations permissions |
| `BO_username_no_access` | `customerSupport@gmail.com` | user with no integrations access |
| `domainId` | `1` | brand whose connections are exercised |
| `gatewayType` | `gateway_type_aleaplay` | gateway type used for the created connections |

Captured automatically at runtime (kept in the collection, start empty): `BO_access_token`, `CS_access_token`, `connectionId`, `secondConnectionId`, `initialCount`, `runTag`, `connectionName`, `connectionNameRenamed`, `connectionNameSecond`.

`runTag` is the last six digits of the clock at the start of the run, and every connection name carries it. A name is unique per brand, so without it a second run collides with the first and step 3 fails with a legitimate 400.

## Notes
- Every step runs through Backoffice — PO-runnable in preprod, no internal service call, no guard header.
- `gatewayType` is `gateway_type_aleaplay`, the only type the validator does not ping: its provider read call needs a GraphQL query, so it is deliberately left at the key check. Saving therefore never contacts a provider and the run is repeatable. Its four required option keys are `secret_key`, `bonus_api_base_url`, `customer_api_base_url` and `environment_credential`.
- Change it to any other type (`gateway_type_playn_go`, `gateway_type_evolution`, …) only with real credentials — the validator will call that provider, and steps 3, 5 and 6 will fail with a provider error, which is the feature working.
- Two profiles the collection does not cover with the default users: *Access integrations only* and *View Game connections only*. Locally the fixtures grant both policies to `owner` alone; in the real environments permissions are assigned by hand in Access control. In **preprod-1** two of them already exist as real roles (checked 2026-09-21): `product_owner` holds Access integrations + Update Game connections, and `head_of_operations` / `acquisition manager` hold Access integrations only — so the read-without-options profile is runnable there with an existing role. Only *View Game connections only* needs a role created, and only after the CLS-2980 migration is deployed: the policy does not exist in preprod yet. Expected for that profile: list returns 200 **without** `options`, create and update return 403.
- **Running this against preprod writes real data.** It creates two connections on the chosen brand and disables one of them. Pick a brand where that is acceptable, or delete the rows afterwards — the epic has no delete endpoint.
- **The option values in the collection are deliberately fake** (`integration-secret`, `https://alea.example/...`). That matters in preprod: the game's nginx sidecar logs the full request body, and `cel-preprod-1` does not patch that config — it inherits the same `log_format` as production, and preprod's Datadog agent runs with `logs_container_collect_all = true`. So whatever goes into `options` ends up in the logs. Fake values leaking is not a leak. Do **not** swap in a real provider credential to watch the ping succeed until the DevOps ticket on that capture is closed.
- Each run leaves two new connections on the domain. Harmless: assertions compare against a count captured in the same run.
- **Validation errors come back flat.** celesta-game answers `{"message": ..., "errors": {"enabled": [...]}, "code": ...}`; Backoffice forwards the inner map, so what the browser sees is `{"enabled": [...], "code": "VALIDATION_CONSTRAINT"}` — field names at the top level, no `errors` wrapper. That is `FormHelper::handleV2Exception`, shared by every proxying controller, not something this epic chose. Steps 11-13 assert the flat shape; the CLS-2981 form has to bind to it.
- Expected result: `failed: 0` across every row of the Newman summary. Last run: 19 requests, 44 assertions, 0 failures (2026-09-22, dev, both repos on `CLS-1872-CLS-2979`).
