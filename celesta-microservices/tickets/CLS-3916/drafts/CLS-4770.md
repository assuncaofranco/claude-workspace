# CLS-4770 — {D} [promotion] Gift Source entity (user, scenario, promotion), backfill, sourcePromotionId

Sub-task: https://celesta.atlassian.net/browse/CLS-4770 · Parent: https://celesta.atlassian.net/browse/CLS-3916 · Repository: celesta-promotion

## Overview

A gift (`App\AppBundle\Entity\Gift`, table `gift`) records who offered it in two nullable integer columns: `source_user_id` (a back-office user, `sourceUserId`) and `source_scenario_id` (a scenario, `sourceScenarioId`). `POST /api/domain/{domainId}/player/{playerId}/gift` requires exactly one of them (`App\ApiBundle\Model\Request\Gift`), and every gift response (`Gift::jsonSerialize()`, plus the raw-SQL replay in `GiftController::resolveIdempotencyKeyRaceWinner()`) returns both.

[CLS-3916](https://celesta.atlassian.net/browse/CLS-3916) has promotions create gifts on rewarding ([CLS-4772](https://celesta.atlassian.net/browse/CLS-4772)), and the parent requires the gift's *created by* to show the promotion. Such a gift has neither a user nor a scenario behind it, so today it could not name its source. This sub-task adds a third source column, `gift.source_promotion_id`, holding the promotion configuration id (`promotion_configuration.id`), and exposes it as `sourcePromotionId` on every gift response. celesta-backoffice ([CLS-4775](https://celesta.atlassian.net/browse/CLS-4775)) resolves that id to the configuration's name for *created by*.

The split planned a `Source` entity with a backfill and a later drop of the two columns ([CLS-4773](https://celesta.atlassian.net/browse/CLS-4773)). That was replaced by the single column, with no entity, no backfill and no column drop (see Decisions).

## Architecture & Design

- **Storage.** One nullable `INT` column `source_promotion_id` on `gift`, mapped as `?int $sourcePromotionId` next to `$sourceUserId` and `$sourceScenarioId`, the same shape as those two: no foreign key, no index. No query filters on it, and `promotion_configuration` has no delete route, so a foreign key would protect nothing a reader relies on.
- **Value.** The promotion configuration id, not the promotion instance id. The instance belongs to the activity entry CLS-4772 sends, not to the gift.
- **Who writes it.** Only CLS-4772, through `Gift::setSourcePromotionId()`, when it creates the gift at rewarding. No request form or model accepts `sourcePromotionId`: `GiftType` and `App\ApiBundle\Model\Request\Gift` are unchanged, so a client sending it gets the existing `This form should not contain extra fields.` error. `GiftFactory::createFromRequestModel()` is unchanged; the BO reward offer route (`RewardConfigurationController::offerReward`, which creates bonuses) is unchanged.
- **Who reads it.** Every gift response: `Gift::jsonSerialize()` serves `GET /api/domain/{domainId}/gifts`, the 201 of the offer and its early replay (`GiftRepository::findOneByIdempotencyKey`). The late replay (`resolveIdempotencyKeyRaceWinner`) builds its array from `SELECT g.*` by hand, so it gets the key explicitly, in the same position, so that a replayed body equals the original one key for key.
- **Contract.** `sourcePromotionId`, `integer`, nullable, directly after `sourceScenarioId` in `jsonSerialize()` and in the `Gift` OpenAPI schema (from the `#[OA\Property]` on the new property, as `sourceScenarioId` is documented). `public/open-api.json` is git-ignored and regenerated by `make openapi`; it is not committed.
- **Existing gifts.** No backfill: rows created before this change keep `source_user_id` and `source_scenario_id` as they are and get `source_promotion_id` `NULL`, which the API returns as `null`.
- **Unchanged.** The `GiftFilter` (`sourceUserId` filter only), `GiftEventSubscriber` and the `GiftEventJob` it sends to statistics (no source field), and the `exactly one of sourceUserId and sourceScenarioId` rule on the request model.
- **Migration.** Mirrors `Version20261019120100`, which added `source_scenario_id`: guarded by `hasTable` and `hasColumn`, `ALGORITHM=INSTANT` to add (metadata only, no row rewritten), `ALGORITHM=INPLACE, LOCK=NONE` to drop.

## Edge Cases & Error Handling

- **Existing gifts.** `source_promotion_id` `NULL`, returned as `null`; `sourceUserId` and `sourceScenarioId` unchanged. No backfill.
- **Client sends `sourcePromotionId`.** 400 `This form should not contain extra fields.`, no gift recorded (task 8).
- **Replays.** The early replay serialises the stored entity and the late replay reads the row; both return the stored `sourcePromotionId` in the same position (task 7).
- **Deploy window.** The column is added with `ALGORITHM=INSTANT` and is nullable: code from before this change runs on the new schema (Doctrine maps only its known columns, and the old late replay builds its array key by key). Until CLS-4772 ships, every row has `NULL`.
- **Rollback.** `down` drops the column and the promotion attribution of any gift CLS-4772 has created. Roll back CLS-4772 first; before it ships no value is lost.
- **A gift with a promotion and a user.** The entity does not forbid it; the only writer, CLS-4772, sets the promotion alone. The request rule `exactly one of sourceUserId and sourceScenarioId` is unchanged.
- **The `sourceUserId` filter.** A promotion gift has `source_user_id` `NULL`, so filtering by a BO user id never returns it, even when the user id equals a configuration id.
- **Statistics.** `GiftEventJob` carries no source; the KPI events are unchanged.
- **CLS-4540 in flight.** `origin/CLS-4540` (gift requests) adds keys after `sourceScenarioId` in `jsonSerialize()` (`giftRequestId` …), rewrites the late replay's query and extends `bo_user_lists_gifts.feature`. Whichever merges second keeps `sourcePromotionId` directly after `sourceScenarioId` in the entity, the replay array and `GiftControllerTest`'s expected arrays. In celesta-qaa-proteus, CLS-4540 also reworks `gift.pcpr-26`; the second to merge rebases on the first.

## Acceptance criteria

- `GET /api/domain/{domainId}/gifts` returns `sourcePromotionId` on every gift: the stored configuration id for a promotion gift, `null` for a BO or scenario gift.
- A gift created before this change is listed with the same `sourceUserId` and `sourceScenarioId` as before, and `sourcePromotionId` `null`.
- `POST /api/domain/{domainId}/player/{playerId}/gift` answers 201 with `sourcePromotionId` `null`; a replay of the same key, through either replay path, answers 200 with a body equal to the original, `sourcePromotionId` included.
- The same `POST` with `sourcePromotionId` in the body answers 400 with `This form should not contain extra fields.` and records no gift.
- `components.schemas.Gift` documents `sourcePromotionId` as a nullable integer, after `sourceScenarioId`.
- `gift.source_promotion_id` exists as `INT NULL` after the migration and is gone after its `down`.

## Decisions

- **`Source` entity or a column** — a nullable `source_promotion_id` column on `gift`, next to `source_user_id` and `source_scenario_id`; no entity, no backfill, no column drop, so CLS-4773 has no work. Smaller change, and the two existing columns already answer *created by* for users and scenarios · answered by Lucas Franco, 2026-11-17
- **Which id the column holds** — the promotion configuration id (`promotion_configuration.id`), not the instance id; it is what *created by* names, and the activity entry of CLS-4772 already uses the configuration id as its source · answered by Lucas Franco, 2026-11-17
- **Name and place in the API** — `sourcePromotionId`, integer, nullable, after `sourceScenarioId` in `jsonSerialize()` and in the OpenAPI schema; celesta-backoffice (CLS-4775) reads exactly that key · answered by Lucas Franco, 2026-11-17
- **The raw-SQL replay** — `resolveIdempotencyKeyRaceWinner()` returns `sourcePromotionId` too, so a replayed response equals the original · answered by Lucas Franco, 2026-11-17
- **Who writes it** — only CLS-4772, through the setter; no request form accepts `sourcePromotionId`, and the BO reward offer route is unchanged · answered by Lucas Franco, 2026-11-17
- **Existing gifts** — keep `sourceUserId` and `sourceScenarioId` as before, `sourcePromotionId` `null`; held as a regression criterion · answered by Lucas Franco, 2026-11-17
- **Foreign key or index on `source_promotion_id`** — neither, as for `source_user_id` and `source_scenario_id`: no query filters on it and `promotion_configuration` has no delete route · answered by Lucas Franco, 2026-11-17
- **A `sourcePromotionId` filter on the gift list** — not added: no consumer filters by it; CLS-4775 only reads the key · answered by Lucas Franco, 2026-11-17
