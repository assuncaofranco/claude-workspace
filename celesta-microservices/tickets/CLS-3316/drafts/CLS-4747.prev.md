# CLS-4747 — {B} [etl] reward_bonus reason taken from the bonus's reward offering reason

Sub-task: https://celesta.atlassian.net/browse/CLS-4747 · Parent: https://celesta.atlassian.net/browse/CLS-3316 · Repository: celesta-etl

## Overview

The `promotion_reward_bonus` job (`src/etl/triggers.py`, `cron="18 * * * *"`) runs `promotion.reward_bonus.bigquery_copy_mysql_to_global` and rebuilds BigQuery `global.reward_bonus` from scratch every hour: it walks `bonus` in fixed `id` windows, joins `reward_configuration` and `free_round_configuration`, and `get_final_query` replaces the whole table in one `TRUNCATE` + `INSERT` transaction. The column `reward_configuration_reason` is `rc.reason`, the configuration's current legacy key. Editing a configuration therefore rewrites the reason of every past bonus in BigQuery on the next run, which is the problem CLS-3316 fixes.

[CLS-4743](https://celesta.atlassian.net/browse/CLS-4743) gives each bonus its own nullable `bonus.reason_id`, a foreign key to `reward_offering_reason(id)` (soft deleted through `deleted_at`, `name` `VARCHAR(64)`). [CLS-4744](https://celesta.atlassian.net/browse/CLS-4744) seeds every legacy configuration key as a reward offering reason per brand, named exactly as the key, and backfills `bonus.reason_id` from the bonus's configuration. This sub-task makes `reward_configuration_reason` the name of the bonus's own reason, deleted reasons included, and empty when the bonus has no reason. The column keeps its name, position and type, so `global.reward_bonus` keeps its schema and existing readers keep working. PENDING Q1, PENDING Q3.

## Architecture & Design

- **Source of the reason.** The outer `SELECT` reads the reason from a new `LEFT JOIN reward_offering_reason ror ON b.reason_id = ror.id`, mirroring the `LEFT JOIN free_round_configuration frc` already in the same query. The join has no condition on `ror.deleted_at`: a deleted reason keeps its row and its name, the same way the query already exports bonuses of soft-deleted configurations (`rc.deleted_at` is selected, never filtered). It has no condition on the domain either: promotion only stores a reason of the bonus's own brand. `rc.reason` is no longer read by this sync.
- **Text written.** `REPLACE(ror.name, '\n', '')`, the form `src/etl/utils/microservices/game/game/bigquery_copy_mysql_to_global.py` uses for `g.name`. A reason name is free text from the backoffice, and the CSV load (`BigQuery.export_data_csv`, `src/etl/utils/helpers/bigquery.py`) does not set `allow_quoted_newlines`, so one name with a line break would fail the load of the whole table. Migrated reasons are named exactly as the legacy key, so a migrated bonus keeps the text it has today with no transformation. PENDING Q1.
- **Schema.** `ops/sync.py` takes the schema from the live BigQuery table (`get_table_schema_to_json`) and loads the CSV by position, so the expression replaces `rc.reason` in the same slot, between `reward_configuration_free_rounds_game_id` and `reward_configuration_status`. No column is added, renamed or retyped, and nothing changes in celesta-terraform-bi. PENDING Q3.
- **Pagination.** `bonus.reason_id` is added to the `b` CTE. The `min_id` / `max_id` window over `bonus.id` and `should_exit_loop` are unchanged; a `LEFT JOIN` cannot drop rows, so the window logic is not affected.
- **Release gate.** `.github/workflows/ci.yml` `auto_deploy` deploys `master` to `staging-1`, `prod-1` and `prod-2` on merge, so merging is the deploy. The query reads `bonus.reason_id`, which exists only after CLS-4743's migration, and every bonus has an empty reason until CLS-4744's backfill has run. This branch merges only once both are done in all three environments. PENDING Q2.

## Edge Cases & Error Handling

- **Bonus without a reason** (`bonus.reason_id` `NULL`): the `LEFT JOIN` finds nothing and `REPLACE(NULL, ...)` is `NULL`, so the column is written exactly as a configuration without a reason is written today. This applies even when the bonus's configuration still has a legacy `reason`.
- **Deleted reason:** joined like any other, so the bonus keeps showing its name.
- **Configuration edited after the offer:** the bonus's `reason_id` does not change, so its BigQuery reason does not change on the next run.
- **Duplicate names in a brand** (a brand's own `Compensation` next to the seeded `compensation`): each bonus shows its own reason's name; the two texts stay distinct. PENDING Q1.
- **Name with a line break:** the break is removed before the CSV is written, so the load cannot fail on it.
- **Bonuses created with no reason by design:** scenario bonuses (CLS-3316: "a scenario without a reason gives none") and manual offers made before [CLS-4745](https://celesta.atlassian.net/browse/CLS-4745) sends `reasonId` get an empty reason, where today they show the configuration's key.
- **Legacy key with no seeded reason:** a bonus whose configuration key was not seeded by CLS-4744 gets no `reason_id` and an empty reason. CLS-3316 seeds every legacy key; CLS-4744's description still lists 13. PENDING Q1.
- **Merged before CLS-4743's migration:** MySQL rejects `b.reason_id` as an unknown column, every hourly run fails and `global.reward_bonus` stays at its last copy (the failure is in the fetch, before the truncate). The merge gate prevents it. PENDING Q2.
- **Merged after the migration but before the backfill:** every run rewrites the whole table, so every bonus shows an empty reason until the backfill has run, then the next run restores them. The merge gate prevents it. PENDING Q2.
- **Run in progress when the deploy lands:** `get_final_query` replaces the table in one `BEGIN TRANSACTION … COMMIT`, so the table is either the previous copy or the new one.
- **Cost of the join:** one primary-key lookup per bonus row in each `id` window; `reward_offering_reason` holds a few rows per brand. The 3300 s timeout is not touched.

## Open questions

**Q1. Is `reward_configuration_reason` the reason's name as stored, or the name converted to the legacy key form?**

The sub-task's todo list says "write it in the legacy key form (`lower`, spaces → `_`, e.g. `1st_deposit`)". The parent says "BigQuery has the bonus's reason name; for migrated bonuses the name equals the previous slug", and its scope seeds every legacy reason "named exactly as its stored slug". CLS-4744's description still says the opposite: 13 readable names (`Loyalty VIP`, `Sign up`, `1st deposit`, `RAF` …) that "must slug back to the legacy key".

- **A. The name as stored, line breaks removed: `REPLACE(ror.name, '\n', '')`.** *(recommended)* Matches the parent's criterion word for word. With the parent's seed (names equal to the key) a migrated bonus keeps its text with no conversion, and a reason created in the backoffice appears in BigQuery as the brand wrote it. Mirrors the only text clean-up already in the repository (`game/game/bigquery_copy_mysql_to_global.py`). Con: it relies on CLS-4744 being aligned with the parent; if CLS-4744 seeds `Loyalty VIP`, every migrated bonus changes from `loyalty_vip` to `Loyalty VIP` in BigQuery.
- **B. The legacy key form: `REPLACE(LOWER(REPLACE(ror.name, '\n', '')), ' ', '_')`.** Keeps migrated bonuses on the same text whichever way CLS-4744 names the seeded reasons. Cons: a reason created in the backoffice appears in a form nobody typed (`Valentine's day` → `valentine's_day`); a brand's own `Compensation` and the seeded `compensation` collapse into one value; a seeded name that does not slug back (`Sign-up`) silently changes the text; contradicts the parent's "reason name"; no precedent for this conversion in the repository.

Recommendation A, with CLS-4744's description aligned to the parent upstream (names exactly as the key, every key seeded).

**Q2. When does this branch merge, and does the query fall back to the configuration's legacy key?**

Merging deploys to `staging-1`, `prod-1` and `prod-2` (`ci.yml` `auto_deploy`). Before CLS-4743's migration `b.reason_id` does not exist and every run fails (same failure mode as CLS-4694, where a missing wallet table stopped `global.wallet_transaction`). Between the migration and CLS-4744's backfill, every bonus has `reason_id` `NULL`, and because the table is rebuilt every hour, all reasons disappear from BigQuery until the backfill. Once CLS-4746 saves configurations with `reasonId` only, the current code exports an empty reason for bonuses of new configurations.

- **A. Merge gate: after CLS-4743's migration and CLS-4744's backfill are verified in all three environments, before or together with CLS-4745 / CLS-4746 reaching production; no fallback.** *(recommended)* The query stays a straight read of the bonus's reason, which is what every criterion asks; the gate is the same mechanism CLS-4621 used (merge only after the dependency is in prod). Con: this merge waits on the promotion release and on a manual backfill step; the release order has to carry it.
- **B. Fall back to the legacy key: `COALESCE(ror.name, rc.reason)`.** Removes the gap between migration and backfill. Cons: still fails before the migration; breaks "those without a reason have none" and "a scenario without a reason gives none"; for every bonus without a reason, a configuration edit again rewrites its BigQuery reason, which is the bug CLS-3316 exists to remove.
- **C. Merge right after CLS-4743's migration and accept empty reasons until the backfill.** Fewer things to coordinate. Con: every bonus's reason is empty in BigQuery for the duration, visible to every reader.

Recommendation A.

**Q3. Does the bonus's reason stay in `reward_configuration_reason`, or go to a new column?**

The sub-task says "no reason id column, no separate reason table". `ops/sync.py` reads the schema from the live BigQuery table and loads the CSV by position; `global` tables are defined in celesta-terraform-bi (CLS-4621 points at `bigquery/modules/global/*.tf`), so a new column needs a terraform change deployed before the ETL. Who reads `reward_configuration_reason` is not visible from this repository.

- **A. Keep `reward_configuration_reason`, same position and type, now holding the bonus's reason; the readers found by the `INFORMATION_SCHEMA` check are told of the change.** *(recommended)* Matches the sub-task; no schema change, no second repository, no deploy ordering with terraform; readers' queries keep running and get the corrected value. Con: the column name says "configuration" while the value is the bonus's; a reader who relied on it being the configuration's current key sees different values for scenario and manual bonuses and for edited configurations.
- **B. Add a new column (e.g. `reason_name`) at the end and keep `reward_configuration_reason` from `rc.reason`.** Old readers see no change at all. Cons: a celesta-terraform-bi sub-task and an extra deploy step; two reasons per bonus in BigQuery, the old one still rewritten by configuration edits; once configurations stop carrying the legacy key, the old column empties anyway.

Recommendation A.

**Q4. Do the `reward_configuration` and `promotion_reward_configuration` syncs move to the reason name in this sub-task?**

Both export the configuration's legacy `reason` (`reward_configuration/bigquery_copy_mysql_to_global.py:65`, `promotion_reward_configuration/bigquery_copy_mysql_to_global.py:65`). Under CLS-3316 the configuration form stores `reasonId`, so configurations created or edited after CLS-4746 will have an empty `reason` in those BigQuery tables. The parent's only BigQuery criterion is about the bonus.

- **A. Not in this sub-task; raise it on the parent so the PO decides whether those tables need the reason name.** *(recommended)* Keeps this sub-task to its todo list and the parent's criterion; the gap is visible to the PO before release instead of after. Con: until decided, configuration-level reports lose the reason for new configurations.
- **B. Add it here: the same `LEFT JOIN reward_offering_reason` on `reward_configuration.reason_id` in both syncs, in place of `reason`.** Closes the gap in one merge. Cons: outside the sub-task's description and the parent's criteria; changes the meaning of two more BigQuery tables with readers nobody has checked; both syncs page by `id` and merge with `json_to_merge_query`, a different shape from `reward_bonus`, so the change needs its own tests and checks.

Recommendation A.
