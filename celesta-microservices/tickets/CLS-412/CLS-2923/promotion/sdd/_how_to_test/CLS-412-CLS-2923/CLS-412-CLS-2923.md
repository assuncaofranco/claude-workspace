# CLS-412-CLS-2923

**Feature:** the offer endpoint accepts an offer with no back-office user, records which scenario is
behind it, and, given an `idempotencyKey`, answers a repeat with the bonus it already created instead
of making a second one.

## Setup

- Import `CLS-412-CLS-2923.postman_collection.json`. Run with **No environment**.
- Bring up the promotion stack: `make init`, then `docker compose -f docker-compose.dev.yml up -d nginx`.
- Run the whole collection in one go: it is order-dependent and later requests use ids captured earlier.

```bash
newman run CLS-412-CLS-2923.postman_collection.json --env-var "guardKey=<GUARD_KEY>"
```

## Steps

1. Count the bonuses the player already has.
2. Create an enabled manual free reward configuration.
3. Offer it with an `idempotencyKey` and no `sourceUserId` — expect `201`.
4. Offer again with the same key and a different amount — expect `200` and the same bonus.
5. Offer with a different key — expect `201` and a second bonus.
6. Offer with a `sourceScenarioId` — expect `201`.
7. Offer with both `sourceUserId` and `sourceScenarioId` — expect `400` and `AMBIGUOUS_OFFER_SOURCE`.
8. Offer with a currency the player does not hold — expect `400` and `CURRENCY_MISMATCH`.
9. Read the player's bonuses back: exactly three were created, and the scenario one carries its
   `sourceScenarioId` with no `sourceUserId` beside it.

## Variables

| Variable | Example | What it is |
|---|---|---|
| `promotionUrl` | `http://localhost:99` | promotion's own entry point |
| `guardKey` | — | inter-service signing key, passed at run time, never stored here |
| `domainId` | `1` | domain |
| `playerId` | `1` | a player Memberzone resolves, holding EUR |
| `currency` | `EUR` | must match the player's own currency |

Captured at run time: `bonusesBefore`, `rewardConfigurationId`, `firstBonusId`, `secondBonusId`,
`scenarioBonusId`, `idempotencyKey`, `otherIdempotencyKey`, `scenarioIdempotencyKey`.

## Notes

- **Not PO-runnable as it stands.** Every request goes straight to promotion, signed with the
  inter-service guard, because the feature has no entry-point equivalent: the back-office gateway
  builds the offer body itself and sends no `idempotencyKey`. The real caller is celesta-scenario,
  service to service.
- The idempotency keys are generated per run from a timestamp, so the collection can be run
  repeatedly against the same database. The final count is a delta against step 1 for the same reason.
- The guard signature is computed in the collection's pre-request script: HMAC-SHA256 over method,
  host, decoded path and, for writes, the md5 of the body. The URL is resolved before being split —
  signing the template gives a silent 403.
- The attribution is asserted on the **list** read, not on the offer response: the offer answers a
  short body that carries no source field. The list is also the endpoint the backoffice consumes.
- Not covered here: two concurrent calls carrying the same key. A single Newman run is sequential;
  what enforces it is the unique index.
