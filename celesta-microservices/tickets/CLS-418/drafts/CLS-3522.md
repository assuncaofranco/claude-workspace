# CLS-3522 — {A} [statistics] Add pending withdrawals and generosity to the player KPI

Sub-task: https://celesta.atlassian.net/browse/CLS-3522 · Parent: https://celesta.atlassian.net/browse/CLS-418 · Repository: celesta-statistics

## Overview

`GET /api/kpi/{playerId}` returns every atom of the payment, wallet, withdraw-request and game
sources plus the `kpi_formula` rows (`KPIService::getKpiByPlayerIdAndDated`, `KPIResponse`). For
withdrawals it only knows paid ones: the `paid_withdrawal` KPI in `config/kpi.yaml` counts
`event_withdraw_request_transaction` rows with `status: paid` into `kpi_withdraw_request_sum`,
`kpi_withdraw_request_sum_daily` and `kpi_withdraw_request_sum_daily_payment_configuration`.
The backoffice player page (`PlayerStatisticsKpiManager::getWalletData` in celesta-backoffice)
still takes `withdrawalsPendingCount` / `withdrawalsPendingSum` from Wallet MS's legacy KPI table,
which is the last KPI it cannot get from Statistics.

The withdraw request lifecycle already reaches Statistics: the wallet's
`WithdrawRequestEventListener` emits a `WithdrawRequestEventJob` on creation and on every status
change, routed to `statistics_kpi_sqs`; `WithdrawRequestEventJobHandler` stores every status in
`event_withdraw_request_transaction`, keyed `(withdraw_request_id, status)` and carrying
`previous_status`. This sub-task derives pending withdrawals from those events and exposes them on
`/api/kpi`.

Generosity is already served: the `generosity` `kpi_formula` row seeded by
`Version20261407000002` (CLS-419), documented on `KPIResponse` and covered by
`KPIControllerTest` for positive, zero and negative net deposit. [PENDING Q1: no change to
generosity in this sub-task; the formula keeps `giftClaimedAmount`.]

## Architecture & Design

**Definition.** A withdraw request is pending while its status is `pending`, `validated`,
`processing` or `error` (`WithdrawRequestConstants::STATUSES_KPI_PENDING_WD`, and the
`PENDING_WD_CNT` / `PENDING_WD_AMT` definitions). The amount is the request `amount`, not
`payout_amount`, as in the wallet's `WithdrawRequestRepository::getPendingWithdrawalTotalsByCurrency`.

**Storage: two additive KPIs, pending derived on read.** [PENDING Q3: additive KPIs] The pipeline
only adds (`KpiAggregator` yields `count` / `sum` contributions; `KpiWriter` upserts additively), so
a state is stored as what entered it and what left it:

- `requested_withdrawal` — rows with `status: pending`. The event key `(withdraw_request_id,
  status)` makes the `ON DUPLICATE KEY UPDATE` in `EventBatchProcessor::insertBatch` a no-op on
  re-entry, so a request contributes at most one `pending` row, dated by its creation event. This is
  also `REQUESTED_WD_CNT` / `REQUESTED_WD_AMT` (requests that entered `pending` in the period).
- `closed_withdrawal` — rows that leave the pending set for good: `status: paid`, `status: refused`,
  or `status: canceled` with `previous_status` `pending` or `error`. `canceled` from `refused` is
  excluded because `refused` already closed it (`WithdrawRequestConstants::STATUS_TRANSITIONS`:
  `canceled` comes from `pending`, `error` or `refused`; nothing re-enters the set from `paid`,
  `refused` or `canceled`).

Both mirror `paid_withdrawal`: same event table, source `withdraw_request`, dimension
`payment_configuration_id`, columns on the three withdraw-request tables, a cursor row per KPI and
dimension table seeded from `paid_withdrawal`'s by the migration (precedent:
`Version20261406000003` seeding `bonus_claimed` from `bonus_turn_to_real`). The closed filter is
the first list-form filter (OR of groups) in `config/kpi.yaml`; `KpiDefinition::filterGroups`
supports it and `KpiRegistryTest` covers it, and `KpiEventReader` selects every filter key, so
`previous_status` is read without code change. Every atom of a source is exposed (no allow-list,
`KPIService` comment on wallet atoms), so `requestedWithdrawalCount`, `requestedWithdrawalAmount`,
`closedWithdrawalCount` and `closedWithdrawalAmount` appear on `/api/kpi` and
`/api/withdraw-request-kpi`, totals and per configuration.

**Period: pending as of the end of the period.** [PENDING Q2: as of `to`] `pendingWithdrawalCount`
= requested − closed, summed over every day up to `to` (from `kpi_withdraw_request_sum` when `to`
is absent), with the request's currency filter; `from` does not apply. Precedent: the master player
report's "Pending WD amount (on to date)" column (`MasterPlayerReportExporter`,
`MasterPlayerReportBigQueryManager` reading `pending_withdrawal_amount` on `m.date = '$to'`). The
read reuses `AbstractKpiAggregateReader::getAggregated($playerId, null, $to, currency: …)`,
which already reads the daily table with only `date <= :to`.

**Where the subtraction lives.** In `KpiWithdrawRequestAggregateReader`, not in `kpi_formula`.
No precedent: since `kpi_formula` every derived KPI is a row, but `KpiFormulaEvaluator` returns
floats rounded to 2 decimals, which would turn the count into `2.0`, and the rows are evaluated over
the period atoms, not the cumulative ones. The amount is subtracted with `bcsub` at scale 2, as
`KPIService::accumulateTotals` does with `bcadd`.

**Exposure.** Only `/api/kpi`, when `types` includes `withdraw_request` (or is empty), placed
among the withdraw-request fields of `KPIResponse`. Not on `/api/withdraw-request-kpi`: pending per
payout configuration is not asked for.

**Response contract** (fields added to `KPIResponse`; nothing removed or renamed):

| Field | Type | Meaning |
|---|---|---|
| `pendingWithdrawalCount` | integer | requests in `pending`/`validated`/`processing`/`error` at the end of the period |
| `pendingWithdrawalAmount` | number (float, 2 decimals) | sum of their `amount` |
| `requestedWithdrawalCount` | integer | requests created in the period |
| `requestedWithdrawalAmount` | number | sum of their `amount` |
| `closedWithdrawalCount` | integer | requests paid, refused or canceled in the period |
| `closedWithdrawalAmount` | number | sum of their `amount` |

[PENDING Q5: names `pendingWithdrawalCount` / `pendingWithdrawalAmount`]

**History.** Requests created before the new KPIs are processed are not in the requested atoms,
and the ones closed afterwards would be subtracted. [PENDING Q4: backfill DB-to-DB from the wallet
database, outside this repository, with a runbook here mirroring `backfill-bonus-claimed.md` and
`backfill-payment.md`.]

## Edge Cases & Error Handling

- **Re-entry into `pending`** (`validated`→`pending`, `error`→`pending`): the duplicate `(withdraw_request_id, status)` row is dropped by `ON DUPLICATE KEY UPDATE`; the request was already counted once and stays in the set.
- **Refused then canceled**: only `refused` closes; the `canceled` row has `previous_status = refused` and does not match.
- **Out-of-order delivery** (close processed before the `pending` row arrives): pending is −1 for that request until the `pending` row is processed; not clamped, it corrects itself on the next processing run.
- **Event retention**: `kpi:cleanup-events` deletes processed events older than 14 days by default; pending reads the aggregate tables, so it is unaffected.
- **Requests that predate the deploy**: without the backfill, missing or negative. [PENDING Q4]
- **`currency` absent**: sums every currency, as every other atom does today.
- **`to` before any activity**: `0` and `0.0`.
- **Player with only the imported initial paid withdrawals** (`InitialPaidWithdrawalKpiHandler`, `date IS NULL` rows): the new columns default to 0, so pending is unaffected.
- **Generosity, net deposit 0 or rounding to 0.00**: `null` via `ZeroSafeDivisionNode`; negative net deposit gives a negative generosity, as today.

## Open questions (not part of the plan)

**Q1. Generosity is already on master. Drop it from this sub-task, and keep the formula with gifts?**
Evidence: `Version20261407000002` seeds `generosity = (bonusClaimedAmount + giftClaimedAmount) / (successfulPayinAmount - paidWithdrawalAmount - depositRefundAmount) * 100` (commits `72f2dcada`, `86d907ce7`, CLS-419-CLS-3353); `KPIResponse` documents it; `KPIControllerTest::testGetKpiActionGenerosity*` covers positive, zero, zero in cents, negative, currency and gifts; celesta-backoffice `PlayerStatisticsKpiManager::getStatisticsData` already reads `generosity` from Statistics, and its `WalletNormalizer` describes it as "(claimed bonuses amount + claimed gifts amount) / net deposit * 100". The sub-task and the KPI page say claimed bonuses only.
- (a) **Recommended.** No generosity code here; formula stays with gifts. Pros: FR8 (no value change on the BO tile), decided under CLS-419, already tested. Con: the KPI page is out of date (product to update it).
- (b) Change the row to bonuses only with a migration `UPDATE kpi_formula`. Con: changes what the BO shows today, contradicts CLS-419 and the BO OpenAPI.

**Q2. What does "pending withdrawals for a period" return?**
Evidence: KPI page defines `PENDING_WD_*` as requests with status in (pending, validated, processing, error), with no `{period}`, unlike `REQUESTED_WD_*`; master player report has "Pending WD amount (on to date)" (`MasterPlayerReportExporter`, `MasterPlayerReportBigQueryManager`); wallet's live `getPendingWithdrawalTotalsByCurrency` has no period; BO passes `from`/`to` to `/api/kpi`; the wallet legacy table the BO reads today is per-day rows summed over the period (`PlayerKpiRepository`, `sum(pk.withdrawalsPendingCount)`), whose daily meaning lives in BigQuery and was not verified.
- (a) **Recommended.** Pending as of the end of `to`; `from` ignored; no `to` = now. Pros: house precedent (master player report), true point-in-time value, reuses `getAggregated(player, null, to)`. Con: the tile does not change when only `from` moves.
- (b) Requests created in `[from, to]` and still pending now. Pros: moves with both bounds. Cons: needs per-request state, which the additive tables do not hold; mixes "created" with "now".
- (c) Ignore the period, always now. Pros: matches the wallet live endpoint. Con: `to` in the past returns today's value.

**Q3. How is pending stored?**
Evidence: `KpiAggregator` only adds (`count`, `sum`, `count_positive`, `count_distinct`); `event_withdraw_request_transaction` is keyed `(withdraw_request_id, status)` with `previous_status`, indexes on `status` and `date` only (no `player_id`); `KpiEventsCleanupCommand` deletes processed events older than 14 days by default (whether it runs in prod was not verified, no argocd clone read); `paid_withdrawal` and `Version20261406000003` are the patterns for a new KPI on an existing event table.
- (a) **Recommended.** Two additive KPIs, `requested_withdrawal` (status pending) and `closed_withdrawal` (paid, refused, canceled not from refused), pending = requested − closed on read. Pros: mirrors the pipeline, survives event cleanup, supports Q2(a), `requested_*` is the page's `REQUESTED_WD_*`. Cons: four extra atoms exposed on `/api/kpi` and `/api/withdraw-request-kpi` (house rule: every atom exposed); needs a backfill (Q4).
- (b) Read the latest status per request from `event_withdraw_request_transaction` on each request. Cons: old pending requests disappear after retention; needs a `player_id` index on the event table; no precedent for an API reading event tables.

**Q4. Backfill of withdraw requests that exist before the deploy, and who writes the script?**
Evidence: Statistics has read access to the wallet database (`docs/service-boundary.yaml`, `wallet-database`); `backfill-payment.md` uses an external script (`lancastersScripts/script/CEL-8263/BackfillPaymentKpiAggregates.php`) plus `kpi:reconsolidate --daily-from-dimensions`; `backfill-bonus-claimed.md` freezes the cursors around the deploy; `InitialPaidWithdrawalKpiHandler` is the wallet-pushed alternative (job-library `InitialPaidWithdrawalKpiJob`), writing `date IS NULL` rows that `getAggregated` with a `to` never reads.
- (a) **Recommended.** DB-to-DB script outside this repository (new sub-task, or in the scripts repo under this key), importing per day: requested by `created_at`, closed by `status_changed_at` for paid/refused/canceled; runbook in this repository. Pros: full history, works with Q2(a). Con: one more piece of work outside this repo.
- (b) Wallet-pushed initial job, like `InitialPaidWithdrawalKpiJob`. Cons: needs job-library and wallet sub-tasks; the `date IS NULL` bucket is invisible to an as-of-`to` read.
- (c) No backfill. Con: missing and negative values until every pre-deploy request closes.

**Q5. Response field names for CLS-3526.**
Single suggested answer: `pendingWithdrawalCount` (integer) and `pendingWithdrawalAmount` (number, 2 decimals), amount from the request `amount`, not `payout_amount`. Evidence: Statistics' own `paidWithdrawalCount` / `paidWithdrawalAmount`; wallet's `pendingWithdrawalCount` / `pendingWithdrawalAmount`; master player report `pending_withdrawal_amount`; KPI page `WDR_AMT`; wallet `getPendingWithdrawalTotalsByCurrency` sums `wr.amount`. BO maps them to its existing `withdrawalsPendingCount` / `withdrawalsPendingSum`.
