## Contract with payment

**What the wallet sends.** It uses `POST /domain/{domainId}/payment-configuration/{id}/payout`, and only for a group of 2 or more requests (no upper bound):
- `amount` is the sum of the members' `payoutAmount`, rounded to 2 decimals.
- `fee` is the sum of the members' `fee`, or `null` when every member's fee is null.
- `additionalData.withdrawRequestId` is the lead, which is the lowest ID.
- `additionalData.withdrawRequestIds` holds every member ID, lead included, as integers in ascending order.
- A single request sends today's body unchanged, with no list.

**What the wallet reads back:**
- From the synchronous response, `id` and `uid` as today, now written onto every member's withdraw transaction.
- From `TransactionCreateJob` / `TransactionUpdateJob`: `additionalData.withdrawRequestId` (the lead) and `additionalData.withdrawRequestIds`, which arrives as a JSON string and gets decoded. The final status is mapped onto each member.

**A 409 for a group:** the wallet treats it as "a payout already exists". No member is moved to error and the whole group stays `processing`.

**Constraints back on payment (CLS-4753):**
1. The 409 check has to count an ID that is a non-lead member of an active combined payout. Today `TransactionRepository::hasActivePayoutForWithdrawRequest` only matches key `withdrawRequestId`. The contract's "any ID in lead + list already has a payout" should be stated to cover the `withdrawRequestIds` rows too, for single and combined calls.
2. `withdrawRequestIds` has to be on every status job of a combined payout, including the final one, not only on creation.
3. Deploy order: payment, then statistics, then wallet, then backoffice, then front. The wallet rolls back before payment. If an older payment silently drops the list, the lead is paid for the total and the other members stay `processing`.

# CLS-4755 — {A} [wallet] Combine a player's validated Bank Transfer (auto) requests into one payout

Sub-task: https://celesta.atlassian.net/browse/CLS-4755 · Parent: https://celesta.atlassian.net/browse/CLS-1214 · Repository: celesta-wallet

## Overview

Today `withdraw-request:payout-delay` (`PayoutDelayCommand`) moves every payable validated withdraw request to `processing` + `queued`, and dispatches one `PayoutJob` per request. `PayoutJobHandler` hands each request to `PayoutProcessor`, which calls `PaymentClient::postPayout` once per request. `PaymentTransactionJobHandler` later maps the payout's final status onto the one request named in `additionalData.withdrawRequestId`. A player with three validated Bank Transfer (auto) requests therefore causes three bank transfers and three fees.

This change makes the payout run combine the validated Bank Transfer (auto) requests of one wallet on one payment configuration into a single payout for their summed payout amount and fee. The payout carries every request ID. When payment reports the payout's status, every combined request moves to paid or to error. Each request keeps its own amount, its own status changes, its own emails and its own withdraw transaction. One-request groups, every other payout method and the backoffice "pay" action stay on today's path.

The payout contract (the `additionalData.withdrawRequestIds` list, the lead `withdrawRequestId`, no upper bound on the number of IDs, 409 semantics, the list echoed as a JSON string on payment's transaction jobs) is defined by sibling CLS-4753 in celesta-payment.

## Architecture & Design

**Grouping key.** A wallet is one player and one currency in one domain, and a payout targets exactly one payment configuration (`PaymentClient::postPayout`). So "same player, same currency, Bank Transfer (auto)" is implemented as same `wallet_id`, same `payment_configuration_id`, and `payout_method = bank_transfer_auto` (`PaymentConfigurationConstants::PAYMENT_METHOD_BANK_TRANSFER_AUTO`). Requests of one player on two Bank Transfer (auto) configurations are paid in separate payouts.

**Where grouping happens: `PayoutDelayCommand`.** The command keeps its global lock (`payout_command_execution`, Redis-backed `LockFactory`, refreshed per batch, and the cron additionally runs under `flock` on a single pod), so two runs never group the same requests. The run is split in two passes:
1. The existing per-row eligibility (payment configuration, payout schedule) produces the eligible rows.
2. Eligible rows become units:
   - Bank Transfer (auto) rows are bucketed per wallet and configuration. Each bucket is reloaded and rechecked (`validated` and not `queued`, as today; plus `payoutAmount` not null) and sorted by ID ascending. There is no upper bound on the size of a group.
   - A bucket left with two or more requests is a group, led by its lowest ID. A bucket left with one, and every row of any other method, is a single.
   - Every member of a group goes to `processing` + `queued` with the group recorded on it. A single goes to `processing` + `queued` with any stale group record removed.
   - One `PayoutJob` is dispatched per unit: for the lead, or for the single.
   - Batch flushes happen only at unit boundaries, so a group is committed (one Doctrine flush, one database transaction) or skipped as a whole.

No precedent: today one request is one job and one payout. The `queued` handshake and the batch flush/dispatch split are the existing pattern, reused unchanged per member.

**How the group is recorded.** The request's `additional_data` gets a `combinedPayout` key: `{"leadWithdrawRequestId": <int>, "withdrawRequestIds": [<int>, …]}`, ascending, lead included. It is read and written only through `WithdrawRequest` helpers, mirroring `isAutoWithdrawal()` and `getSensorSessionId()`, which read keys from the same JSON. Every other key is kept. The record stays after paid or error as the trace of the payout. It is overwritten when the request is grouped again and removed when the request goes to `processing` as a single (payout run or backoffice PATCH). No migration.

**`PayoutJobHandler`.** For a lead (its own record names itself as lead), the members are the requests in its recorded list that are still `processing` + `queued` with the same recorded lead, on the same wallet. `queued=false` is written on the lead and those members in one flush, then `PayoutProcessor::process($lead, $members)` runs. When the lead itself is not processable, members still `processing` + `queued` under it are moved to error with `queued=false`, as `WithdrawRequestManager::markEnqueueFailed` does for an undispatched request. A redelivered job finds the lead and its members already at `queued=false` and touches nothing, as today.

**`PayoutProcessor`.** One payout for the lead and its members:
- `amount`: the sum of their `payoutAmount`, rounded to 2 decimals.
- `fee`: the sum of non-null fees rounded to 2 decimals, or `null` when every fee is null.
- `additionalData.withdrawRequestId`: the lead, as today.
- `additionalData.withdrawRequestIds`: every ID in ascending order, sent only when there are members.

Customer and bank data come from the lead, as today: for Bank Transfer (auto) the destination is the CRM customer's bank data and `paymentInformation` holds only `paymentConfigurationId`, so all members share it. Every existing outcome now applies to each member:
- Pre-flight failure (CRM, missing withdraw transaction for any member) or payment rejection: error on all.
- 409 or transport failure: all stay `processing`.
- Success: `payment_transaction_id` and the provider ID stored on each member's withdraw transaction, and one user-activity job per member.

Combined request body:

```json
{
  "payoutInformation": {},
  "amount": 4000.0,
  "fee": null,
  "clientId": 434714,
  "additionalData": {
    "withdrawRequestId": 4290150,
    "withdrawRequestIds": [4290150, 4292746, 4301966],
    "...": "customer fields unchanged"
  }
}
```

**409 for a group.** Same reasoning as the existing comment in `proceedPayment`: a payout already exists, and error would make processing → paid illegal. All members stay `processing` with `queued=false`. The log is `critical` and lists every ID, because a group 409 can mean one member had its own payout and the others need an operator.

**`PaymentTransactionJobHandler`.** The per-request block (status map `FINANCIAL_TO_WDR_STATUS_MAP`, workflow validation, save, withdraw transaction update) becomes a private method applied to the lead as today. Then, when `additionalData.withdrawRequestIds` is present, it is json-decoded and applied to every other ID whose request is on the job's wallet and records the job's lead. Others are logged and skipped. All members share the wallet lock the handler already takes. Settling several requests from one payment job has no precedent; the per-request logic is reused unchanged.

**What the player sees.** Status changes are written per request, so `TransactionalEmailListener` (paid email with that request's amount), `WithdrawRequestToFinalStatusListener` (user activity), `WithdrawRequestListener` (CRUD job) and the request history fire per request, exactly as for single payouts. No change there.

**Constants.**
- No new shared constant: the group size has no upper bound.
- The list of combinable methods is a private class constant in `PayoutDelayCommand`, like `EXCLUDED_PAYOUT_METHODS` and `INSTANT_PAYOUT_METHODS` beside it.
- `combinedPayout` and `withdrawRequestIds` are JSON keys written inline, like `is_auto`, `sessionId` and `withdrawRequestId` today.

**Not changed.** The job library (`PayoutJob` still carries one ID), the wallet's HTTP API, the database schema, the backoffice "pay" PATCH (stays single).

## Edge Cases & Error Handling

- **Many requests in one wallet and configuration:** all go in one payout, with no upper bound. If the provider rejects it, every request of the group goes to error and is handled as today.
- **Requests validated in different payout windows:** only requests payable in the same run are combined. The 300-second delay and the configuration's payout schedule decide which run picks them, as today.
- **Request moved by an operator between the run and the job:** dropped from the payout. If it was the lead, the queued members go to error and can be retried from error as today.
- **Group flush fails:** the whole unit stays `validated` (existing flush catch). **Dispatch fails:** the lead and its members go to error.
- **Duplicate `PayoutJob` delivery:** the second sees `queued=false` on all and discards, as today.
- **409:** all stay `processing`, logged `critical` with every ID. Payment's reconciliation and transaction jobs settle what exists.
- **Transport failure:** all stay `processing`, as today.
- **Payment job before the synchronous response is stored:** each member's withdraw transaction is updated by whichever comes first, as today for one request.
- **Payment job listing a request of another wallet, or one not recorded under the lead:** that request is not touched and an error is logged.
- **Deploy window:** payment must be fully rolled out before the wallet. An older payment drops the list and pays the total under the lead, leaving the other members `processing`. Rollback order is wallet first.
- **On-hold requests (CLS-3445):** never candidates, because grouping only takes requests from today's `validated` payable set.
- **Withdraw transactions sharing one provider transaction ID:** allowed. `provider_transaction_id` has a plain index, no unique constraint (`idx_provider_transaction_id`).

## Decisions

- **Grouping key?** Same wallet and same payment configuration, Bank Transfer (auto) only. A wallet is one player and one currency, and a payout targets exactly one payment configuration, so this is how "same player, same currency, Bank Transfer (auto)" is carried. Decided by Lucas.
- **Where is the group recorded on each request?** A `combinedPayout` key in `additional_data`, no migration, read through entity helpers like `isAutoWithdrawal()`; every lookup is by primary key. Decided by Lucas.
- **What does the wallet do when payment answers 409 for a group?** Every member stays `processing`, none goes to error, and the log is `critical` with every ID: error would make the later processing → paid transition illegal, as for a single payout today. Decided by Lucas.
- **A member moved by someone else before the payout job runs?** The members still processing and queued are paid; if the lead is not processable, its queued members go to error so none stays `processing` forever. Decided by Lucas.
- **Is there a maximum number of requests per payout?** No. No limit for Genome or My.Tu exists in the code, a player rarely has more than a few validated requests at once, and if a provider rejects the payout every request goes to error and is handled as today. Decided by Lucas.
- **Is the backoffice "pay" (PATCH validated → processing) grouped?** No: it dispatches one payout at once, with nothing to group with, and clears any stale group record. Decided by Lucas.
- **How are requests on hold excluded?** Nothing is built here: candidates are today's `validated` payable set, so a future on-hold status stays out of it. Decided by Lucas.
- **Rollout guard?** Deploy order only: payment, then statistics, then wallet, then backoffice, then front; the wallet rolls back before payment. Decided by Lucas.
- **Which members does a payment job settle?** The job's `withdrawRequestIds`, each verified against its own record (same wallet, same lead), so a malformed list cannot settle the wrong request. Decided by Lucas.
