## 2. Contract for siblings

**What the backoffice reads ([CLS-4756](https://celesta.atlassian.net/browse/CLS-4756)).** The backoffice gets transaction report lines from `GET /api/bi/transaction_movement`: `StatisticsClient::getTransactionMovements()` calls it and `TransactionReportNormalizer::normalize()` maps each element. Each element is `TransactionMovement::jsonSerialize()`, which uses snake_case keys. This plan adds one key to every element:

| Movement | `withdraw_request_ids` (`list<int>` or `null`) |
|---|---|
| `type` `withdraw`, combined payout | every request ID in the order payment stored them (ascending, lead included), e.g. `[4290150, 4292746, 4301966]` |
| `type` `withdraw`, single payout, or synced before this change | `[withdraw_request_id]`, e.g. `[557795]` |
| `type` `withdraw` with no request ID | `null` |
| every other type (`deposit*`, `refund`, `adjustment`, `withdraw_request`, `initial_balance`) | `null` |

- `withdraw_request_id` does not change (`int` or `null`, the lead request).
- No new filter, sort or aggregate field.
- No backfill. The only migration adds a nullable column inside statistics.
- The backoffice should read the key with a `?? null` default, so rolling statistics back does not break the line.

**What this asks of payment ([CLS-4753](https://celesta.atlassian.net/browse/CLS-4753)).** Nothing in that contract blocks statistics. It needs to hold three things:
- The key is `withdrawRequestIds` and the value is a JSON array of ints with the lead included. Numeric strings are tolerated.
- Payment keeps writing the `withdrawRequestId` row (the lead) on every payout. Both `withdraw_request_id` and the single-payout fallback are built from it.
- The list row is saved in the same flush as the transaction, before `TransactionCreateJob` is dispatched. Statistics builds the movement when it handles that job, and the cron only re-syncs the last 2 days.

**What this asks of wallet ([CLS-4755](https://celesta.atlassian.net/browse/CLS-4755)).** Wallet must not start combining payouts before statistics and its migration are deployed. Otherwise someone has to re-sync by hand with `synchronize:transaction-movements --from=<date>`.

# CLS-4754 — {A} [statistics] Carry every combined request ID on payout transaction movements

Sub-task: https://celesta.atlassian.net/browse/CLS-4754 · Parent: https://celesta.atlassian.net/browse/CLS-1214 · Repository: celesta-statistics

## Overview

Payout movements are built by `TransactionMovementManager::getWithdrawTransactionMovements()`, which reads the payment database directly: `transaction` (type `payout`) left-joined to `transaction_additional_data` on key `withdrawRequestId`, copied into the `withdraw_request_id` int column of `transaction_movement`. It runs live from `PaymentTransactionJobHandler` → `TransactionMovementSynchronizer` (`synchronize:transaction-movements --type=withdraw --external-id=<uid>`) on every payout create/update job, and from the cron with `--from=-2 days`. The backoffice reads the movements from `GET /api/bi/transaction_movement` (`TransactionMovement::jsonSerialize()`) and shows `withdraw_request_id` on the transaction report line.

Sibling CLS-4753 lets one payout pay several withdrawal requests. On a combined payout, payment stores an extra `transaction_additional_data` row: key `withdrawRequestIds`, value a JSON array of integers in ascending order with the lead included, e.g. `[4290150,4292746,4301966]`. The `withdrawRequestId` row keeps the lead ID as today. This sub-task stores that list on the movement and returns it as `withdraw_request_ids`. A payout without a list (single payout, or synced before this change) returns its one ID.

## Architecture & Design

- **Storage.** New nullable column `transaction_movement.withdraw_request_ids`, Doctrine `json`, entity property `?array`. It holds payment's list only when payment stored one; `NULL` otherwise. `new_transaction_movement` is created `LIKE transaction_movement` in `SynchronizeTransactionMovementCommand::PREPARE_SQL`, so the sync's temporary table picks the column up with no change to the command. The repository's other JSON column is `Report::$filters`; this is the first one on `transaction_movement`.
- **Read from payment.** A second left join on `transaction_additional_data` (alias `adl`, `adl.additional_data_key = 'withdrawRequestIds'`), mirroring the existing `ad` join on `withdrawRequestId` exactly. The key is a string literal, as `'withdrawRequestId'` is today; no constant is added. One extra indexed join per payout row (`transaction_id` foreign key); no extra query.
- **Normalisation at sync.** `normalizeWithdrawRequestIds()` turns payment's string into the stored JSON. The value must decode to a non-empty list whose entries are positive integers or digit strings. Entries are cast to int and the list is re-encoded in stored order. Anything else, including `NULL`, `''` and `'null'`, becomes `NULL`. The existing `'null'` handling of `withdraw_request_id` is the closest precedent. The manager has no JSON decoding today.
- **Fallback on read.** `jsonSerialize()` returns the stored list when there is one. Otherwise it returns `[withdrawRequestId]` when `type` is `TransactionMovementConstants::TYPE_WITHDRAW` and `withdrawRequestId` is not null, and `null` in every other case. **No precedent:** `jsonSerialize()` maps columns one to one today (the only special case is the `memberzone_name` key rename), and the existing fallbacks (`movement_id`, `related_movement_id`) are applied at sync time in the manager. Doing it on read is what lets older rows answer without a backfill: the cron only re-syncs the last 2 days, and `SynchronizeTransactionMovementFilter` refuses `--type` without `--external-id`.
- **Contract.** Additive: one new key on every element of `GET /api/bi/transaction_movement`; `withdraw_request_id` and every other key unchanged. In the OpenAPI schema `TransactionMovement`, the property is `withdrawRequestIds`, next to `withdrawRequestId`, following that schema's convention.

```json
{ "type": "withdraw", "withdraw_request_id": 4290150, "withdraw_request_ids": [4290150, 4292746, 4301966] }
```

## Edge Cases & Error Handling

- **No list in payment** (single payout, payouts before CLS-4753, payment not yet deployed): column `NULL`, response `[withdraw_request_id]`. Statistics can deploy before or after payment.
- **Rows synced before this deploy:** column `NULL`, same fallback; no backfill.
- **Malformed list:** stored `NULL`, response falls back to the lead; the sync does not fail.
- **Payout without a lead** (`withdrawRequestId` absent or `'null'`): `withdraw_request_id` `null`; response `null` unless a list is stored, in which case the list is returned as stored.
- **List order and content:** returned as payment stored it (ascending, lead included). Statistics does not re-sort and does not check that the lead is in the list; payment validates both.
- **Status updates:** every payout create/update job re-syncs the movement (delete + insert), reading the list again each time.
- **Deploy window:** statistics and its migration must be live before wallet (CLS-4755) starts combining. Otherwise a combined payout whose status was last set more than 2 days before the statistics deploy keeps only `[lead]` until `synchronize:transaction-movements --from=<date>` is run.
- **Rollback:** roll the code back first, then the migration's `down()` drops the column. Readers must treat a missing key as `null`.

## Decisions

- **Where does the single-ID fallback live, and is there a backfill?** On read in `jsonSerialize()`, `withdraw` rows only; no backfill. Rows synced before the deploy answer correctly at once, while a backfill would need a chunked data migration, since the cron only re-syncs the last 2 days. Decided by Lucas.
- **What do non-combined movements return?** `null` for payouts without a request ID and for every type other than `withdraw`, mirroring `withdraw_request_id` on those movements. Decided by Lucas.
- **Column type?** Doctrine `json`, entity `?array`, so readers get integers without decoding. Decided by Lucas.
- **Migration form?** Plain `ADD ... JSON DEFAULT NULL`, as in `Version20230712135405`; on MySQL 8 a column added at the end is an instant change, while `ALGORITHM=INPLACE` would rebuild the table. Named `Version20261408000001`, so it follows the repository's latest migrations, `Version20261407000001` to `Version20261407000004`. Decided by Lucas.
- **Malformed list from payment?** Stored as `NULL`, so the line falls back to the lead and the sync does not fail; numeric strings accepted. Decided by Lucas.
- **Does the CSV export carry the IDs?** No, out of scope: the export has no request ID column today. Decided by Lucas.
- **OpenAPI property name?** `withdrawRequestIds`, next to `withdrawRequestId`, following that schema's convention. Decided by Lucas.
- **Deploy order?** Payment, then statistics, then wallet, then backoffice, then front. Decided by Lucas.
