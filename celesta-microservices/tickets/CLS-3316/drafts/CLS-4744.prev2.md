# CLS-4744 — {D} [promotion] Migration: seed legacy reasons per brand, backfill reasonId on configurations and bonuses

Sub-task: https://celesta.atlassian.net/browse/CLS-4744 · Parent: https://celesta.atlassian.net/browse/CLS-3316 · Repository: celesta-promotion

## Overview

Today a reward configuration's reason is the legacy key in `reward_configuration.reason` (`VARCHAR(64)`, nullable), checked against the fixed list `RewardConfigurationConstants::REASONS` (31 keys) by the `Assert\Choice` in `Model\Request\RewardConfiguration` and `Model\Request\GiftRewardConfiguration`, which since [CLS-4743](https://celesta.atlassian.net/browse/CLS-4743) runs only when the request sends `reason` (`LegacyReason` validation group). Each brand also has its own reasons in `reward_offering_reason` (CLS-4163): `domain_id`, `name` `VARCHAR(64)`, soft deleted, no database unique on `(domain_id, name)`: the uniqueness is a `UniqueEntity` entity constraint (`RewardOfferingReason.php:30`), checked only when the entity is validated. CLS-4743 adds a nullable `reason_id` to `reward_configuration` and `bonus` (migration `Version20261116103914`: indexes `IDX_C857891A59BB1592` and `IDX_9F987F7A59BB1592`, foreign keys `FK_C857891A59BB1592` and `FK_9F987F7A59BB1592` to `reward_offering_reason(id)`), mapped as `offeringReason` on `RewardConfiguration` and `Bonus`, and stores a reason on every new bonus at creation: the configuration's, or the offer request's `reasonId` when a back-office user or a scenario offers it. After its migration every existing row has `reason_id` `NULL`.

This sub-task fills those columns for existing data, in each environment: per brand, it seeds every legacy key its configurations store as a reward offering reason named exactly as the key, even when the brand already has a reason with that name; it points every non-gift configuration that stores a legacy key to its brand's reason for that key; and it gives every existing bonus of those configurations, created until the cutoff, its configuration's `reason_id`. It is a console command run by hand from the deployment instructions, safe to re-run, that prints the counts per brand. It adds no schema and does not touch `reward_configuration.reason`.

## Architecture & Design

**Where it runs.** A console command, `reward-offering-reason:migrate-legacy`, run per environment after the promotion deploy that carries CLS-4743's migration (Decisions, Q3), with `--dry-run`, `--batch-size` (default 1000) and `--sleep` (milliseconds between bonus batches, default 100), the three options of wallet's `CleanupTransactionAggregationLogCommand`. It mirrors `RetryTargetBetRewardCommand`, the repository's manually run command: a required argument, options, `Command::FAILURE` when the run leaves work undone. Two runs never overlap: the command takes a `LockFactory` lock for its whole run and acquires it without blocking, as `KycStatusJobHandler` does (`acquire()`, return on failure), releasing it in `finally` as `DisableEndedPromotionCommand::expireWithLock()` does; a second run that cannot acquire it exits with `Command::FAILURE` and writes nothing. The lock store is Redis with an expiry (`redis_lock_store` in `config/services.yaml`), so the lock is created with an explicit TTL and refreshed after each pair and each bonus window, and a run longer than the TTL keeps it. The orchestration lives in a new service, `LegacyRewardReasonMigrationService`; the SQL lives in `RewardConfigurationRepository` and `BonusRepository`, as `PromotionRepository::expireEngagedPromotionsForConfig()` does for its raw `UPDATE`. Every read and every write except the seed is raw SQL, so the soft-delete filter does not apply: deleted configurations are seeded, linked and their bonuses updated like any other, because their bonuses are reported too. The seed goes through the ORM (`RewardOfferingReason` and `RewardOfferingReasonRepository::save()`), not raw SQL.

**Which keys, which brands.** The seed reads `reward_configuration` itself rather than `RewardConfigurationConstants::REASONS`: each distinct pair of `domain_id` and stored key, over configurations whose `type` is not `gift` and whose `reason` is not blank, deleted configurations included. A key stored in the data that is not in the fixed list is seeded like any other; a brand with no such configuration gets nothing (Decisions, Q2). Pairs are grouped on the exact stored value (`reason COLLATE utf8mb4_bin`; `BINARY` as an operator is deprecated since MySQL 8.0.27 and the test image is `mysql:8.4`), so two spellings that the `utf8mb4_unicode_ci` collation treats as equal each get a reason named exactly as stored.

**Names.** The seeded reason's `name` is the stored key, unchanged (`loyalty_vip`, `goodwill`, `test`), as the parent specifies, so client reports reading the reason, and the reason name of every migrated bonus in BigQuery, keep the previous slug (Decisions, Q1). A brand's own reason is never reused by name, so a brand that already has `goodwill` or `Goodwill` ends with two. Seeded rows go through `RewardOfferingReason` and `RewardOfferingReasonRepository::save()`, so `created_at` and `updated_at` are set by the Timestampable listener as for any reason. `UniqueEntity` is an entity constraint (`RewardOfferingReason.php:30`) that runs only through the validator, which `save()` does not call, and there is no database unique on `(domain_id, name)`, so the duplicate is stored.

**Configurations.** A pair is selected while at least one of its non-gift configurations has no `reason_id` (`HAVING SUM(reason_id IS NULL) > 0`), together with the reason a configuration of the same brand and key already points to (`MIN(reason_id)`). Per pair: when such a reason exists it is reused and nothing is seeded; only when there is none is a new reason seeded. Then `reason_id` is set on every non-gift configuration of that brand with that exact key and no `reason_id` yet. A configuration created later with a key its brand already had linked is therefore linked to the same reason on the next run, and a re-run never seeds a pair twice. Each pair runs in one transaction, with explicit `beginTransaction()` / `commit()` / `rollBack()` on the connection as `GiftRepository::saveWithinStock()` does; when `linkLegacyReason()` updates 0 rows (another writer got there first), the pair is rolled back, so no reason is left seeded without a configuration. Gift configurations are never linked: the parent requires that gift configurations existing before the release have no reason. `reward_configuration.reason` and `updated_at` are not written.

**Bonuses.** After the seed, one `UPDATE bonus b INNER JOIN reward_configuration rc` sets `b.reason_id = rc.reason_id` for bonuses with no `reason_id`, created at or before the cutoff the command receives, whose configuration is not a gift, stores a non-blank key and has a `reason_id`. The statement runs over windows of `bonus.id` of `--batch-size` ids (default 1000), from `MIN(id)` to `MAX(id)` read at the start of the pass, each window its own autocommitted statement, with `--sleep` milliseconds between windows: row locks on `bonus` (and the shared locks on the `reward_configuration` rows the join reads) last one window, never the whole table. It is not a schema change, so the non-transactional migration and `foreign_key_checks` concerns of CLS-4743's migration do not apply; every id written is a reason that exists. `bonus.updated_at` is not written: the reason is not a change of the bonus, and no Doctrine listener or job runs on raw SQL, so nothing is sent to the wallet or to any consumer. Once a configuration is linked, the bonuses created from it afterwards get its reason at creation from CLS-4743's code (`RewardOfferService::bonusDefaultSetup()` copies `getOfferingReason()`), so they already have one and are skipped; bonuses offered by a back-office user or a scenario store the request's `reasonId` instead, which the current backoffice does not send, so until the cutoff they are created without one and filled here. Promotion has no raw-SQL update over id windows yet: its only batching command, `RefreshRewardConfigurationStateCommand`, batches through the ORM. The precedents for a raw batched write with `--batch-size` and `--sleep` are sibling services: wallet `CleanupTransactionAggregationLogCommand` and crm `DeleteOrphanDocumentCommand`.

**Cutoff.** The command takes `bonusesCreatedUntil` (`Y-m-d H:i:s`, UTC, as `bonus.created_at` is written: `date.timezone = UTC` in `ops/docker/config/php.ini`) and refuses a value in the future. Bonuses created after it keep what their offer path stored. The final run happens right before [CLS-4746](https://celesta.atlassian.net/browse/CLS-4746) goes live, after [CLS-4745](https://celesta.atlassian.net/browse/CLS-4745), and that moment is the cutoff: until then the current front end creates offers and configurations without a reason, so every bonus up to it gets its configuration's; from then on a bonus without a reason can be a user's choice and is never overwritten. Earlier runs, with an earlier cutoff, are allowed and idempotent (Decisions, Q4).

**Report.** After the writes, two grouped reads count per brand: configurations with a non-blank legacy key and not a gift, with and without `reason_id`; and their bonuses created until the cutoff, with and without `reason_id`. The command prints one line per brand with the keys it seeded and these four counts, then the number of bonuses updated. It exits `Command::FAILURE` when any brand still has a configuration or a bonus without a reason, `Command::SUCCESS` otherwise. `--dry-run` writes nothing, lists the keys it would seed or link per brand and prints the current counts; it is how each environment's stored keys are read before the real run. Keys not in `RewardConfigurationConstants::REASONS` are marked in the report (`welcome_offer (not in the fixed list)`), in dry runs and real runs alike.

**Lifetime.** The command stays in the repository until `reward_configuration.reason` is removed, and is removed in the same follow-up, raised on the parent (Decisions, Q5).

**Out of the boundary.** No schema change (CLS-4743), no change to `celesta-constants`, `celesta-job-library`, `gift` or `gift.reason_id`, and no endpoint.

## Edge Cases & Error Handling

- **Same-name reason already in the brand** (`goodwill`, or `Goodwill`): a second one is seeded; configurations point to the seeded one. The brand deletes the one it does not want through the existing endpoint.
- **Spellings equal under the collation** (`Goodwill` and `goodwill` stored on two configurations): grouped on `reason COLLATE utf8mb4_bin`, each gets its own reason named exactly as stored.
- **`NULL`, empty or blank key**: no reason, nothing seeded.
- **Gift configuration with a key**: no reason; its key alone seeds nothing.
- **Deleted configuration**: seeded, linked and its bonuses updated; the raw SQL ignores the soft-delete filter.
- **Key in the data but not in `RewardConfigurationConstants::REASONS`**: seeded and linked like any other, and marked in the report.
- **Bonus that already has a reason** (offered after CLS-4743's deploy from a configuration already linked, or with a `reasonId` in the request): untouched.
- **Bonus created after the cutoff**: untouched; it keeps what its offer path stored.
- **Interrupted run**: each pair commits its reason and its configurations together, each bonus window commits alone; a re-run reuses the reasons already linked, seeds only the pairs that have none, and updates only the bonuses still without a reason.
- **Configuration created with a legacy key while the command runs, or after it**: counted as "without" in the report, the command fails; the next run links it to the reason its brand and key already point to, without seeding.
- **Run after CLS-4746 is live**: not planned; the final run is right before it. A configuration whose reason a user cleared still has its legacy key, so such a run would link it again; the deployment instructions say not to run the command after CLS-4746 goes live.
- **Two runs at the same time**: the second does not get the lock, writes nothing and exits with `FAILURE`.
- **Run longer than the lock's TTL**: the lock is refreshed after each pair and each bonus window, so it does not expire while the run is alive; a run that dies leaves the lock to expire after the TTL.
- **`linkLegacyReason()` updates 0 rows** (the pair's configurations were linked by another writer between the select and the update): the pair is rolled back, so no orphan reason is seeded.
- **Concurrent bonus writes** (claim, expiry, wallet notifications): they wait for at most one window's statement.
- **Unparsable or future cutoff**: `Command::INVALID`, nothing written.
- **Empty `bonus` table**: no window runs.
- **Rollback of the promotion code**: the seeded reasons and the `reason_id` values stay and the previous code ignores them; CLS-4743's `down` drops the columns, and the seeded reasons remain in the brands' lists until deleted through the endpoint. There is no undo command.

|---|---|---|

## Decisions

- **Which sub-task adds the `reason_id` columns on `reward_configuration` and `bonus`** — CLS-4743 adds them, nullable, with an index and a foreign key to `reward_offering_reason(id)`; this sub-task adds no schema and only seeds and backfills, so the code and its schema ship together · Lucas Franco
- **How the foreign key on `bonus.reason_id` is added** — with `SET SESSION foreign_key_checks = 0`, `ALGORITHM=INPLACE, LOCK=NONE`, in a non-transactional migration with `hasForeignKey` guards, as celesta-payment's `Version20260609120749`, so `bonus` is not copied; the backfill here writes only ids of existing reasons · Lucas Franco
- **`reward_configuration.reason`** — stays in place; this sub-task reads it and never writes it · Lucas Franco
- **Q1. Are the seeded reasons named exactly as the stored key, or with readable names?** — Exactly as the stored key (`loyalty_vip`, `goodwill`, `test`), unchanged. The parent's specification is the source: each legacy reason is seeded "named exactly as its stored slug ... so client reports reading the reason keep working", and for migrated bonuses the reason name in BigQuery equals the previous slug; the readable names in this sub-task's description are superseded by it · Lucas Franco, 2026-11-16
- **Q2. Which keys are seeded, and for which brands?** Per brand, each distinct non-blank key its non-gift configurations store, deleted configurations included. Every configuration and bonus with a legacy key gets a reason, keys outside the fixed list included, which is the parent's 100% goal; a brand gets only the keys it used. Keys outside the fixed list are marked in the report · Lucas Franco
- **Q3. Where does the seed and backfill run?** A console command run by hand from the deployment instructions, with `--dry-run`, `--batch-size` (default 1000), `--sleep` and a lock. Migrations stay schema-only, as on CLS-4163; locks on `bonus` last one batch; the command is covered by the unit and Behat suites; the dry run reads each environment's keys before the real run · Lucas Franco
- **Q4. Which bonuses get their configuration's reason, and when does the run happen?** The final run is right before CLS-4746 goes live, after CLS-4745, and that moment is the bonus cutoff: until then the current front end creates offers and configurations without a reason, so no bonus up to the cutoff carries a user's choice. Earlier runs are allowed and idempotent · Lucas Franco
- **Q5. How long does the command stay in the repository?** Until `reward_configuration.reason` is removed, in the same follow-up, raised on the parent: while the column exists the command can still link a configuration created with a legacy key, and one cleanup removes both · Lucas Franco
