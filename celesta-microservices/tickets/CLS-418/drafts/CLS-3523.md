# CLS-3523 — {A} [statistics] Serve daily KPIs for all players of a domain for Segment

Sub-task: https://celesta.atlassian.net/browse/CLS-3523 · Parent: https://celesta.atlassian.net/browse/CLS-418 · Repository: celesta-statistics

## Overview

Statistics serves player KPIs one player at a time. `KPIController` has `GET /api/kpi/{playerId}`, `GET /api/payment-kpi/{playerId}` and `GET /api/withdraw-request-kpi/{playerId}`. Each one is backed by `KPIService` and the `AbstractKpiAggregateReader` subclasses. They read the daily tables `kpi_payment_sum_daily`, `kpi_payment_sum_daily_payment_configuration`, `kpi_withdraw_request_sum_daily` and `kpi_withdraw_request_sum_daily_payment_configuration`, and evaluate the derived KPIs (`netDeposit` among them) from the `kpi_formula` rows through `KpiFormulaEvaluator`. Nothing returns KPIs for many players at once, or one row per day.

Segment's five sync commands rebuild deposit count, deposit amount, net deposit, paid withdrawal count and paid withdrawal amount. They call Payment's `POST /transaction/aggregate/day/{type}` with `splitByCurrency: true`, one window of player ids at a time (`ownerIdAtRanges[0]`, 100 ids by default, from 1 up to the highest customer id) and an optional start day (`statusSetAtRange.from`). They get back one row per player, day and currency, and per payment configuration for the four deposit and withdrawal types. The deposit-by-payment-configuration criterion reads those same rows through their `paymentConfigurationId`.

This sub-task adds the same read to Statistics: daily rows for a window of player ids, per currency, with and without the payment-configuration breakdown. Segment can then switch to it in [CLS-3527](https://celesta.atlassian.net/browse/CLS-3527) without changing how it pages.

## Architecture & Design

**Three daily, many-player reads, mirroring the three per-player reads** `[PENDING Q2: one daily variant per existing per-player endpoint]`:

| New route | Mirrors | Table read | One row per |
|---|---|---|---|
| `GET /api/kpi/daily` | `GET /api/kpi/{playerId}` | `kpi_payment_sum_daily` + `kpi_withdraw_request_sum_daily` | player, day, currency |
| `GET /api/payment-kpi/daily` | `GET /api/payment-kpi/{playerId}` | `kpi_payment_sum_daily_payment_configuration` | player, day, currency, payment configuration |
| `GET /api/withdraw-request-kpi/daily` | `GET /api/withdraw-request-kpi/{playerId}` | `kpi_withdraw_request_sum_daily_payment_configuration` | player, day, currency, payment configuration |

The existing routes constrain `playerId` to `\d+`, so `daily` does not match them. The routes sit under the `/api` prefix of `config/routes.yaml` and inherit `guard_protected: true`, like every other KPI route. Segment's HTTP client already sends `guard_protected` to Payment.

**What Segment reads, and where it comes from:**

| Segment command | Payment today | Statistics after this sub-task |
|---|---|---|
| `player-information:synchronize:deposit-count-aggregated` | `deposit-count` → `count`, `periodAt`, `paymentConfigurationId`, `currency` | `/api/payment-kpi/daily` → `successfulPayinCount`, `periodAt`, `paymentConfigurationId`, `currency` |
| `player-information:synchronize:deposit-amount` | `deposit-amount` → `value`, `date`, `paymentConfigurationId`, `currency` | `/api/payment-kpi/daily` → `successfulPayinAmount`, `periodAt`, `paymentConfigurationId`, `currency` |
| `player-information:synchronize:net-deposit` | `net-deposit` → `value`, `date`, `currency` | `/api/kpi/daily` → `netDeposit`, `periodAt`, `currency` |
| paid withdrawal count command | `paid-withdrawal-count` → `count`, `periodAt`, `paymentConfigurationId`, `currency` | `/api/withdraw-request-kpi/daily` → `paidWithdrawalCount`, … |
| `player-information:synchronize:paid-withdrawal-amount-aggregated` | `paid-withdrawal-amount` → `value`, `date`, `paymentConfigurationId`, `currency` | `/api/withdraw-request-kpi/daily` → `paidWithdrawalAmount`, … |

Payment's `clientId` becomes `playerId`, the name every Statistics KPI response uses. Payment's `date` and `periodAt` become `periodAt` on every row, because the API guidelines suffix date fields with `At`. Payment's `lastAggregatedId` is not returned `[PENDING Q7: omitted]`. The KPI tables have no transaction id, and Segment stores the value without reading it back.

**Paging** `[PENDING Q3: player-id window, no limit/offset]`. The request carries one player-id window, `filter[playerIdRange][from]` and `filter[playerIdRange][to]`, both required, inclusive, `to - from < 1000`. It may also carry a day window, `filter[periodAtRange][from]` and `filter[periodAtRange][to]` (`Y-m-d`, inclusive, both optional). This is the window Payment's `buildFilterSqlPart()` applies (`player_id >= from`, `player_id <= to`, `status_set_at >= from 00:00:00`, `status_set_at <= to 23:59:59`). Every row for the window is returned in one response, as Payment does, ordered by `playerId`, `periodAt`, `currency` and, on the per-configuration routes, `paymentConfigurationId`, all ascending. There is no `limit` or `offset`. The width cap bounds the response instead: the daily tables are unique on (`player_id`, `date`, `currency`[, `payment_configuration_id`]), so one window returns at most (ids × days × currencies × configurations) rows. Segment's default window is 100 ids, and the single-player resync sends `from = to`. There is no domain filter `[PENDING Q1: no domainId; the window spans every domain]`: the KPI tables carry no domain, and Segment's commands do not filter by domain today.

The query is `filter[...]` in the query string, as `sdd/_rules/general/api-guidelines.md` describes. The form follows `PaymentKPIRequestType` (`DateType` single-text `yyyy-MM-dd`, `IntegerType`). `TransactionMovement\FilterType` uses `RangeFilterType` from `SymfonyComponents`, but that type is not followed here, because its fields could not be read. A cross-field rule (`to >= from`, width under 1000) has no precedent in the KPI request models, which only use per-field attributes. It is added with `Assert\Expression` on the model, and that choice has no precedent in this repository.

**Reading.** `AbstractKpiAggregateReader` gains two methods built like `getAggregated()` and `getAggregatedByDimension()`. They use the same `buildSelectExprs()` (`SUM(field) AS camelField` for every field `KpiRegistry::fieldNamesForSource()` lists) and the same `mapRow()` casting. They read `getDailyTable()` and `getDimensionTable()` with `player_id BETWEEN :playerIdFrom AND :playerIdTo`, `date IS NOT NULL`, the optional `date >=` / `date <=`, and `GROUP BY player_id, date, currency[, dimension]`. On the payment and withdraw-request tables the unique key already makes each group one row. The `GROUP BY` keeps the method correct for a daily table with a `source` column (`kpi_game_sum_daily`). The unique keys lead with `player_id`, so the window is an index range scan and no migration is needed. The fields come from the registry, as in every existing read, so a field later added to the `payment` or `withdraw_request` source in `config/kpi.yaml` shows up in these rows without a change here.

**`date IS NULL` rows are left out** `[PENDING Q4: excluded]`. `kpi_payment_sum_daily*` and `kpi_withdraw_request_sum_daily*` hold the all-time bucket for imported players' initial deposits and initial paid withdrawals (`AbstractKpiAllTimeAggregate`, `KpiReconsolidateProcessor::foldAllTimeBucketIntoSum()`). It has no day, and Payment's daily aggregates do not return it either.

**Net deposit per row.** `KPIService::getDailyKpi()` reads the payment and withdraw-request daily rows for the window and merges them on (`playerId`, `periodAt`, `currency`). A side missing from a row is filled with zeros, the way `KPIService::initTotals()` builds totals. The service then runs `KpiFormulaEvaluator::evaluate()` on each merged row, as `getKpiByPlayerIdAndDated()` does on the totals. So `netDeposit` comes from the `kpi_formula` row `successfulPayinAmount - paidWithdrawalAmount - depositRefundAmount`, the same formula `GET /api/kpi/{playerId}` serves. It equals Payment's `sale - payout - refund` term by term. Formula rows whose atoms are not on the row (`ggr`, `rtp`, `ngr`, `generosity`) are skipped by the evaluator. The evaluator reads `kpi_formula` once per instance, so the whole response costs one formula query.

**Payment configuration `0`.** The dimension tables store "no configuration" as `0` (column default). The daily per-configuration rows return it as `null`, which is what Payment returns for a transaction with no configuration `[PENDING Q5: 0 → null on the daily rows only]`. The per-player `PaymentConfigurationKpiItem` and `WithdrawRequestConfigurationKpiItem` are unchanged.

**Errors.** An invalid request returns 400 with the body `FormErrorNormalizer::normalize()` builds, as `getPaymentKpiAction()` and `getWithdrawRequestKpiAction()` do. A window with no rows returns `200 []`.

**Service boundary.** `docs/service-boundary.yaml` lists `backoffice` and `gateway` as consumers of `statistics-api`. Segment is added.

## Edge Cases & Error Handling

- **Player with no KPI rows in the window:** no row for that player, as Payment returns no row today. Segment writes nothing for them, so the value stays 0 on its side.
- **Day with only withdrawals, or only deposits:** `/api/kpi/daily` still returns the row, with the missing side at 0. `netDeposit` is computed from the zeros.
- **Imported player's initial deposit or initial paid withdrawal (`date IS NULL`):** not returned `[PENDING Q4]`. Initial-balance figures stay in `GET /api/kpi/{playerId}` totals only.
- **Same player and day in two currencies:** two rows, one per currency. Payment does the same with `splitByCurrency: true`.
- **Payment configuration not set (`0`):** returned as `null` `[PENDING Q5]`.
- **Window wider than 999, `to < from`, or missing bound:** 400 with the standard validation body. No partial result.
- **Player ids above the highest existing id:** the query returns `[]`. Segment's loop ends on the highest customer id it reads from CRM.
- **Read while `kpi:reconsolidate` rebuilds the same range:** `KpiReconsolidateProcessor` deletes the affected daily rows and rebuilds them outside a transaction, so a read in between can miss rows. The endpoint does not guard this. A Segment resync run after the reconsolidation picks up the rebuilt rows.
- **Paid withdrawals are counted from wallet withdraw requests** (`event_withdraw_request_transaction`, `status: paid`, `sum(payout_amount)`, dated by `status_changed_at`). Payment counts payout transactions (`type payout`, `status success`, `SUM(price)`, dated by `status_set_at`). Where the two differ (fee, a request paid on another day than its payout transaction), the Statistics value is served `[PENDING Q6: Statistics' definition is the one served]`.
- **Fields added later to the `payment` or `withdraw_request` source** in `config/kpi.yaml` appear on these rows, because the readers select every registry field, as the per-player reads do.

## Open questions (not part of the plan)

The parent spec (CLS-418) uses the older layout (Summary / Background / Functional Requirements / Scope / Surfaces touched / Edge Cases / Acceptance Criteria) rather than the five sections. It is **usable** as the specification:
- what must be true: FR 4, 5 and 8, and the AC "Segment criteria results … same before and after (4, 5)";
- for whom: Segment's five sync jobs and the by-payment-configuration criterion;
- under what constraints: same data as the sync jobs read today, no response change elsewhere, a sync window not exceeded.

What it leaves open is below. Q1, Q4 and Q6 touch the parent's wording.

**Q1. Does the read take a domain?** The sub-task title and FR5 say "for all players of a domain". Segment's sync commands do not filter by domain. They walk player ids from 1 to `MemberzoneClient::getCustomersAggregate(max id)` across all domains, and Payment's `buildFilterSqlPart()` has no domain filter. The KPI tables (`AbstractKpiAggregate`) have no `domain_id`.
- **(a) No domain; the player-id window spans every domain.** Evidence: the five `PlayerInformationSynchronize*Command::execute()`, Payment `TransactionRepository::buildFilterSqlPart()`.
  - Pro: drop-in for the paging Segment runs today; no join.
  - Con: the title's wording stays inaccurate unless amended.
- **(b) `/api/domain/{domainId}/…` with a join to the CRM database** (Statistics has read access, per `docs/service-boundary.yaml` `crm-database`).
  - Pro: matches the title.
  - Con: a cross-database join on every call, deeper critical coupling, and Segment would have to loop over domains, which it does not do today. The CRM column names were not read.
- **Recommended: (a).** It is what "as its sync jobs require today" means in code. The title's "of a domain" should read "for a window of players".

**Q2. Route shape.**
- **(a) Three daily routes mirroring Statistics' per-player trio:** `/api/kpi/daily` (combined, with `netDeposit` from `kpi_formula`), `/api/payment-kpi/daily` and `/api/withdraw-request-kpi/daily` (per configuration). Evidence: `KPIController::getKpiAction`, `getPaymentKpiAction`, `getWithdrawRequestKpiAction`; `KpiFormulaEvaluator`.
  - Pro: in-repo precedent and the same reader classes; `netDeposit` uses the same formula as the BO tile; CLS-4328's "add `ngr` to the same daily read, computed with `kpi_formula` `ngr`" becomes adding atoms to one row; one per-configuration call gives Segment both count and amount.
  - Con: Segment's five commands map onto three routes and pick fields, not types.
- **(b) One route per type mirroring Payment:** `GET /api/kpi/daily/{type}` with `deposit-count | deposit-amount | net-deposit | paid-withdrawal-count | paid-withdrawal-amount`, and a uniform row `{playerId, periodAt, currency, paymentConfigurationId, value}`. Evidence: Payment `TransactionController::getTransactionAggregateDayAndType()`.
  - Pro: closest to a one-for-one swap in each Segment command.
  - Con: no precedent in Statistics; type-specific code paths; `netDeposit` needs its own two-table merge anyway; CLS-4328 adds an `ngr` type that bypasses the formula row.
- **Recommended: (a).** It mirrors the repository's own structure and matches how CLS-4328 is already worded.

**Q3. Paging.** Segment pages by player-id window (`batch_size` default 100) and takes every row of the window in one response. The API guidelines advise `limit`/`offset` (0–1000).
- **(a) Required `filter[playerIdRange][from|to]`, width capped at 1000, no `limit`/`offset`.** Evidence: Payment `buildFilterSqlPart()` (single `ownerIdAtRanges[0]`), Segment `$batchStartId`/`$batchEndId` loop.
  - Pro: drop-in.
  - Con: the response is bounded by ids × days × currencies × configurations, not by row count; a full-history resync of 1000 ids returns every day of those players.
- **(b) The window plus `limit`/`offset`.**
  - Pro: follows the guideline.
  - Con: Segment would need an inner loop it does not have; no consumer asks for it.
- **(c) A cap other than 1000:** say which, for example 500 to stay well within the guideline.
- **Recommended: (a) with 1000.** It mirrors the guideline's limit range while keeping the paging Segment uses.

**Q4. Imported players' all-time bucket rows (`date IS NULL` in `kpi_payment_sum_daily*` / `kpi_withdraw_request_sum_daily*`).** The parent's edge case says deposit count and amount include initial-balance figures (CLS-2646). A daily read has no day to put them on.
- **(a) Exclude them.**
  - Pro: identical to what Payment's daily aggregates return today (Payment's `transaction` rows); Segment's `new DateTime($fields['periodAt'])` never sees a null.
  - Con: Segment's deposit criteria still omit initial balances, as today.
- **(b) Return them with `periodAt: null`.**
  - Pro: the data is available.
  - Con: Segment's commands would need a new branch, and its documents are keyed by day (`getCurrencyKeyedId()` formats `periodAt`).
- **Recommended: (a).** The parent's edge case applies to the per-player totals; the parent should say so explicitly for the Segment read.

**Q5. Payment configuration stored as `0`.** The dimension tables default `payment_configuration_id` to 0; Payment returns `null` for no configuration; `PaymentConfigurationKpiItem` returns 0 today.
- **(a) `null` on the new daily rows only.**
  - Pro: Payment returns `null` and Segment's real-time path stores `$event->getPaymentConfigurationId()`, so the synced document matches what Segment writes in real time.
  - Con: two conventions inside Statistics.
- **(b) `0`, as the per-player items.**
  - Pro: consistent inside Statistics.
  - Con: Segment documents get `payment_configuration_id: 0` where they had `null`.
- **Recommended: (a).**

**Q6. Paid-withdrawal definition.** Statistics counts wallet withdraw requests (`config/kpi.yaml` `paid_withdrawal`: `status: paid`, `sum(payout_amount)`, day of `status_changed_at`). Payment's aggregates count payout transactions (`type payout`, `status success`, `SUM(price)`, day of `status_set_at`). I did not verify whether `payout_amount` equals the payout transaction's `price`, or whether the two dates can fall on different days.
- **(a) Serve Statistics' definition.**
  - Pro: the parent's Summary makes Statistics the single source; the BO tiles already show these values.
  - Con: the AC "criteria results … same before and after" can differ for some players.
- **(b) Add a Payment-equivalent paid-withdrawal KPI to Statistics.**
  - Pro: identical numbers.
  - Con: a new KPI definition and backfill, outside this sub-task.
- **Recommended: (a).** The parent's before/after AC should tolerate differences that come from the definition. That note belongs on CLS-418.

**Q7. `lastAggregatedId`.** Payment returns `MAX(t.id)` per row; Segment writes it to `last_aggregated_id` and never reads it outside tests (`PlayerUpdateHandlerTransactionAggregationTest`). The KPI tables carry no transaction id.
- **(a) Omit it; CLS-3527 stops writing it from the sync.**
- **(b) Return `lastAggregatedId: null`.** This only keeps `$fields['lastAggregatedId']` from raising an undefined-key warning in an unchanged Segment.
- **Recommended: (a).** Segment's client and mapping change anyway in CLS-3527.
