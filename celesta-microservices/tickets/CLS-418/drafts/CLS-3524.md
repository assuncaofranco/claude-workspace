# CLS-3524 — {B} [gateway] Source /wallet/balances deposit count from Statistics

Sub-task: https://celesta.atlassian.net/browse/CLS-3524 · Parent: https://celesta.atlassian.net/browse/CLS-418 · Repository: celesta-gateway

## Overview

`GET /wallet/balances` (`WalletInformationController::getWalletBalances()`) answers the player's wallets, one entry
per currency, from wallet's `GET api/domain/{domainId}/wallets/{ownerId}` (`WalletClient::getWalletsByOwner()`), plus
one `successfulDepositCount`. That count comes from wallet's legacy KPI endpoint
`GET api/wallet/{ownerId}/player-statistics-information` (`WalletClient::getSuccessfulDepositCount()`), which reads
the `PlayerKpi` table filled from BigQuery. That table has no currency column, so the count covers every currency.

`GET /wallet/information` (`getWalletInformation()`) already takes its `successfulDepositCount` from celesta-statistics:
`StatisticsClient::getPlayerKpi($playerId, $currency)` → `GET api/kpi/{playerId}?currency=…`, field
`successfulPayinCount`, `0` when absent (since CLS-1534-CLS-1556, with the currency since CLS-550-CLS-1866).

This change moves `/wallet/balances` to the same Statistics read, so the parent's goal holds for the gateway: Statistics
is the only source of the player's deposit count (FR2), with the response unchanged (FR8). The wallet KPI endpoint
stays in place in celesta-wallet (out of scope on the parent); only this repository stops calling it.

## Architecture & Design

**Precedent mirrored.** `getWalletInformation()`: the controller receives `StatisticsClient` by method injection,
calls `getPlayerKpi()`, reads `successfulPayinCount ?? 0`, and wraps the call in `try`/`catch (V2Exception)` that logs
`ErrorMessageConstants::UNKNOWN_ERROR` and throws `ServiceUnavailableHttpException`. `/wallet/balances` reuses
`StatisticsClient::getPlayerKpi()` as it is: no new client, no new method, no change to its signature.

**Currency scope.** celesta-statistics requires `currency` on `GET /api/kpi/{playerId}` (`KPIRequest::$currency` is
`#[Assert\NotBlank]`; blank answers `400`), and answers the totals of that one currency. `/wallet/balances` documents
its count as the "total deposit count" next to balances in every currency, and the wallet value it replaces is
currency-less. So the count is the sum of `successfulPayinCount` over the currencies of the wallets
`getWalletsByOwner()` returns, one `getPlayerKpi()` call per wallet currency. [PENDING Q1: sum over every wallet
currency]

**No precedent for the per-currency fan-out.** No controller in this repository calls a KPI endpoint once per
currency. The nearest pattern is `PaymentTransactionController::getRewardingByTransactionId()`, which calls
`PromotionClient::getRewarding()` once per chunk inside a loop. The calls are sequential (the curl client is
synchronous; nothing in the repository issues concurrent downstream calls). A player has one wallet per currency, so
the number of calls is the number of currencies the player holds.

**Which KPI types.** `getPlayerKpi()` sends only `currency`, so Statistics computes every KPI type (payment, wallet,
withdraw request, game and the formulas) and the gateway reads one field. The call is kept as `/wallet/information`
makes it. [PENDING Q2: keep the call unchanged, no `types[]` filter]

**Failure.** Both reads stay in the one existing `try`/`catch (V2Exception)`: a failure of the wallets read or of any
Statistics call logs `ErrorMessageConstants::UNKNOWN_ERROR` and throws `ServiceUnavailableHttpException` with the
`V2Exception` as previous, exactly as today. The status the player gets is then set by `HttpExceptionSubscriber`
through `UpstreamFailure::fromThrowable()`: `502 BAD_GATEWAY` for an upstream 5xx (what the existing
`testGetWalletBalancesV2ExceptionOnDepositCount` asserts), `504` on a timeout, the upstream status and body for
402/404/409/410/422/429, and `503 SERVICE_UNAVAILABLE` for a misconfigured upstream. This mechanism is unchanged;
only the upstream it guards changes. No partial `200` is returned.

**Removal.** `WalletClient::getSuccessfulDepositCount()` has one caller, `getWalletBalances()` (searched in `src/`,
`tests/`, `config/` and `docs/`). After this change nothing calls it, so it is deleted with its test assertions, its
mock `mockGetDepositsCount()` (also pushed, unused, by `PaymentControllerTest::setUpBeforeClass()`) and its entry in
`docs/service-boundary.yaml`. `WalletClient` itself stays: `getWalletsByOwner()` and the other methods are used.

**Contract.** The response body, field names and types do not change: `successfulDepositCount` stays an integer.
The OpenAPI attributes on `getWalletBalances()` are not touched, so `make openapi` produces the same document and
`celesta-api-gateway` needs no change.

## Edge Cases & Error Handling

- **Player without wallets.** `getWalletsByOwner()` answers `[]`: no Statistics call, `successfulDepositCount` `0`,
  `balances` `[]`. Same body as today for such a player, who has no deposit.
- **Player with no KPI rows in Statistics.** `successfulPayinCount` missing → `0` for that currency (`?? 0`, as in
  `getWalletInformation()`), per the parent's edge case.
- **Player with wallets in several currencies.** One Statistics call per wallet currency; the counts add up.
  [PENDING Q1]
- **Statistics unavailable, or any one of the per-currency calls failing.** The whole request fails through the
  existing `catch (V2Exception)` → `ServiceUnavailableHttpException`; the status is the one `HttpExceptionSubscriber`
  derives today (`502` for a 5xx). No partial count is returned.
- **Wallets read failing.** Unchanged: same `catch`, no Statistics call is made.
- **Deposit not yet in Statistics.** The count reflects what Statistics has consumed; how fast Statistics reflects a
  deposit is out of scope on the parent (CSD-2584).
- **Imported player with an initial balance.** The count includes the initial-balance figures, as Statistics already
  applies since CLS-2646; the gateway does not adjust it.
- **Deploy window.** No migration, no config and no dependency on another sub-task: Statistics already serves
  `GET /api/kpi/{playerId}`. The change is live when the gateway deploys; rollback is a gateway redeploy.

## Open questions (not part of the plan)

**Q1. Which currencies does `successfulDepositCount` on `/wallet/balances` count?**

Statistics requires `currency` on `GET /api/kpi/{playerId}` (`KPIRequest::$currency` `#[Assert\NotBlank]`) and answers
one currency's totals. The value it replaces, wallet's `PlayerKpi` (`deposit_count`, unique on `player_id` + `period`,
no currency column; `KpiManager::get()` and the BigQuery queries take no currency), counts every currency.

- **A. Sum over every wallet currency (recommended).** One `getPlayerKpi($ownerId, $wallet['currency'])` per wallet
  from `getWalletsByOwner()`, added up.
  - Why valid: keeps the value the route answers today (currency-less wallet KPI) and matches its OpenAPI text
    "Balances per currency with total deposit count"; the route already lists every currency.
  - Pros: no change in meaning for a player who deposited in a currency other than their default; a player who
    deposited only in USD with EUR as default does not show `0`.
  - Cons: one Statistics call per wallet currency, sequential; no precedent in the repository for a per-currency KPI
    fan-out (nearest: `PaymentTransactionController::getRewardingByTransactionId()` looping `getRewarding()`).
- **B. The player's default currency only**, `$user->getCustomerData()['currency']`, as `getWalletInformation()`
  falls back to.
  - Why valid: literal mirror of `/wallet/information`; AC2 says "equal to Statistics' `successfulPayinCount` for the
    player", singular.
  - Pros: one call, identical code path to the precedent.
  - Cons: drops deposits in other currencies, so the number changes for multi-currency players, against FR8 (same
    response) in substance.

Recommendation: **A**, because the route is the multi-currency one and the number it replaces was never scoped to a
currency.

**Q2. Should the Statistics call on this route ask only for payment KPIs (`types[]=payment`)?**

`StatisticsClient::getPlayerKpi()` sends only `currency`; Statistics then computes payment, wallet, withdraw-request
and game totals plus the formulas (`KPIService::getKpiByPlayerIdAndDated()`), and the gateway reads one field.
`KPIRequest::$types` accepts `payment`.

- **A. Keep the call unchanged (recommended).** Reuse `getPlayerKpi($playerId, $currency)` as is.
  - Why valid: the sub-task says "as /wallet/information already does"; no client change.
  - Pros: smallest change; `/wallet/information` and its tests untouched.
  - Cons: Statistics computes totals nobody reads, once per wallet currency under Q1-A, on a route the front calls
    for every balance refresh.
- **B. Add an optional `types` argument to `getPlayerKpi()` and pass `['payment']` from `/wallet/balances`.**
  - Why valid: Statistics supports it (`KPIRequestType` `types`, `KPIService` `$includePayment` etc.).
  - Pros: less work per call in Statistics (it still reads paid withdrawals for `netDeposit` when payment is included).
  - Cons: changes the shared client signature (and `StatisticsClientTest::testGetPlayerKpiMethodSignature`, which
    asserts two parameters); no precedent in this repository for filtering KPI types.

Recommendation: **A**; revisit with B only if Statistics latency on this route shows up after release.
