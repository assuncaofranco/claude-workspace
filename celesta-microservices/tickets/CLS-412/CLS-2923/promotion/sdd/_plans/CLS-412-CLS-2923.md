# Plan: CLS-412-CLS-2923 — Offer a bonus with no back-office user, once

branch: CLS-412-CLS-2923
spec: sdd/_specs/CLS-412-CLS-2923.md

## Overview

Four independent changes to the offer endpoint, none of which introduces a new bundle, service or
endpoint:

1. `sourceUserId` stops being required.
2. The request can carry an `idempotencyKey`; a repeat call with the same key replays the first
   bonus instead of creating a second one, and says so by answering `200` where the creating call
   answered `201`.
3. An offer-eligibility refusal leaves the endpoint as a `422` carrying its code, instead of being
   swallowed into a `500`.
4. Every failure answers in one shape, `message` + `code`, with the legacy `error` / `errors` kept
   alongside for the callers that still read them.
5. "Player not found" stops absorbing every upstream failure: only a real Memberzone 404 keeps it,
   anything else becomes `503 UPSTREAM_UNAVAILABLE`.

Wallet routing is no longer a branch here: master removed the `move_bonus_to_promotion` flag in
CLS-2847-CLS-2852 while this branch was open, so `offerReward()` always returns a bonus and the `409`
it used to answer is gone.

## Architecture & Design

### Components affected

| Layer | Component | Change |
|---|---|---|
| Domain | `AppBundle/Entity/Bonus.php` | nullable `idempotencyKey` column, unique constraint on the triple, nullable `sourceScenarioId` column exposed in `jsonSerialize()` |
| Domain | `AppBundle/Offer/Exception/OfferEligibilityException.php` | keep the code string, expose `getErrorCode()` |
| Infrastructure | `AppBundle/Repository/BonusRepository.php` | `findOneByIdempotencyKey()` |
| Infrastructure | one migration in `src/Migrations/` | both columns and the unique index, all online |
| Application | `ApiBundle/Form/Type/RewardConfiguration/RewardOfferType.php` | `sourceUserId` optional, `idempotencyKey` and `sourceScenarioId` declared |
| Application | `ApiBundle/Normalizer/BonusNormalizer.php` | `sourceScenarioId` and `sourceUserId` in `normalizeBonus()` and in the `BonusResponse` schema |
| Domain | `AppBundle/Service/Exception/InvalidRewardConfigurationException.php` | string error codes and `getErrorCode()` |
| Application | `ApiBundle/Controller/RewardConfigurationController.php` | replay lookup, key and scenario assignment, the mutually-exclusive-source check, unique-violation recovery, one error body, the 422 and the upstream split |

`AppBundle/Service/RewardOfferService.php` is **not** touched.

### Key design decisions

1. **Idempotency lives in the controller, not in `RewardOfferService`.** The service returns an
   unpersisted `Bonus` and its own docblock says so; its two other callers mutate the result right
   away — `RewardClaimService.php:47` and `DepositRewardClaimService.php:100` both call
   `setStatus(CLAIMED)`. If the service could return an already-persisted bonus, those callers would
   re-claim an existing one. Keeping the lookup in the controller also leaves the service signature
   alone, so the positional call sites in `DepositRewardClaimServiceTest` and the three
   `RewardHandlerTest` suites stay valid.

2. **The key is supplied, not derived.** A guard derived from player + reward configuration would
   change the backoffice bulk action, which the epic requires to keep working, and would block the
   second offer an `occurrences > 1` configuration legitimately allows. The offering period cannot
   rescue it either — `calculateOfferingPeriodTo()` produces `now + N days` for the manual case, so
   it differs between two deliveries and never matches; the spec has the full argument. A
   read-then-write derived guard also races: two deliveries landing together both read "none yet"
   and both insert — the CLS-2450 duplicate-`sub_balance` shape. The unique index settles it in the
   database.

3. **The unique constraint is on `(player_id, reward_configuration_id, idempotency_key)`, not on
   `idempotency_key` alone.** One action job covers up to 50 players and one reward configuration, so the
   scenario's key is `<scenarioId>:<ActionJob id>:<playerId>`; scoping to the triple means a caller
   may reuse a prefix across configurations without collisions. MySQL treats `NULL`s as distinct in a unique
   index, which is what keeps the keyless backoffice path unchanged.

11. **The created/replayed distinction is carried by the status, not the body.** `201` only on the
    path that inserted the row; both replay paths, the pre-check hit and the race loser, answer
    `200`. The caller needs that fact and cannot derive it — the body is identical either way — and
    a status costs them nothing to read.

    What it deliberately does not claim: it says nothing about whether the caller finished recording
    its own side of the first attempt. A worker that died after dispatching its activity entries and
    before acknowledging its message sees the same `200` as one that died before dispatching them,
    and those two want opposite handling. Giving them the one fact we hold is the whole of our part;
    solving their replay is not.

4. **The replay lookup runs before everything else in the action.** Before the Memberzone call,
   before the currency check, before the condition chain, before any flush.
   A replay must be a pure read, and it must keep answering `200` after the reward configuration has
   since been disabled — the first call already succeeded, and
   re-validating it would make the same request return two different answers over time. The
   corollary is that the rest of the body is ignored on a repeat: the key decides.

5. **The lookup compares the FK directly, without a join.** It is the simplest query for what it
   needs. It is *not* a workaround for the soft-delete filter: a replay for a deleted configuration
   never reaches this code, because `RewardConfigurationValueResolver:41` answers `404` first —
   `getRewardConfiguration()` goes through `createQueryBuilder()` and the `softdeleteable` filter is
   globally enabled (`config/packages/doctrine.yaml:37`). `Bonus` is not soft deletable, so its own
   side needs no filter juggling.

6. **The loser of a race gets the same `200`, with no fallback status.** An error code for a request
   that was satisfied is a lie the caller then records: CLS-2925 would write a refusal onto the
   activity of a player who did receive the offer. That rules out a conflict status and it equally rules out
   letting the violation fall through to the generic `500`.

   The winner is read through the DBAL connection, not the ORM. A failed commit closes the
   EntityManager, and this service does not declare it lazy, so resetting it raises a
   `LogicException` instead of recovering it — checked in dev, test and prod. The connection survives
   the rollback, so the arm queries it directly and builds the response from that row. It also logs,
   being the one path no test reaches.

   The path is rare to begin with: `ActionJobMessageHandler` takes a blocking Redis lock per
   `(playerId, action name)` before dispatching (`celesta-scenario/config/services.yaml:69-83`), so
   a redelivery waits and then lands on the replay lookup. Rare is not the same as impossible, and
   the lock lives in another service — the index is promotion's own guarantee, for a public endpoint
   with callers it does not control.

7. **`OfferEligibilityException` stays a plain `RuntimeException`.** Making it implement
   `HttpExceptionInterface` would route it into the controller's existing generic handler, which
   produces a body with no `code` key — and CLS-2925 needs the code, not the English sentence. A
   dedicated catch placed first gives both the status and the code, and leaves
   `RewardController::claimMultipleRewards`'s `catch (Throwable)` behaviour where it is.

8. **The offer condition chain is not touched.** An earlier draft promoted `BonusOfferAllowedCondition`
   to run on `manual` configurations, so a scenario offer would respect a player who blocked bonus
   offers. It was dropped: a scenario offer is the backoffice bulk action under another trigger, and
   the bulk action does not make that check either. Giving the automated path a stricter rule than
   the operator's own button is a behaviour change the ticket did not ask for, and it reached outside
   the endpoint — `DepositRewardClaimService` swallows the exception, so a `manual` +
   `claimingEvent = deposit` configuration would silently stop granting on deposit.

   The consequence to keep in mind while implementing: since the chain never runs for `manual`, and
   `celesta-scenario` only lets an operator select a `manual` configuration, **none of the five
   `OfferEligibilityException` codes can occur on the scenario's path**. Decision 3 is still right —
   a business refusal collapsing into a `500` is a bug — but it serves the automatic path, which is
   reached from the backoffice. What the scenario's refusals actually need is decision 9.

9. **One error body, `message` + `code`, with `error` and `errors` kept as legacy.** The endpoint
   hand-rolled `error` in three places and `errors` in three others, while its own OpenAPI attributes
   referenced `#/components/responses/not-found` and friends — schemas built on `message` + `code`
   (`src/Kernel.php:45-79`). The documentation described a body that was never returned.

   All of it now goes through one private `offerError()` helper. The legacy keys stay because
   celesta-backoffice's bulk action reads `['error']`
   (`BulkActionBundle/Handler/OfferFreeBonusHandler.php:101`) with a fallback to the generic
   exception message — dropping them would quietly replace a useful message with a useless one on an
   operator's screen, in another team's repository. They are marked deprecated in the schema.

   `InvalidRewardConfigurationException` gains a `getErrorCode()` mapping its five numeric codes to
   strings, for the same reason `OfferEligibilityException` has one: a caller cannot store `1002`.
   The strings are constants on the exception, referenced by the OpenAPI enum too — duplicating them
   as literals would let the documentation drift from the behaviour, which is the defect this whole
   decision exists to remove.

10. **A failure to reach Memberzone is no longer reported as a missing player.** The catch grouped
    `V2Exception`, `InvalidArgumentException` and `TypeError` into one `404 Player not found`. That
    was survivable while the answer was thrown away; CLS-2925 now writes it onto the player's
    activity, and the activity ticket states a wrong row cannot be repaired. So: a Memberzone `404`
    stays `PLAYER_NOT_FOUND`; any other status, an unreachable Memberzone, and a payload with no
    usable domain id become `503 UPSTREAM_UNAVAILABLE`; `TypeError` leaves the group entirely,
    because a programming error masquerading as a business answer is the worst of the three.

    `V2Exception::getCode()` carries the upstream status
    (`vendor/lancasters/curl-library/src/CurlLibrary/GuzzleClient.php:141`), and a connection with no
    response at all is reported as `500` (`CurlClient.php:183`), so both land on the right side.

    Nothing is needed from `celesta-scenario`: it already treats anything outside `[400, 404]` as a
    batch failure rather than a per-player refusal, so it writes no activity entry and reports those
    players as not reached on the session step. Its transport runs `max_retries: 0`, so there is no
    redelivery — those players get nothing from that trigger, which is the honest outcome, not a
    retry. The backoffice bulk action gains from it too: an outage stops being shown to the operator
    as a player who does not exist.

    This is a behaviour change outside the strict ask, and it is worth naming why it is not the same
    kind of change as the dropped condition-chain one. That one gave the automated caller a stricter
    rule than the operator's own button. This one adds no rule: it corrects a label that is already
    wrong today, for every caller, and that this ticket would otherwise make permanent.

12. **The scenario is stored as its own nullable column, and only one source may arrive.** The
    alternative, folding `source_user_id` into a `source_type` + `source_id` pair, is the better model
    in the abstract and the worse change here: it backfills every existing row and renames a field
    that the backoffice, and anything else reading the bonus payload, already consumes. Two nullable
    columns cost one `ALGORITHM=INSTANT` migration and leave every existing reader alone.

    A request carrying both is refused rather than resolved by precedence. A bonus has one origin, and
    a wrong one is not detectable afterwards — nothing in the row says which field the caller meant.
    The check sits after the replay lookup, like every other validation, because decision 4 already
    settled that a repeat is answered from the key and the rest of the body is ignored.

    The column carries no index. Nothing queries by it; the backoffice reads it out of the row it
    already fetched.

    `sourceUserId` joins it in that payload even though it is not new: the normalizer carried neither
    half, and a source column that can only ever name a scenario is worse than none.

    It has to be written in two places, not one. The entity's `jsonSerialize()` is not what the bonus
    list returns: `BonusController::getBonuses()` goes through `BonusNormalizer::normalizeMany()` and
    `normalizeBonus()`, which build their own array. A field added only to the entity reaches the
    database and stops there.

## Implementation Tasks

1. **`Bonus` entity** (`src/AppBundle/Entity/Bonus.php`)
   - `#[ORM\Column(name: 'idempotency_key', type: Types::STRING, length: 64, nullable: true)]
     private ?string $idempotencyKey = null;` after `promotionId`, plus getter and setter.
   - `#[ORM\UniqueConstraint(name: 'uniq_player_reward_config_idempotency_key',
     columns: ['player_id', 'reward_configuration_id', 'idempotency_key'])]` alongside the existing index
     attributes.
   - Do **not** add it to `jsonSerialize()` — that array is the response body of other bonus
     endpoints.
   - `#[ORM\Column(name: 'source_scenario_id', type: Types::INTEGER, nullable: true)]
     private ?int $sourceScenarioId = null;` next to `sourceUserId`, plus getter and setter, and
     **do** add it to `jsonSerialize()`: this one is what the backoffice bonus list has to read.

2. **Migration** (`src/Migrations/VersionYYYYMMDDHHMMSS.php`)
   - `getDescription()` naming the ticket.
   - `up()`: guard on `hasTable('bonus')`, then `hasColumn('idempotency_key')` →
     `ALTER TABLE bonus ADD idempotency_key VARCHAR(64) DEFAULT NULL, ALGORITHM=INSTANT`, then
     `hasIndex(...)` → `ALTER TABLE bonus ADD UNIQUE INDEX uniq_player_reward_config_idempotency_key
     (player_id, reward_configuration_id, idempotency_key), ALGORITHM=INPLACE, LOCK=NONE`.
     The two algorithms differ on purpose — the spec's Database Migrations section has the reasoning.
   - `down()`: same guards, index dropped before the column, both `INPLACE`.
   - `source_scenario_id` in the same file: `hasColumn` guard then
     `ALTER TABLE bonus ADD source_scenario_id INT DEFAULT NULL, ALGORITHM=INSTANT`, dropped `INPLACE`
     in `down()` before the key column.
   - Rename to a timestamp newer than master's latest before merging.

3. **`BonusRepository`** (`src/AppBundle/Repository/BonusRepository.php`)
   - `findOneByIdempotencyKey(int $playerId, int $rewardConfigurationId, string $idempotencyKey): ?Bonus`, in the
     style of `getBonus()`, with `b.rewardConfiguration = :rewardConfigurationId` — no join.

4. **`RewardOfferType`** (`src/ApiBundle/Form/Type/RewardConfiguration/RewardOfferType.php`)
   - drop the `Assert\NotBlank` on `sourceUserId`, and declare it `IntegerType::class`.
   - `->add('idempotencyKey', null, ['constraints' => [new Assert\Length(max: 64)]])` — mandatory, because
     `allow_extra_fields: true` silently drops undeclared fields before `getData()`.
   - `->add('sourceScenarioId', IntegerType::class)`, and `sourceUserId` typed the same way. The
     pairing rule stays in the controller, since it needs the other field's value, but the **type**
     belongs here: untyped, a non-numeric string reaches the `?int` setter and becomes a `500`.
   - OA schema: `required: ['currency']`, `sourceUserId` gains `nullable: true`, new `idempotencyKey`
     and `sourceScenarioId` properties documenting the replay and the exclusivity.

5. **`OfferEligibilityException`** (`src/AppBundle/Offer/Exception/OfferEligibilityException.php`)
   - store `$codeString` in the private constructor, expose `getErrorCode(): string`.
   - stays a `RuntimeException`.

6. **`RewardConfigurationController::offerReward()`**
   (`src/ApiBundle/Controller/RewardConfigurationController.php`)
   - inject `LoggerInterface`.
   - right after `$data = $form->getData()`: read `$idempotencyKey`; if non-null and
     `findOneByIdempotencyKey()` finds a bonus, return `normalizeBonusOffer()` with `200` immediately.
   - after the replay block, refuse a body carrying both `sourceUserId` and `sourceScenarioId` with
     `400` and `AMBIGUOUS_OFFER_SOURCE`. After, not before: a repeat is answered from the key.
   - capture `$rewardConfigurationId = $rewardConfiguration->getId()` before the save.
   - `$bonus->setIdempotencyKey($idempotencyKey)` and `$bonus->setSourceScenarioId($sourceScenarioId)`
     before `$bonusRepository->save($bonus)`. Both on the controller side, so `RewardOfferService`
     keeps its signature and its fourteen positional call sites.
   - wrap **only** the save in `catch (UniqueConstraintViolationException)`: rethrow when `$idempotencyKey`
     is null; otherwise read the winner straight from the connection, log a warning, and return
     `200` with a response built from that row; rethrow if no winner is found, since the violation
     was then a different constraint. No fallback status — see decision 6. Return without flushing
     again: the flush listeners still hold the losing entity in their buffers, which only `postFlush`
     clears.
   - route every failure through one private `offerError(string $message, string $code, int $status)`
     returning `message`, `code`, and the legacy `error` / `errors`.
   - catch order: `OfferEligibilityException` → 422 with its code; `InvalidRewardConfigurationException`
     → its own status with its code; `HttpExceptionInterface` → its status, `OFFER_REFUSED`;
     `V2Exception` split on `getCode()` into 404 `PLAYER_NOT_FOUND` and 503 `UPSTREAM_UNAVAILABLE`;
     `InvalidArgumentException` → 503; `\Exception` → 500. `TypeError` is no longer caught.
   - `OA\Response` for 422 and 503, both referencing a new `OfferErrorResponse` schema declared on
     `offerError()`; 400 becomes a `oneOf` of that and `ValidationErrorsSchema`; describe the replay
     on the success response.
