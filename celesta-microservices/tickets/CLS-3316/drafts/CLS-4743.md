# CLS-4743 — {D} [promotion] reasonId on reward configurations and bonuses, set on every offer path

Sub-task: https://celesta.atlassian.net/browse/CLS-4743 · Parent: https://celesta.atlassian.net/browse/CLS-3316 · Repository: celesta-promotion

## Overview

Today a bonus has no reason of its own. `Bonus` points to its `RewardConfiguration`, and the only reason in the system is `RewardConfiguration::$reason` (column `reward_configuration.reason`), a key from the fixed list `RewardConfigurationConstants::REASONS`. Anything that reads a bonus's reason reads its configuration's current key, so editing a configuration rewrites the reason of every bonus already offered from it. Gifts already reference the brand's own reasons since CLS-4163: entity `RewardOfferingReason`, table `reward_offering_reason`, soft deleted, and `Gift::$offeringReason` on `gift.reason_id`.

This sub-task gives reward configurations (all four types, gift included) and bonuses the same reference: an optional `offeringReason` stored as `reason_id`. Configuration create and edit accept `reasonId`; every path that creates a bonus stores a reason on it at creation, either the one the offer request sends or a copy of the configuration's; configuration and bonus responses return `reasonId` and `reasonName`, deleted reasons included. Once stored, a bonus's reason never follows later edits of its configuration.

The legacy `reason` key is left as it is: still accepted, stored and returned on configurations, still optional, still filterable in the configuration list. Seeding the legacy keys as reasons and backfilling existing rows is [CLS-4744](https://celesta.atlassian.net/browse/CLS-4744); passing `reasonId` from the backoffice is [CLS-4745](https://celesta.atlassian.net/browse/CLS-4745).

## Architecture & Design

**Storage.** `RewardConfiguration` and `Bonus` each gain a nullable `ManyToOne` `offeringReason` to `RewardOfferingReason`, join column `reason_id`, mirroring `Gift::$offeringReason`. Reasons are never hard deleted, so the column always points to an existing row, deleted or not. `reward_configuration.reason` is not touched. This sub-task adds both columns; CLS-4744 only fills them (Decisions, Q2).

**Migration.** One schema migration, in the style of `Version20261019143000` (bonus) and `Version20261102080516`: each column is added with `ALGORITHM=INSTANT`, its index with `ALTER TABLE ... ADD INDEX ..., ALGORITHM=INPLACE, LOCK=NONE` (as in `Version20261019143000.php:35-36`), columns and indexes guarded with `hasColumn` / `hasIndex`. The foreign keys are added with `SET SESSION foreign_key_checks = 0` and `ADD CONSTRAINT ... ALGORITHM=INPLACE, LOCK=NONE`, so MySQL adds them in place instead of copying `bonus`; the columns are all `NULL` at that moment, so there is nothing to check. The migration is not transactional and each foreign key is guarded with `hasForeignKey`. The precedent is celesta-payment `Version20260609120749.php`, which adds a foreign key the same way (`isTransactional()` false, `SET SESSION foreign_key_checks = 0`, `ALGORITHM=INPLACE, LOCK=NONE`, `hasForeignKey` guards); no migration in this repository does it yet (Decisions, Q3). `down` drops the foreign keys, the indexes and the columns.

**Who sets the reason, path by path.** `RewardOfferService::bonusDefaultSetup()` copies `$rewardConfiguration->getOfferingReason()` onto every new bonus, so every path that builds a bonus through `RewardOfferService` gets the configuration's reason without its own code:

| Path | Entry point | Reason stored |
|---|---|---|
| Promotion reward (standard, multiplus) | `offerForPromotionReward()` from both `RewardHandler`s | the configuration's |
| Automatic (segmentation) claim | `RewardClaimService::offerAutomaticBonus()` → `offerReward()` | the configuration's |
| Deposit claim | `DepositRewardClaimService::resolveBonus()` → `offerReward()` | the configuration's |
| Automatic bonuses rendered in the list, not persisted | `offerMultiple()` | the configuration's, at render time |
| Offer endpoint, BO user (`sourceUserId`: manual or bulk) | `RewardConfigurationController::offerReward()` | the request's `reasonId`, or none |
| Offer endpoint, scenario (`sourceScenarioId`) | same | the request's `reasonId`, or none (Decisions, Q1) |
| Offer endpoint, no source | same | the configuration's (Decisions, Q1) |

An existing offered bonus that is claimed later keeps the reason it was stored with: both claim services reuse the stored bonus.

The copy reads the association without loading it: assigning the configuration's proxy to the bonus and flushing writes only its id. A deleted reason is therefore copied like any other, as the specification requires.

**One rule for "which reason may be set".** A new service `RewardOfferingReasonResolver::resolve(int $domainId, ?int $reasonId, ?RewardOfferingReason $kept): ?RewardOfferingReason`:

- `$reasonId` null → null;
- `$reasonId` equal to `$kept?->getId()` → `$kept`, even when it is deleted;
- otherwise `RewardOfferingReasonRepository::getReason($reasonId, $domainId)` (active reasons of the brand only); null → `RewardOfferingReasonNotFoundException`.

`$kept` is the configuration's stored reason: on a configuration edit it lets the configuration keep its own deleted reason; on an offer it lets the caller send the configuration's own deleted reason (the bulk offer sends it). Any other deleted, unknown or other-brand reason is refused. The resolver has two callers, the configuration constraint and the offer action; the factory only applies what the constraint accepted.

**Configuration create and edit.** Both request models (`Model\Request\RewardConfiguration`, `Model\Request\GiftRewardConfiguration`) gain `reasonId` (mapped by the form) and `storedReasonId` (not in the form, set by `RewardConfigurationFactory` from the entity on edit, null on create). A class constraint `RewardConfigurationReasonConstraint` on both models calls the resolver itself (domain, `reasonId`, and the stored reason looked up by `storedReasonId`), so the rule exists in one place; on `RewardOfferingReasonNotFoundException` it adds `This reason does not exist.` at path `reasonId`, so the response is the standard 400 validation error and nothing is saved. It has the shape of `GiftReasonConstraint`. `RewardConfigurationFactory` does not validate again: once the form is valid it sets `offeringReason` to the entity's current reason when `reasonId` equals it, to null when `reasonId` is null, and otherwise to `EntityManagerInterface::getReference(RewardOfferingReason::class, $reasonId)`, which runs no query and is not restricted to active reasons. A reason deleted between validation and save is therefore saved, never a 500 (`post` and `patch` catch nothing around the factory). On edit, a body without `reasonId` keeps the current reason (both edit paths submit without clearing missing fields); `reasonId: null` clears it.

**Legacy `reason` validated only when submitted.** Both edit paths build the request model from the entity (`RewardConfigurationFactory.php:70` for gifts, `map()` at `:106` for the rest), so the stored legacy key is validated by `Assert\Choice(choices: REASONS)` on every PATCH even when the body does not carry `reason`. Once the backoffice stops sending `reason` ([CLS-4745](https://celesta.atlassian.net/browse/CLS-4745)), a configuration whose stored key is not one of the 31 would get a 400 on every edit, permanently. The `Choice` on `reason` moves to a `LegacyReason` validation group in both request models, and both form types set `validation_groups` to `['Default', 'LegacyReason']` only when their `reason` child was submitted, `['Default']` otherwise. A PATCH without `reason` no longer validates the stored key; a request that sends `reason` is validated as today. Validation groups are already used in the repository (`RewardController.php:362`).

**Offer endpoint.** `RewardOfferType` gains `reasonId` (`IntegerType`, `Assert\Positive`). The controller resolves it after the idempotency replay and after the ambiguous-source check, before the call to Memberzone: a replay is answered from the stored bonus and never fails on a reason deleted since. The `try`/`catch` for `RewardOfferingReasonNotFoundException` sits right around the `resolve()` call, not on the action's existing chain, because that chain ends in `catch (\Exception)` (`RewardConfigurationController.php:509`), which turns any exception it reaches into a 500. A refused reason adds `This reason does not exist.` as a `FormError` on the `reasonId` field and returns the form, so the body is the same validation error as any other field error and no bonus is created (Decisions, Q5). The resolved entity is the one set on the bonus, so a reason deleted after the check is still saved. After `offerReward()`, when the call carries a source (Decisions, Q1), the controller sets the resolved reason on the bonus, replacing the configuration's copy, the same way it sets `idempotencyKey` and `sourceScenarioId` today.

**Reading names, deleted reasons included.** The gift reads its reason with a fetch-join under a query that switches the whole soft-delete filter off (`GiftRepository.php:101-113`), because the gift is always loaded by its own repository. A configuration is not: it reaches the normalizers through loaders that keep the soft-delete filter on (the resolver, the automatic list, the promotion handlers), so its reason is often an unloaded proxy, and loading a deleted reason's proxy with the filter on throws. That is why the read side differs from the gift. Nothing therefore reads `getName()` on the association:

- `RewardConfiguration::jsonSerialize()` returns `reasonId` only, from the proxy's id, which does not load it. `Bonus::jsonSerialize()` is not changed (its nested configuration gains `reasonId` through the line above).
- `RewardOfferingReasonRepository::getNamesByIds(int $domainId, array $ids): array<int, string>` reads names with the `softdeleteable` filter disabled and re-enabled in `finally`, as `getReasons()` does.
- `RewardConfigurationNormalizer::normalize()` adds `reasonName` from that method; it already adds `offeredCount` the same way.
- `BonusNormalizer::normalizeMany()` prefetches the names of every reason on the page in one call, as `prefetchCustomAttributes()` does, and `normalizeBonus()` returns the bonus's own `reasonId` and `reasonName`.
- The configuration list (`RewardConfigurationRepository::getApiRewardConfigurations()`) selects `IDENTITY(rc.offeringReason)` with no join, so the query and its soft-delete filter are unchanged and deleted configurations stay hidden; the names of the page's reasons come from one `getNamesByIds()` call after the query.

**Response shape.** New keys `reasonId` (integer or null) and `reasonName` (string or null), as on the gift since CLS-4163, on: the configuration body (GET, POST, PATCH, gift configurations included), each configuration of `GET /reward-configurations`, and each bonus of `GET /bonuses`. The legacy `reason` key stays on configurations, unchanged. The offer response (`BonusOfferResponse`) is not changed (Decisions, Q4).

**Out of the boundary.** No change to `celesta-job-library` (no job carries the reason), to `Gift` or to the gift offer (it already takes `reasonId` since CLS-4163).

After switching branches: `make init`. Both coverage gates are at 100%, so every new line is reached by PHPUnit alone (`phpunit.xml`) and by the combined run.

- `RewardConfigurationTest`: `reasonId` in `jsonSerialize()`, null without a reason.

- BO user (`sourceUserId`) with an active reason → 201, the stored bonus has it, even when the configuration has another one;
- BO user without `reasonId`, and with `reasonId: null` → bonus without reason although the configuration has one;

## Edge Cases & Error Handling

- **Current backoffice after this deploy.** It sends the legacy `reason` and no `reasonId`: configurations save as today with no reason reference; manual and bulk offers carry `sourceUserId` and no `reasonId`, so their bonuses get no reason (they get one once [CLS-4745](https://celesta.atlassian.net/browse/CLS-4745) ships); automatic, deposit and promotion bonuses copy the configuration's reason, which is none until [CLS-4744](https://celesta.atlassian.net/browse/CLS-4744) backfills.
- **Configuration's reason deleted.** Configuration GET, list and edit still return it; automatic, deposit and promotion bonuses still copy it; an offer may send it back; any other deleted reason is refused.
- **Proxy of a deleted reason.** Never loaded under the filter: entities expose only the id, names come from `getNamesByIds()` or the list query with the filter off for reasons. A claim response (`Bonus::jsonSerialize()`) therefore cannot fail on a deleted reason.
- **Reason deleted between validation and save.** Configuration: the constraint accepted the id and the factory sets it by `getReference()`, with no second lookup, so it is saved with it; re-querying active reasons there (`RewardOfferingReasonRepository::getReason`) would throw, and `post` / `patch` catch nothing around the factory, so it would answer 500. Offer: the entity the resolver returned is the one set on the bonus, so it is saved with it too. Either way it then shows like any later-deleted reason.
- **Foreign-key session flag.** `foreign_key_checks` must be back to 1 even when a statement between the two `SET SESSION` fails: the reset sits in a `finally`, or the migration connection is not reused after a failure. A connection left with checks off would let later statements in the same session write unchecked references.
- **Replay after the sent reason was deleted:** answered from the stored bonus, the reason is not re-validated. **Lost idempotency race:** answered from the raw row, whose body has no reason, as today.
- **`reasonId` of another brand equal to the configuration's own id:** impossible, a configuration only stores a reason of its own brand.
- **Non-numeric `reasonId`:** rejected by `IntegerType` as a validation error on `reasonId`, as `sourceUserId` is.
- **Synthesized automatic bonuses** in `GET /bonuses` show the configuration's current reason until claimed; the claim stores the reason current at that moment.
- **Configuration with a legacy `reason` and no `reasonId`:** returns `reason` and `reasonId: null` until the backfill.
- **Stored legacy key outside the 31 keys** (older keys still in the data): the edit paths copy it into the request model, so with `Choice` always on, every PATCH would answer 400 once the backoffice stops sending `reason`, and the configuration could never be edited again. With `Choice` only in the `LegacyReason` group, a PATCH without `reason` saves and leaves the key as stored; sending `reason` is still validated against the list.
- **Rollback of promotion:** the previous code ignores both columns. Running `down` drops them and the reasons stored after the deploy (and the backfill); rolling back the code without `down` keeps them.
- **Migration on a large `bonus` table:** the column is instant, the index online; the foreign key is added in place with checks off.

## Acceptance criteria

| Given | When | Then |
|---|---|---|
| an active reason of the domain | create or edit a configuration of any of the 4 types with its `reasonId` | 200, body `reasonId`/`reasonName`, stored |
| an unknown, deleted or other-domain reason | create or edit a configuration with it | 400 on `reasonId`, nothing saved |
| a configuration whose reason was deleted | edit it keeping that `reasonId`, or without `reasonId` | 200, reason kept |
| a configuration with a reason | edit with `reasonId: null` | reason cleared |
| a configuration whose stored legacy key is not one of the 31 | PATCH without `reason` | 200, legacy key unchanged |
| a configuration with reason X, deleted or not | `GET /reward-configuration/{id}`, `GET /reward-configurations` | `reasonId` and `reasonName` of X |
| a configuration with reason X | a BO user offers it with reason Y | the bonus stores Y |
| a configuration with reason X | a BO user offers it without `reasonId` | the bonus has no reason |
| a configuration whose reason X was deleted | a BO user offers it with X | 201, the bonus stores X |
| an unknown, deleted (not the configuration's) or other-domain reason | an offer sends it | 400 on `reasonId`, no bonus created |
| a configuration with reason X, deleted or not | an automatic claim, a deposit claim or a promotion reward creates a bonus from it | the bonus stores X; none when the configuration has none |
| a scenario offers a configuration with reason X | with `reasonId` Y / without | the bonus stores Y / has no reason |

## Dependencies

- **Blocks** [CLS-4744](https://celesta.atlassian.net/browse/CLS-4744) — the seed and backfill write the columns this sub-task adds.
- **Blocks** [CLS-4745](https://celesta.atlassian.net/browse/CLS-4745) — the backoffice sends `reasonId` on configurations and offers, sends the configuration's `reasonId` with each bulk offer, reads `reasonId`/`reasonName`, and maps the 400 on `reasonId` onto its forms.
- **Related to** [CLS-4747](https://celesta.atlassian.net/browse/CLS-4747) — the ETL joins `bonus.reason_id` to `reward_offering_reason`.
- **Related to** [CLS-4746](https://celesta.atlassian.net/browse/CLS-4746) — the front end reads the fields through the backoffice.
- **Scenario bonus action** — the specification gives the scenario its own reason; no sub-task covers `celesta-scenario` yet. Until one ships, scenario bonuses are stored without a reason.
- **Deploy order:** promotion first; the columns are nullable and the legacy `reason` keeps working, so the current backoffice is unaffected. The Proteus pull request ships with this one.

## Out of Scope

- Seeding the legacy keys as reasons and backfilling `reason_id` ([CLS-4744](https://celesta.atlassian.net/browse/CLS-4744)).
- Removing or deprecating the legacy `reason` field, column or list filter.
- Filtering or aggregating configurations or bonuses by `reasonId`.
- The gift offer: it already stores the request's `reasonId` (CLS-4163) and is not changed; gifts offered by promotions belong to [CLS-3916](https://celesta.atlassian.net/browse/CLS-3916).
- Changing the reason of an existing bonus.
- Adding the reason to `BonusOfferResponse`, to `Bonus::jsonSerialize()` beyond the nested configuration's `reasonId`, or to any job.

## Decisions

| Question | Decision and reason | Decided by |
|---|---|---|
| Q1. Which offer-endpoint calls take the reason from the request, and which copy the configuration's? | Calls with `sourceUserId` or `sourceScenarioId` store the request's `reasonId`, or none when absent; calls with neither source copy the configuration's reason. This follows the parent's criterion that a scenario without a reason gives none even if the configuration has one, and leaves the endpoint ready for the scenario's own select. Until a `celesta-scenario` sub-task ships, scenario bonuses have no reason. | Lucas |
| Q2. Which sub-task adds the `reason_id` columns on `reward_configuration` and `bonus`? | This one adds both columns, their indexes and foreign keys; CLS-4744 only seeds reasons and backfills. The mappings here cannot run without the columns, so code and schema ship and are tested together, and the existing Blocks link (CLS-4743 blocks CLS-4744) stays right. | Lucas |
| Q3. How is the foreign key on `bonus.reason_id` added? | On both tables, in a non-transactional migration, with `SET SESSION foreign_key_checks = 0`, `ADD CONSTRAINT ... ALGORITHM=INPLACE, LOCK=NONE` and `hasForeignKey` guards, as celesta-payment `Version20260609120749.php` does. Adding it the default way copies `bonus` and blocks bonus creation while it runs; with checks off MySQL adds it in place, and the new column is all `NULL`, so there is nothing to check. Same integrity and mapping as `gift.reason_id`. | Lucas |
| Q4. Which responses carry `reasonId` / `reasonName`? | The configuration body (GET, POST, PATCH), each configuration of the list, and each bonus of `GET /bonuses`; the offer and claim responses are unchanged and the legacy `reason` key stays. That covers what the backoffice forms and bonus list read, uses the gift's keys, and leaves the gateway-facing claim response and the raw-SQL race-winner path alone. | Lucas |
| Q5. Where and in what shape does the offer endpoint refuse a reason? | In the controller, after the idempotency replay (`RewardConfigurationController.php:408`) and the ambiguous-source check, as a `FormError` on `reasonId`, which answers the standard 400 validation error. Form validation runs first (lines 392-396) and the replay after it; checking the reason in the form would run before the replay, so a retry after the reason was deleted would get a 400 instead of its bonus. The shape follows `GiftController.php:188`, which adds a `FormError` after validation, and celesta-scenario already maps a 400 on `reasonId` to a node error (`OfferRewardGiftActionJobHandler.php:28`). | Lucas |
