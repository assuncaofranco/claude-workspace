# CLS-4755 — {A} [wallet] Combine a player's validated Bank Transfer (auto) requests into one payout

Sub-task: https://celesta.atlassian.net/browse/CLS-4755 · Parent: https://celesta.atlassian.net/browse/CLS-1214 · Repository: celesta-wallet

## Overview

The payout-delay run (`withdraw-request:payout-delay`, `PayoutDelayCommand`) moves every eligible validated withdraw
request to `processing` and dispatches one `PayoutJob` per request. `PayoutJobHandler` hands it to
`PayoutProcessor`, which posts one payout to payment (`PaymentClient::postPayout()`) for the request's
`payoutAmount` and `fee`, with `additionalData.withdrawRequestId`, and stores the payment transaction on the
request's withdraw transaction. When payment finalises the payout, `PaymentTransactionJobHandler` reads
`additionalData['withdrawRequestId']` from the `TransactionCreateJob` / `TransactionUpdateJob` and moves that one
request to `paid` or `error` through `FINANCIAL_TO_WDR_STATUS_MAP`.

This sub-task makes the run combine a player's validated Bank Transfer (auto) requests of the same wallet and payment
configuration into one payout: the group is recorded on each request as it moves to processing, one payout is sent
for the summed payout amount and fee with every request ID (the contract of
[CLS-4753](https://celesta.atlassian.net/browse/CLS-4753)), the payment transaction is recorded on every grouped
request's withdraw transaction, and every request of the group is settled from the payout's status. One-request
groups, every other payout method and the manual PATCH path stay on today's path. The bank description and the
duplicate guard are payment's ([CLS-4753](https://celesta.atlassian.net/browse/CLS-4753)); the transaction report is
statistics' and backoffice's.

## Architecture & Design

**Group record.** New nullable column `withdraw_request.payout_group_id` (INT), mapped as
`WithdrawRequest::$payoutGroupId` (`?int`). For a group of two or more requests it holds the lead's id on every
member, the lead included; for a request paid alone it is null. The lead is the lowest id of the group. The column is
not added to `jsonSerialize()`, to `API_FIELDS` or to the OpenAPI schema, like `queued`. The audit table
`withdraw_request_audit` gets the same column, because `WithdrawRequest` is an audited entity
(`config/packages/simple_things_entity_audit.yaml`). The migration mirrors `Version20260922140000`: guarded by
`hasColumn`, `ALGORITHM=INPLACE, LOCK=NONE`, no backfill. No index: the group is always read with the wallet, through
`wallet_id`'s existing index.

**Grouping, in `PayoutDelayCommand`.** `getPayableWithdrawRequestIds()` also returns `walletId` and `payoutMethod`.
The command first runs today's per-row checks (payment configuration, payout schedule, eligibility) and keeps the
eligible rows. It then builds units: rows whose `payoutMethod` is
`PaymentConfigurationConstants::PAYMENT_METHOD_BANK_TRANSFER_AUTO` are grouped by `"{walletId}-{paymentConfigurationId}"`
(a wallet is one player in one currency), mirroring `BonusExpirationManager::groupByOwner()`; every other row is a
unit of one. For each unit the requests are loaded, and only those still `validated` and not `queued` are kept, with
today's skip message for the others. Kept requests:

| Kept | Each request | Lead | Dispatch |
|---|---|---|---|
| 1 | `processing`, `queued` true, `payoutGroupId` null | — | its `PayoutJob`, as today |
| 2 or more | `processing`, `payoutGroupId` = lead id | lowest id, `queued` true; members `queued` false | one `PayoutJob`, for the lead |

When a group is formed, any other request of the wallet still carrying the lead's id as `payoutGroupId` (left from an
earlier failed group with the same lead) gets `payoutGroupId` null in the same flush, so the requests carrying a
lead's id are exactly its current group. Flushing still happens every `batch-size` requests, but only after a whole
unit: a group is never split across two flushes.

**Payout, in `PayoutProcessor`.** `PayoutJobHandler` is unchanged for the normal path: it checks the lead is
`processing` and `queued`, sets `queued` false, and calls `process()`. A lead that is not `processing` but is still
`queued` was never picked up: the handler sets `queued` false, saves it, then calls `process()`, so its group fails
pre-flight; a lead with `queued` false was already handled and is skipped as today. A member's own `PayoutJob`, if one
ever runs, is skipped by the existing "already picked up (queued=false)" branch. `process()` resolves the members:
the lead's `findPayoutGroup()` result when `payoutGroupId` equals its own id, otherwise the request alone. Pre-flight
(`collectPayoutContext()`) fails when any member is not `processing` or has no withdraw transaction; the failure moves
every member still in `processing` to `error` with the same message, leaves members in any other status as they are,
and calls nothing on payment. For a group, the payout carries:

```json
{
  "payoutInformation": {},
  "amount": 4000,
  "fee": 0,
  "clientId": 434714,
  "additionalData": {
    "withdrawRequestId": 4290150,
    "withdrawRequestIds": [4290150, 4292746, 4301966],
    "firstName": "…"
  }
}
```

`amount` is the sum of the members' `payoutAmount`, with `bcadd` at scale 2 and cast to float, following
`WithdrawRequestFee`. `fee` is null when every member's `fee` is null, otherwise the `bcadd` sum of the non-null fees
at scale 2, cast to float, as a single request sends its own `fee` today. Customer data, `payoutInformation` and `ip`
come from the lead; for Bank Transfer (auto) `payoutInformation` holds only `paymentConfigurationId`
(`payoutInformationBankTransferAuto`) and the bank details come from CRM, so they are the same for every member. A
one-request payout sends exactly today's body, with no `withdrawRequestIds`. After the call: a rejection marks every
member `error`; a 409 or a transport failure leaves every member in `processing`, as today; on success every member's
withdraw transaction gets `payment_transaction_id`, the provider uid and the account fields, and a user activity job is
emitted per member.

**Settlement, in `PaymentTransactionJobHandler`.** For a payout job, `additionalData['withdrawRequestIds']`, a JSON
string from payment, is decoded; when it is a non-empty list, those IDs are settled, otherwise the single
`withdrawRequestId` as today. Each ID goes through the existing per-request block, moved into a private method
unchanged: find the request, apply the mapped status through the `workflow` validation group, and update its withdraw
transaction. Each request keeps its own amount and withdraw transaction, so the player's history still shows them one
by one.

**Lost dispatch and manual paths.** `WithdrawRequestManager::markEnqueueFailed()` already marks a request whose
`PayoutJob` could not be enqueued as `error`; for a lead it does the same for every member still in `processing`. The
PATCH validated→processing path in `WithdrawRequestController` (operator's manual payout) sets `payoutGroupId` to null
before dispatching, so a request re-paid by hand never carries a stale group.

**Precedents, and choices without one.**

| Choice | Existing reference |
|---|---|
| New nullable column on `withdraw_request` and its audit table, INPLACE, guarded | `Version20260922140000` |
| Column kept out of the API | `queued` (mapped, not in `jsonSerialize()`) |
| Grouping rows in PHP under a string key | `BonusExpirationManager::groupByOwner()` |
| Summing money with `bcadd` | `WithdrawRequestFee` |
| Fee sent as null when there is none | `PayoutProcessor::collectPayoutContext()` (`'fee' => getFee()`) |
| Pre-flight failure marks error without calling payment | `PayoutProcessor::process()` / `markAsError()` |
| 409 and transport failure leave the request in processing | `PayoutProcessor::proceedPayment()` |
| Decoding a JSON string held in additional data | `PayoutProcessor::collectPayoutContext()` (`json_decode(...) ?? []`) |
| One payout and one `PayoutJob` for several withdraw requests | **No precedent**: every payout path handles one request |
| A request in `processing` with `queued` false that never gets a job of its own | **No precedent**: today `queued` false in processing means "picked up by the handler" |
| Clearing another request's stale `payoutGroupId` when a group is formed | **No precedent** |
| Flush batches that wait for a whole unit | **No precedent**: today's batches count single requests |
| Failing a whole group pre-flight while leaving members moved by someone else as they are | **No precedent** |
| Sending a lead found out of processing, never picked up (`queued` true), to the processor so its group fails | **No precedent** |

Not abstracted: no change to `PayoutJob`, `TransactionUpdateJob` or any library, no new constant, no API change.

## Implementation Tasks

1. In `WithdrawRequest`, add `private ?int $payoutGroupId = null` mapped to column `payout_group_id`
   (`integer`, nullable), with `getPayoutGroupId(): ?int` and `setPayoutGroupId(?int): self`. No `OA\Property`; do not
   add it to `jsonSerialize()` or to `WithdrawRequestRepository::API_FIELDS`.
2. Add `src/Migrations/Version20261116120000.php`, mirroring `Version20260922140000`: `up()` adds
   `payout_group_id INT DEFAULT NULL` to `withdraw_request` and to `withdraw_request_audit`, each guarded by
   `hasTable` / `hasColumn`, with `ALGORITHM=INPLACE, LOCK=NONE`; `down()` drops both, guarded the same way.
   `getDescription()`: "Add withdraw_request.payout_group_id (lead of a combined payout) and its audit column."
3. In `WithdrawRequestRepository::getPayableWithdrawRequestIds()`, add `wr.wallet_id AS walletId` and
   `wr.payout_method AS payoutMethod` to the select. Add `findPayoutGroup(WithdrawRequest $lead): array`, returning the
   requests with the lead's wallet and `payoutGroupId` equal to the lead's id, ordered by id ascending.
4. In `PayoutDelayCommand::execute()`, split the row loop in two:
   1. A first pass applies today's checks (null payment configuration, schedule cache, invalid frequency message,
      eligibility cache) and keeps the eligible rows.
   2. A private `buildPayoutUnits(array $rows): array` groups the rows whose `payoutMethod` is
      `PaymentConfigurationConstants::PAYMENT_METHOD_BANK_TRANSFER_AUTO` under the key
      `"{walletId}-{paymentConfigurationId}"`, ids ascending, and makes every other row a unit of one.
   3. For each unit, load each request with `$repo->find()` and keep those that are `validated` and not `queued`,
      writing today's "no longer eligible" line for the others. With one kept request, set `processing`, `queued` true
      and `payoutGroupId` null, as today. With two or more, take the lowest id as the lead; set every kept request to
      `processing` with `payoutGroupId` = lead id, `queued` true on the lead and false on the others; then, for every
      request returned by `$repo->findPayoutGroup($lead)` that is not among the kept ones, set `payoutGroupId` null.
      Persist all of them, add the lead's (or the single request's) id to the dispatch list, add the number of
      persisted requests to the batch count, and mark the payment configuration as handled.
   4. After a whole unit, when the batch count reaches `batch-size`, refresh the lock, call
      `flushAndDispatchBatch()` with the dispatch list, clear the entity manager and reset both, as today.
5. In `WithdrawRequestManager::markEnqueueFailed()`, after the request is saved as `error`: when its `payoutGroupId`
   equals its id, set every other request from `findPayoutGroup()` that is in `processing` to `error` with the same
   message and `queued` false, and save each one, with the same `OptimisticLockException` handling as the lead.
6. In `WithdrawRequestController`, PATCH action: when `$dispatchPayout` is true, call `setPayoutGroupId(null)` next to
   `setQueued(true)`.
7. In `PayoutContext`, replace `Transaction $withdrawTransaction` with `array $withdrawRequests` (every request paid,
   lead included, ids ascending) and `array $withdrawTransactions` (the withdraw `Transaction` of each, keyed by
   request id).
8. In `PayoutProcessor`:
   1. `process()`: resolve the members first, with `findPayoutGroup()` when the request's `payoutGroupId` equals its
      id, otherwise the request alone. On a pre-flight failure, call `markAsError()` for every member whose status is
      `processing`, with the existing pre-flight message.
   2. `collectPayoutContext()`: throw `RuntimeException` "WDR %d of the payout group is %s" when a member is not
      `processing`; find each member's withdraw transaction with `findWithdrawTransaction()`. With more than one
      member, set `amount` to the `bcadd` sum of the members' `payoutAmount` at scale 2, cast to float; set `fee` to
      null when every member's `fee` is null, otherwise to the `bcadd` sum of the non-null fees at scale 2, cast to
      float; and add `withdrawRequestIds` (member ids ascending, integers) to `additionalData`. `withdrawRequestId`
      stays the lead's. With one member, the payload is unchanged.
   3. `proceedPayment()`: on the rejection branch, call `markAsError()` for every member.
   4. `storePaymentTransaction()`: apply today's writes to every member's withdraw transaction and save each.
   5. `emitUserActivity()`: emit the job for every member, each with its own `withdrawal_id`.
9. In `PayoutJobHandler`, in the branch where the status is not `processing`: when the request's `payoutGroupId`
   equals its id and it is still `queued`, set `queued` false, save it with `$repo->save()`, then call
   `$this->payoutProcessor->process($withdrawRequest)`, with the same `OptimisticLockException` / `DBALException`
   handling as the existing path. Any other request in that branch, including a lead with `queued` false, keeps
   today's log line and skip.
10. In `PaymentTransactionJobHandler`, move the body of the payout branch, from `findOneBy` to the withdraw transaction
    save, into `private function settleWithdrawRequest(AbstractTransactionJob $job, int|string $withdrawRequestId): void`,
    unchanged. In the payout branch, decode `additionalData['withdrawRequestIds']` when it is a string; when the result
    is a non-empty array, call `settleWithdrawRequest()` for each entry, otherwise for `additionalData['withdrawRequestId']`.
11. Add and amend the tests listed under Testing Strategy.

## Edge Cases & Error Handling

- **Requests validated in different runs**: the run only picks requests validated at least 300 s ago
  (`PAYOUT_DELAY`), inside the configuration's schedule; requests that become payable in different runs are paid
  separately.
- **A member is not validated, or already queued, when the run loads it**: left out of the group; the run never moves
  a request that is not `validated`. A request on hold (CLS-3445) is not `validated`, so it is never grouped.
- **A member is moved out of processing before the job runs**: the group fails pre-flight; members still in
  `processing` go to `error` with the same message, the moved one is left as it is, payment is not called.
- **The lead is moved out of processing before the job runs**: the lead is still `queued`, so `PayoutJobHandler` sets
  `queued` false, saves it, and sends it to the processor; the group fails pre-flight the same way and the lead is
  left as it is.
- **A `PayoutJob` for the lead is redelivered after the payout was sent**: the lead has `queued` false, so the handler
  skips it as today and never fails members that settlement is about to mark `paid`. Settlement holds the wallet lock
  and the handler holds `withdraw_request_process_%d`; the `queued` check is what keeps them apart.
- **The lead's `PayoutJob` cannot be enqueued**: the lead and every member in `processing` go to `error`.
- **Payment answers 409** (an ID already has a pending or successful payout): every member stays in `processing`, as
  for a single request today.
- **Transport failure**: every member stays in `processing`; payment reconciliation settles them through the job.
- **Recording after the payout fails**: logged with the existing critical message, as today; settlement still comes
  from the job.
- **A member cannot take the settled status** (workflow validation fails): logged and left, as for a single request
  today; the other members are still settled.
- **Stale group on a request re-paid later**: a group formed again by the run rewrites `payoutGroupId` and clears it
  on the old group's leftovers; the manual PATCH payout clears it.
- **Big groups and batching**: a group is flushed whole, even when it exceeds `batch-size`. The size of the ID list is
  bounded by payment's `additional_data_value` (CLS-4753, about 60 ids); a payout that fails there is a rejection and
  every member goes to `error`.
- **Rollout**: an old wallet pod would pay only the lead of a group, or settle only the lead. Before the wallet deploy,
  the Jenkins job `wallet-payout-delay` (it runs `withdraw-request:payout-delay` through
  `kubectl exec service/wallet-active`, `ops/jenkins/wallet-payout-delay.jenkinsfile`) is disabled; it is re-enabled
  once every wallet pod runs this version. `PayoutJob`s already queued by an old run are single payouts and are paid
  as today.
- **Rollback of payment below CLS-4753 while the wallet sends lists**: payment drops the list and pays the total under
  the lead only; payment is not rolled back below that version once this is deployed.

## Out of Scope

- Grouping on the manual PATCH payout path.
- Exposing `payout_group_id`, or the other requests a request was paid with, through any API.
- Combining other payout methods, other players or other currencies.
- Splitting a combined payout after it was sent.

## Decisions

- **Where is the group recorded on each request?** New nullable column `withdraw_request.payout_group_id` holding the
  lead's id, with the same column on `withdraw_request_audit`, migration mirroring `Version20260922140000`, kept out
  of `jsonSerialize()`. Decided by Lucas.
- **What happens when a member is no longer processing, or has no withdraw transaction, when the payout runs?** The
  whole group fails pre-flight: every member still in processing goes to error with the same message, members moved
  by someone else are left as they are, payment is not called. Decided by Lucas. A lead found out of processing goes
  to the processor only while it is still `queued` (never picked up), after `queued` is saved false; a lead with
  `queued` false was already handled and is skipped, so a redelivered job never fails members that settlement is about
  to mark paid. Decided by Lucas.
- **How is the rollout kept from paying or settling only the lead?** A manual release action: the Jenkins job
  `wallet-payout-delay`, which runs `withdraw-request:payout-delay`, is disabled before the wallet deploy and
  re-enabled once every wallet pod runs this version; no env flag. Decided by Lucas.
- **Which request is the lead?** The lowest id of the group. Decided by Lucas.
- **What fee does a group payout carry?** Null when every member's fee is null, otherwise the `bcadd` sum of the
  non-null fees, as a single request sends its own fee today. Decided by Lucas.
