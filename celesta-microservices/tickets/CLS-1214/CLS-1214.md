# CLS-1214 combine withdrawal requests into one payout

**Feature:** a player's validated Bank Transfer (auto) requests of the same wallet and payment configuration are paid in one payout; the group settles together and the report line carries every id.

## Setup
- Stacks up: gateway, backoffice, payment, wallet, statistics. **Not run yet:** wait for the coordination to release them.
- `python3 -I gen.py` regenerates both collections; `./run.sh` runs the local flow (credentials from 1Password at run time).
- Order matters. Locally `run.sh` plays the cron and the queue consumers between the Newman parts; in preprod the crontab does, so import the collection and run it whole (set `pollMax` for the 5-minute cron, weekdays 05-18 UTC).
- Needs: the player has a Bank Transfer (auto) payout configuration **with a payout schedule** (the command skips configurations without one), enough withdrawable balance (folder 0 tops it up through the BO), and the BO user can validate withdrawal requests.

## Steps
1. Folder 0: tokens; read the player's payout configurations (picks A: bank_transfer_auto, B: a second one, other: another method; each is skipped when absent); top up the balance if short.
2. Folder 1 (player): withdraw D (stays pending), A, B, C (same configuration), E (other method), G (other configuration).
3. Folder 2 (BO): validate A, B, C, E, G. The lowest id of A, B, C is the lead.
4. Wait for `withdraw-request:payout-delay` (300 s after validation, then the next cron run).
5. Folder 3 (BO): A, B, C end in the same status, paid or error; each keeps its own amount; D is still pending; E is paid on its own (auto method) or stays `validated` (manual method).
6. Folder 4 (player): one withdraw transaction per request, none for the summed amount; each shows its own status, equal across the group, `success` when the group is paid.
7. Folder 5 (BO report): one payout line, `withdrawRequestIds` = A, B, C ascending, `withdrawRequestId` = lead, amount = sum of payout amounts, fee = sum or null, status follows the group; B and C have no line of their own; E (auto method) and G have their own.
8. Folder 6: request F alone, validate it. Wait for the next run.
9. Folder 7: F settles; its line lists only `[F]`; amount and fee are its own.

## Notes
- PO-runnable in preprod: `CLS-1214.postman_collection.json`, entry points only (gateway, BO). `CLS-1214.dev-only.postman_collection.json` calls payment directly (guard-signed, `guardKey` from the vault): not PO-runnable.
- Where the spec's criteria and the plans' decisions differ, the decision wins:
  - "same method" (criterion 3) becomes wallet + payment configuration (plan 4755): two Bank Transfer (auto) configurations of one player are paid separately. Request G checks it.
  - "the report shows the IDs" (criterion 6) becomes a new `withdrawRequestIds` list next to `withdrawRequestId`, which stays the lead until CLS-4758; a single payout returns `[its own id]` (plans 4754, 4756).
  - "on hold is never combined" (criterion 9): CLS-3445 is in Backlog and the status does not exist. D stays `pending`, the nearest thing that is not `validated`; swap it for a held request when CLS-3445 lands.
  - "Total amount" (criterion 1) is the sum of the members' `payoutAmount` (plan 4755), not of the requested amounts. They differ when the configuration charges a fee: the description's example (2500 + 1000 + 500 = 4000) has no fee. The report line is checked against the payout amounts.
  - A request that is not `processing` fails the whole group (decision 2026-11-16, was "pay the rest"). Not reachable from an entry point.
- Not covered by this collection, and why:
  - Bank description (criterion 2): the Genome and My.Tu transfer description has no entry-point read; `GenomeProviderTest` and `MyTuProviderTest` cover it.
  - Different currency: a currency is a wallet; the player has one. `PayoutDelayCommandUnitTest` covers two wallets of one player.
  - `PayoutJob` redelivered without failing members: only the queue redelivers it.
  - Criteria 4 and 5 are branches of one run: the provider decides which one happens. Run once with `expectedGroupStatus=paid` and, if the environment's provider mock can be steered, once with `error`. "Followed up together" is covered by the report line listing every id with status `failure`.
  - List over 512 characters: payment's payout is internal. The DEV-ONLY collection sends 70 ids and a lead outside the list, both expecting 400 before any write. Through the entry points it would take about 60 requests of one player.
  - Front (CLS-4757): UI, no HTTP.
- Player side (criterion 7): the collection reads `/wallet/transactions`, the only per-request view the gateway exposes. I did not check which endpoint the brand site itself calls; the status there is the withdraw transaction's, not the request's.
- E is the other payout method: the discovery prefers one the command pays on its own. A method with no payout schedule is skipped by the command, so E would time out in the poll; then drop E from the run.
- First real run may need these adjusted (written from the code, not yet seen): the report `amount` against the sum of `payoutAmount` (it may include the fee); `fee` null versus 0 on the report line; the `amount` key of `/wallet/transactions`; the `list` key of `/payout/configurations`.
- A group can split if the cron fires between two validations (about 1 s apart, against a 300 s window): rerun.
- Scripts: the first version ran against a stub of these endpoints (81 assertions, 0 failures; three broken variants each fail where expected). The later edits (E, player status, criteria 4 and 5) are only syntax-checked, 44 scripts, not run.
