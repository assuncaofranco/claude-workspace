# Spec: CLS-412-CLS-2923

branch: CLS-412-CLS-2923
ticket: CLS-2923 — [promotion] API - offer a bonus with no back-office user, once
epic: CLS-412 — Offer bonus as a scenario action

## Summary

The offer endpoint can only be called by a backoffice user, and it happily creates a second bonus
for a repeated call. CLS-412 turns "offer bonus" into a scenario action, so the same endpoint has to
answer a caller that has no BO user behind it and that can deliver the same action twice.

Three things block that today, all on
`POST /api/domain/{domainId}/player/{playerId}/reward-configuration/{rewardConfigurationId}/offer`:

| # | Today | File |
|---|---|---|
| 1 | `sourceUserId` is `NotBlank` and is written onto `Bonus::$sourceUserId` | `ApiBundle/Form/Type/RewardConfiguration/RewardOfferType.php:38`, `AppBundle/Service/RewardOfferService.php:148` |
| 2 | `offerReward()` builds `new Bonus()` on every call — a repeat creates a second row | `AppBundle/Service/RewardOfferService.php:55` |
| 3 | `OfferEligibilityException` is a plain `RuntimeException`, caught by the controller's `catch (\Exception)` and returned as `500 Internal server error` with the message discarded | `AppBundle/Offer/Exception/OfferEligibilityException.php:7`, `ApiBundle/Controller/RewardConfigurationController.php:363` |

Blocker 3 matters beyond this ticket: CLS-2925 records the refusal reason on the player's activity
entry, so the reason has to survive the HTTP boundary in a machine-readable form.

Nothing scenario-shaped is stored on the bonus. The cause of the offer is recorded by the caller as a
player activity entry, the way `manual_bonus_offered` already is.

The `move_bonus_to_promotion` flag and its `409` are gone from the endpoint: master removed the flag
in CLS-2847-CLS-2852 while this branch was open, `offerReward()` no longer returns `null`, and the
cells that keyed on the flag went with it.

### What "once" keys on

Caller-supplied, not derived. The request carries an optional `idempotencyKey`; it is persisted on the
bonus and protected by a unique index on `(player_id, reward_configuration_id, idempotency_key)`. A repeat
call with the same key replays that bonus with `200` instead of creating a second one, where the
call that created it answered `201`.

Two reasons for a supplied key over deriving one from player + reward configuration + offering
period:

- **The backoffice stays byte-for-byte unchanged.** It sends no key, the column is `NULL`, and MySQL
  allows any number of `NULL`s in a unique index. A derived guard would silently change the bulk
  action, which the epic requires to keep working. Deriving would also block the legitimate second
  offer that an `occurrences > 1` configuration allows.
- **A read-then-write guard has a race.** Two deliveries of the same action job landing together
  both read "no bonus yet" and both insert. That is the duplicate-`sub_balance` failure already seen
  in CLS-2450. The unique index settles it in the database instead of in PHP.
- **The offering period cannot carry the comparison.** `calculateOfferingPeriodTo()` resolves it
  three ways. When the caller supplies nothing and the configuration is manual, or automatic with no
  `offerPeriodTo`, the value is `now + N days`, computed at the instant of the call — two deliveries
  thirty seconds apart produce values thirty seconds apart, so an equality test never matches and
  the guard never fires. When the configuration is automatic *with* an `offerPeriodTo`, the value is
  a fixed date shared by every offer of that configuration, so the guard matches always and blocks
  the second offer an `occurrences > 1` configuration exists to allow. Wrong in both directions,
  and no tolerance window fixes both at once.

The caller reached the same conclusion from its own side: the scenario has no `offerPeriodTo` to
send, so a derived key was never something it could have participated in.

The scenario sends `<scenarioId>:<ActionJob id>:<playerId>`. `AbstractJob::$id` is `uniqid('job_')`,
fixed at construction and serialized with the message, so it survives a redelivery; the job carries
up to 50 players, hence the player id; and `uniqid()` is only unique within one process, hence the
scenario id in front. Read from `OfferBonusActionJobHandler::getIdempotencyKey()` on their branch,
not from what was agreed in chat — the two differ.

Two same-key calls arriving at the same instant are rare in practice: `ActionJobMessageHandler`
takes a blocking distributed lock per `(playerId, action name)` before dispatching a handler, backed
by Redis (`celesta-scenario/config/services.yaml:69-83`), so a redelivery waits for the first
attempt to finish and then hits the replay lookup. The unique index is still the guarantee that
matters here: this endpoint is public API, the lock lives in another service, and promotion cannot
depend on a caller behaving well. The loser of a genuine race is answered with the same `200` as any
other replay — an error status for a request that was in fact satisfied would be recorded by
CLS-2925 as a refusal on the activity of a player who did receive the offer.

## Functional Requirements

- [ ] `sourceUserId` is optional. When absent, the bonus is created with `source_user_id = NULL`.
- [ ] `idempotencyKey` is an optional string (max 64) on the request body, persisted on the bonus.
- [ ] A second call carrying an `idempotencyKey` already used for the same player and reward configuration
      returns `200` with the bonus created by the first call, and creates no second row.
- [ ] Two concurrent calls with the same key end with exactly one bonus, and both callers get `200`
      with the same bonus.
- [ ] A call with no `idempotencyKey` behaves exactly as today, including creating a second bonus when
      repeated.
- [ ] `sourceScenarioId` is an optional integer on the request body, persisted on the bonus and
      returned by the endpoints that serialise a bonus, so the backoffice bonus list can show that a
      scenario, and which one, is behind the offer.
- [ ] A call carrying both `sourceUserId` and `sourceScenarioId` is refused with `400` and
      `AMBIGUOUS_OFFER_SOURCE`, and writes nothing.
- [ ] A refusal from the offer condition chain is returned as `422` with the refusal code in the body.
- [ ] The offer condition chain keeps its current reach: it runs for `automatic` configurations and
      not for `manual` ones. A scenario offer is the backoffice bulk action under another trigger,
      so it gets the same eligibility treatment, no more and no less.

## Architecture / Module Placement

Existing bundles modified, no new bundle.

- `AppBundle` (domain + infrastructure)
  - `Entity/Bonus.php` — new nullable `idempotencyKey` column and unique constraint, new nullable
    `sourceScenarioId` column, exposed in `jsonSerialize()`
  - `ApiBundle/Normalizer/BonusNormalizer.php` — `sourceScenarioId` in `normalizeBonus()` and in the
    `BonusResponse` schema, which is what the bonus list endpoint actually returns
  - `Repository/BonusRepository.php` — `findOneByIdempotencyKey()`
  - `Offer/Exception/OfferEligibilityException.php` — keeps its code string, exposes `getErrorCode()`
- `ApiBundle` (application boundary)
  - `Form/Type/RewardConfiguration/RewardOfferType.php` — `sourceUserId` optional, `idempotencyKey`
    and `sourceScenarioId` added
  - `Controller/RewardConfigurationController.php` — replay lookup, key and scenario assignment,
    the mutually-exclusive-source check, unique-violation recovery, `422` catch
- `src/Migrations/` — one migration

`RewardOfferService` is deliberately **not** changed. It returns an unpersisted `Bonus` that its two
other callers mutate immediately — `RewardClaimService.php:47` and `DepositRewardClaimService.php:100`
both call `setStatus(CLAIMED)` on the result. A service that sometimes returns an already-persisted
bonus would re-claim an existing one. Idempotency is an HTTP transport concern and stays in the
controller; the service signature is untouched, so its callers and the positional call sites in the
unit tests are untouched too.

No new services, no DTOs, no Messenger messages, no workflow changes.

## API Endpoints

| Method | Path | Auth | Description |
|--------|------|------|-------------|
| POST | `/api/domain/{domainId}/player/{playerId}/reward-configuration/{rewardConfigurationId}/offer` | unchanged | Offer a reward configuration to a player |

Request body — changes only:

| Field | Type | Required | Constraint |
|---|---|---|---|
| `sourceUserId` | integer or `null` | **was required, now optional** | — |
| `idempotencyKey` | string | optional (new) | max 64 |
| `sourceScenarioId` | integer or `null` | optional (new) | rejected when `sourceUserId` is also set |

What the caller actually sends, read from `PromotionClient::offerReward()` on celesta-scenario's
branch: `currency`, `idempotencyKey`, `amount` and `freeRoundsRoundCount`, and **no `sourceUserId`
key at all**. Its author said in chat that it would send an explicit `null`; the code omits the
field. Both shapes have to keep resolving to `null` either way, but the matrix follows the code.

`currency`, `amount`, `freeRoundsRoundCount` and `offeringPeriod.to` are unchanged.

Both source fields are declared as `IntegerType`. Left untyped, the form hands a non-numeric string
straight through to a `?int` setter and the request dies as a `500` — which is the exact failure mode
this ticket set out to remove, reintroduced by a field it added. `sourceUserId` had it already and is
fixed in the same line.

`sourceScenarioId` is the id of the scenario entity on celesta-scenario's side. Promotion stores it
and gives it back; it never resolves it, so a scenario that is later deleted leaves the bonus pointing
at an id that no longer exists — the same weakness `source_user_id` already has with deleted
backoffice users, and the same one the epic accepts by asking for the attribution at all.

`idempotencyKey` and `sourceScenarioId` must both be declared on the form. The form sets `allow_extra_fields: true`
(`RewardOfferType.php:48`), so an undeclared field is accepted by the submit and then silently
dropped before `$form->getData()`.

Responses:

| Status | Body | When |
|---|---|---|
| **201** | `BonusOfferResponse` | the bonus was created by this call |
| 200 | `BonusOfferResponse` | the bonus already existed and this is a replay of a matching `idempotencyKey` |
| 400 | form errors, or `OfferErrorResponse` | invalid body; missing customer currency; currency mismatch; both sources sent at once |
| 403 | unchanged | |
| 404 | `OfferErrorResponse` | player unknown (Memberzone said 404), reward configuration unknown |
| **503** | `OfferErrorResponse` | **new** — Memberzone unreachable or answering badly |
| **422** | `OfferErrorResponse` | **new** — the offer condition chain refused |
| 500 | `OfferErrorResponse` | unexpected failure |

### The error body

Every failure of this endpoint answers in one shape, `OfferErrorResponse`:

```json
{
  "message": "Bonus currency EUR should be equal to customer currency USD",
  "code": "CURRENCY_MISMATCH",
  "error": "Bonus currency EUR should be equal to customer currency USD",
  "errors": ["Bonus currency EUR should be equal to customer currency USD"]
}
```

`message` and `code` are the service's declared convention — `ValidationErrorsSchema`,
`NotFoundSchema` and `UnexpectedErrorSchema` in `src/Kernel.php:45-79` all use them, and this
endpoint already referenced those schemas in its OpenAPI attributes while returning something else.
The documentation was describing a body the endpoint never produced.

### How a caller should classify a failed call

The caller records some of these against the player and treats the rest as a failure of its own run,
so the split has to be stated rather than guessed:

- `400`, `404` and `422` are about **this player**: record them.
- `500` and `503` are about **us**: do not record them against anyone.
- one exception: a `400` produced by request validation is a bug in the call, not a fact about the
  player. It is recognisable by having **no `code`**, or a `code` of `VALIDATION_CONSTRAINT`.

Both halves of that last sentence are needed. Promotion today builds validation errors through
`SymfonyComponents\Subscriber\FormResponseSubscriber`, which emits `{"message": "Validation Failed",
"errors": {...}}` with no `code` at all — this is the only Celesta PHP service that does not register
`ErrorCodeResponseSubscriber`, so it is the only one whose validation errors are codeless. The day
that is fixed, the same response starts carrying `code: VALIDATION_CONSTRAINT`, and a caller that
keyed only on the absence would silently invert. Writing both now costs the caller one clause and
removes a regression that would otherwise arrive with someone else's cleanup.

`error` and `errors` repeat the message and are **legacy**. They exist only because
celesta-backoffice's bulk action reads `json_decode(...)['error']`
(`BulkActionBundle/Handler/OfferFreeBonusHandler.php:101`) and would otherwise degrade to a generic
exception message in front of an operator. They should be dropped once that caller reads `message`;
until then, removing them is a silent downgrade of someone else's screen.

`code` is the field a caller stores. The five from
`OfferEligibilityException::CODE_TO_MESSAGE` — `OFFER_NOT_ALLOWED`, `NO_SEGMENT_DEFINED`,
`NO_SEGMENT_INTERSECTION`, `OCCURRENCE_LIMIT_REACHED`, `ALREADY_OFFERED` — plus the endpoint's own
`CUSTOMER_CURRENCY_MISSING`, `CURRENCY_MISMATCH`, `AMBIGUOUS_OFFER_SOURCE`, `PLAYER_NOT_FOUND`,
`UPSTREAM_UNAVAILABLE`, `OFFER_REFUSED`, `SERVER_ERROR`, and the five `REWARD_CONFIGURATION_*` mapped
from `InvalidRewardConfigurationException`'s numeric codes.

The codes matter more than they look: CLS-2925 writes one onto the player's activity entry, so a
rename rewrites history that is already stored. The message is free to be reworded; the code is not.

### "Player not found" stops meaning "we could not ask"

The endpoint caught `V2Exception`, `InvalidArgumentException` and `TypeError` together and answered
all three with `404 Player not found`. That was tolerable while nobody kept the answer. It stops
being tolerable here, because the scenario treats 404 as a per-player refusal and writes it to the
player's activity, where the activity ticket says a wrong row cannot be repaired.

`V2Exception` carries the upstream status in `getCode()`
(`vendor/lancasters/curl-library/src/CurlLibrary/GuzzleClient.php:141`), and a connection that never
got a response is reported as 500 (`CurlClient.php:183`). So:

| Cause | Now |
|---|---|
| Memberzone answered 404 | `404`, `PLAYER_NOT_FOUND` |
| Memberzone answered anything else, or was unreachable | `503`, `UPSTREAM_UNAVAILABLE` |
| Memberzone answered without a usable domain id (`InvalidArgumentException`) | `503`, `UPSTREAM_UNAVAILABLE` |
| `TypeError` | no longer caught here — it is a bug, and it surfaces as a real 500 |

The scenario already treats anything outside `[400, 404]` as a failure of the whole batch rather
than a refusal, so it records no activity entry and marks those players not reached on the session
step. Nothing changes on their side; the correct behaviour falls out of the correct status. Note
that their queue does **not** redeliver — the transport runs with `max_retries: 0` — so those
players simply get nothing from that trigger, which is honest rather than wrong.

This also reaches the backoffice bulk action, and improves it: a Memberzone outage stops being
reported to the operator as a player who does not exist.

The replay returns the same `BonusOfferResponse` shape as the first call, with `200` instead of the
`201` the creating call got. It is produced from the stored bonus, so `status` reflects the bonus as
it is now — a replay after the player claimed the offer returns `"claimed"`.

The status is the whole point of the distinction: without it the caller cannot tell a bonus it just
created from one that was already there, and that is the one fact only this service holds. It is
worth being precise about what it does **not** say, because the caller will be tempted to read more
into it. It does not say whether the caller's own side finished recording the first attempt. A
worker that died after writing its activity entries and before acknowledging its message sees the
same `200` as one that died before writing them, and those two need opposite handling. Only the
caller can tell them apart.

Two consequences of the key deciding, worth stating rather than discovering:

- **The rest of the body is ignored on a repeat.** A second call with the same key but a different
  `amount` or `offeringPeriod.to` gets the original bonus back, unchanged. That is what an
  idempotency key means, and the alternative — validating that the body matches — buys nothing for
  the only caller that sends a key, which rebuilds the same payload from the same job.

## Doctrine Entities

`Bonus`:

- new field `idempotencyKey` — `VARCHAR(64)`, nullable, no default
- new unique constraint `uniq_player_reward_config_idempotency_key` on
  `(player_id, reward_configuration_id, idempotency_key)`
- **not** added to `jsonSerialize()` — that array is the response body of other bonus endpoints, and
  adding a key there changes contracts this ticket does not own
- new field `sourceScenarioId` — `INT`, nullable, no default, set instead of `sourceUserId` when a
  scenario is behind the offer, and **added** to `jsonSerialize()`, unlike the key above: this one is
  a property of the bonus that the epic requires the backoffice bonus list to show

`jsonSerialize()` is not enough on its own, and assuming it was would have shipped a column nobody
could read. `GET /api/domain/{domainId}/bonuses`, the endpoint the backoffice actually calls, builds
its rows in `BonusNormalizer::normalizeBonus()` and never touches the entity's own serialiser. The
field has to be added there and to the `BonusResponse` schema beside it, or it stops at the database.

`sourceUserId` is added to that same payload, although it is not new. The normalizer never carried
either half, so exposing only the scenario would let the backoffice list name a scenario and never a
back-office user — a source column that is blank for every offer an operator made. One line, additive,
and it is what makes the pair readable. Called out here because it is a change this ticket was not
asked for.

Two nullable columns, not a polymorphic `source_type` + `source_id` pair. The polymorphic shape is the
tidier model on paper, but it means rewriting `source_user_id` in every row with a backfill and
breaking every reader of `sourceUserId` in the payload, the backoffice included, in exchange for a
generality no third source needs yet.

Only one of the two may arrive in a request; both together are refused with `AMBIGUOUS_OFFER_SOURCE`.
Silently preferring one would write an origin nobody can tell is wrong afterwards. No CHECK
constraint backs it: the endpoint is the only writer, and a constraint there would also have to be
taught about the rows that legitimately have neither.

Scoping the constraint to the triple rather than to `idempotency_key` alone means a caller reusing a key
across reward configurations or players still gets its own bonus per pair, which is what the scenario
needs: one action job, one key prefix, many players.

## Database Migrations

- Modified table: `bonus` — one migration adds `idempotency_key`, `source_scenario_id` and the
  unique index. One file, because nothing has shipped: the first version of it exists only on the
  branch, so folding the second column in costs a local re-run and leaves the ticket with a single
  schema change to review
- House style: guarded by `hasTable` / `hasColumn` / `hasIndex` so a rerun is a no-op, raw `addSql`,
  symmetric `down()` dropping the index before the column
- **The column uses `ALGORITHM=INSTANT`, the index `ALGORITHM=INPLACE, LOCK=NONE`.** A nullable
  column at the end of the table is metadata only, so forcing `INPLACE` there would rewrite every
  row of `bonus` for nothing; `INSTANT` takes no `LOCK` clause, being lock-free by definition.
  Adding a secondary index cannot be instant, but it does not rebuild the table either. The repo
  already has this exact shape at `src/Migrations/Version20260623130815.php:43` — the newest
  migration, which only adds an index, is the wrong neighbour to copy from
- Both are named explicitly rather than left to MySQL's own choice. MySQL picks the cheapest
  available anyway; naming it makes the migration fail loudly if the operation ever stops being
  cheap, instead of silently rebuilding a large table
- `source_scenario_id` is a plain nullable `INT` with no index: nothing queries by it, and the
  backoffice reads it out of the row it already fetched
- `down()` drops the column with `INPLACE` on purpose, asymmetric with `up()`: an instant drop only
  hides the column and leaves its bytes in every row, and a rollback is rare enough to pay for a
  clean rebuild
- The file has to be renamed to a timestamp newer than master's latest before merging, as the repo's
  history already does

## Acceptance Criteria

One per A cell.

- [ ] (1) `POST .../offer` with `{"currency":"EUR","amount":"50.05"}` and **no** `sourceUserId` key
      returns `201`; the created row has `source_user_id IS NULL` and `status = 'offered'`. The same
      holds when the key is sent explicitly as `null`.
- [ ] (3) The same call plus `"idempotencyKey":"job_x:1"` returns `201` and stores `idempotency_key = 'job_x:1'`.
- [ ] (4) Repeating that exact call returns **`200`**, not `201`, with the same `id`, and
      `SELECT count(*) FROM bonus WHERE player_id = 1 AND reward_configuration_id = <id>` is 1.
- [ ] (5) Repeating it after the bonus has moved to `claimed` returns `200` with the same `id` and
      `"status":"claimed"`, and still one row.
- [ ] (7) Repeating it after the reward configuration has been disabled returns `200` with the same
      `id`, not a 400.
- [ ] (8) Two concurrent calls with the same key end with one row; the winner gets `201` and the
      loser `200`, both carrying the same `id`.
- [ ] (10) The same key sent for a different reward configuration returns `201` and a second row

- [ ] (12) With a wallet whose `bonus_offer_allowed` is false, an **automatic** configuration

- [ ] (14) An automatic configuration at its occurrence limit returns `422` with

## Possible Edge Cases

- **A `deposit` offer answers `"amount": 0` while the row holds `NULL`.** `normalizeBonusOffer()`
  casts with `(float)`, and `(float) null` is `0.0`. The behaviour is correct — the epic requires the
  offer to carry no amount until a qualifying deposit claims it — but the response says zero where
  the database says unknown. Pre-existing, and not changed here: the caller reads the bonus id, not
  the amount. Worth knowing before someone reports it as a bug.

- **Replay after the reward configuration was deleted** — it never reaches the lookup.
  `RewardConfigurationValueResolver:41` throws `NotFoundHttpException` first, because
  `getRewardConfiguration()` builds its query through `createQueryBuilder()` and the
  `softdeleteable` filter is globally enabled (`config/packages/doctrine.yaml:37`). The lookup still
  compares the FK directly (`b.rewardConfiguration = :id`) rather than joining — simplest query for
  what it needs, and it keeps the soft-delete filter out of a question it does not have to answer.
  `Bonus` itself is not soft deletable, so a stored key always resolves to its row.
- **Losing a race.** Doctrine ORM 2.20 closes the EntityManager on a failed commit, so recovery goes
  through `ManagerRegistry::resetManager()` and a fresh repository. `$rewardConfiguration->getId()`
  has to be captured before the failing flush, since the entity is detached afterwards; the winner
  comes back from the new manager, so the normalizer can walk its reward configuration normally.
- **Flush listeners on the losing insert.** `BonusListener`, `BonusOfferedListener` and
  `ManualBonusOfferedTransactionalEmailEventSubscriber` all buffer in `onFlush` and drain in
  `postFlush`, which does not run when the insert fails — so the loser sends no e-mail and no push,
  which is correct. Their buffers do keep the losing entity, so the recovery path returns without
  flushing again.
- **What a scenario offer can actually be refused for.** The scenario only ever selects a `manual`
  configuration (`celesta-scenario` validates `offeringMethod` at save time), and the condition
  chain returns before running anything for `manual`. So none of the five `OfferEligibilityException`
  codes can occur on the scenario's path. Its refusals are: the configuration disabled between save
  and trigger, the player having no currency, the bonus currency not matching the player's, the
  player being unknown, and the feature flag being off. The `skip_reason` example in the activity
  ticket's fixture — *"Bonus currency EUR should be equal to customer currency USD"* — is the third
  of those, which is why the envelope of those responses matters more here than the 422.
- **`amount` cast in the response.** `normalizeBonusOffer()` casts `amount` with `(float)`, so a
  free-rounds bonus reports `0`. The replay reproduces it identically because it runs the same
  normalizer.

## Performance Considerations

No new outbound call. The replay lookup is one indexed read that only runs when an `idempotencyKey` is
present, and it short-circuits the Memberzone call the endpoint would otherwise make.

The unique index adds one entry per bonus row. `player_id` is already indexed on its own and with
`status`, so this is an additional index, not a replacement.

## Open Questions

- **The epic's "its source identifies the scenario that created it" is only one third delivered
  here.** Promotion now stores `source_scenario_id` and returns it, but the backoffice remaps the
  promotion payload field by field
  (`GatewayBundle/Normalizer/Promotion/BonusNormalizer.php:58-78`) and its whitelist carries no source
  field at all today, not even `sourceUserId`. So the key dies there, and the bonus list has no
  origin column to show it in either. Closing the criterion needs a backoffice change and a front
  change, neither in this repository.
- **Nothing caps repeat offers on a manual configuration.** `idempotencyKey` stops a *redelivery* of the
  same action job. A fresh trigger of the same scenario — a daily `cron_scheduled`, for instance —
  produces a new key, and `OccurrencesInRecurrencePeriodCondition` only runs for `automatic`
  configurations. If the product wants a per-player cap on manual configurations, it is a separate
  ticket.
- **Promotion is the only Celesta PHP service that does not register `ErrorCodeResponseSubscriber`**
  (twelve others do, with the same four lines). That is why its validation errors carry no `code`,
  and why `src/Kernel.php`'s own `ValidationErrorsSchema` documents a field the service never
  emits. Deliberately not fixed here: it would change every error response of the service, in
  endpoints this ticket does not touch, and the endpoint's own refusals already carry `code`
  because they are built by hand. Worth its own small ticket.
- **A player who asked not to receive bonus offers still gets a scenario offer.** `bonus_offer_allowed`
  is not consulted for `manual` configurations, by the backoffice bulk action today and by the
  scenario tomorrow. Extending the check was considered and dropped: the scenario is the bulk action
  under another trigger, and giving it a stricter rule than the operator's own button would be a
  behaviour change this ticket was not asked for, reaching outside the endpoint. If the product
  wants that check, it belongs to whoever owns the bulk action's rules, for both paths at once.
