# CLS-4772 — {D} [promotion] Create a gift when a promotion instance is rewarded

Sub-task: https://celesta.atlassian.net/browse/CLS-4772 · Parent: https://celesta.atlassian.net/browse/CLS-3916 · Repository: celesta-promotion

## Overview

Today a promotion instance that reaches `rewarded` only issues bonuses: every rewarding handler ends in `Standard\Handler\RewardHandler::issuePlayerBonuses()`, which turns each `Reward` of the matched tier or rule into a `Bonus`. [CLS-3916](https://celesta.atlassian.net/browse/CLS-3916) makes `gift` a promotion reward type (saved and validated by [CLS-4771](https://celesta.atlassian.net/browse/CLS-4771)); nothing creates the gift yet, and `RewardAmountCalculator::calculate()` throws on a `gift` reward, which `issuePlayerBonuses()` does not catch, so a tier holding a gift fails its whole rewarding.

This sub-task creates, on rewarding, one `claimed` `Gift` per gift reward of the matched tier or rule, in Deposit tier, First bet insurance, Instant reward and Refer a friend (to the role's recipient), copied from the gift reward configuration, attributed to the promotion configuration (`Gift::sourcePromotionId`), outside the bonus path (wallet currency and stock do not block it), idempotent per instance and reward, and sends one `gift_offered` `UserActivityJob` per gift with the `promotion` source. A player whose `bonus_offer_allowed` is false is not rewarded at all, as today. Promotions without gift rewards behave exactly as today.

## Architecture & Design

**Where the gift is created.** In the rewarding handlers, after the bonuses of the same tier or rule, in the same unit of work: the gift is persisted, never flushed on its own, and lands in the flush that marks the instance `rewarded` (`Standard\Handler\RewardHandler::updateStatusesAndCounters()`, the flush at `:114`; Refer a friend: the flush per role in `processPlayerRewardFlow()` at `:253`). So the gift and the status commit together.

- `issuePlayerBonuses()` (`Standard\Handler\RewardHandler.php:197-254`) skips gift rewards (`continue` before `RewardAmountCalculator::calculate()` at `:218`), so the calculator never sees one. `RewardAmountCalculator` is unchanged; its `default => throw` stays the guard for an unknown type. Multiplus overrides `issuePlayerBonuses()` (`Multiplus\Handler\RewardHandler.php:99`) and cannot hold a gift (CLS-4771 validation): untouched.
- A new service, `App\AppBundle\Service\PromotionGiftIssuer`, creates the gifts of a `RewardEvaluationResult` for one recipient promotion instance. The handlers call it after `issuePlayerBonuses()`. Because it runs after the bonus loop, a `V2Exception` raised there (`:239-247`) leaves no gift persisted.
- The bonus loop's early return when the player has no currency (`:207-213`) and the per-reward `BonusCurrencyNotEnabledException` (`BonusCurrencyGuard.php:36`, logged at `:234-238`) concern bonuses only: the gifts are issued after them all the same.

**What the gift holds.** A new factory method, `GiftFactory::createForPromotionReward()`, mirrors `createFromRequestModel()` (`GiftFactory.php:19-33`): `domainId` and `currency` of the gift reward configuration, `playerId` of the recipient instance, `name`, `amount` = `offerAmount` scaled to 2 (`AMOUNT_SCALE`), `rewardConfiguration`, `offeringReason` = the configuration's reason (`RewardConfiguration::getOfferingReason()`, from CLS-4743) or none, `sourcePromotionId` = the promotion configuration id (`Gift::setSourcePromotionId()`, from [CLS-4770](https://celesta.atlassian.net/browse/CLS-4770)), `idempotencyKey`, status the entity default `claimed` (`Gift.php:55`). No `description`, `sourceUserId` or `sourceScenarioId`. The reason is loaded with `RewardOfferingReasonRepository::getReasonIncludingDeleted()` (CLS-4743), so a soft-deleted reason is still copied and its name readable. The gift is a copy: editing the configuration later does not touch it.

**Skips.** For each gift reward, `PromotionGiftIssuer` reloads the configuration with `RewardConfigurationRepository::getRewardConfiguration(domainId, id)`, which applies the `softdeleteable` filter (`config/packages/doctrine.yaml:35-37`): a soft-deleted configuration comes back `null` without the `EntityNotFoundException` its lazy proxy would throw. `Reward::$rewardConfiguration` is `onDelete: SET NULL` (`Reward.php:45`), so a hard-deleted one is `null` already. Both are skipped with reason `reward_configuration_deleted`; a configuration whose status is not `RewardConfigurationConstants::STATUS_ENABLED` is skipped with reason `reward_configuration_disabled`. A skip is a `warning` log only (reward id, reward configuration id, promotion instance id, player id, reason); the other rewards go out and the instance is still `rewarded`. The offering status is never checked: gift configurations are always `active`. The stock is never checked: `GiftRepository::saveWithinStock()` (`:46-66`) is not used, and the gift still counts in `countByRewardConfiguration()`.

**Idempotency.** Key `promotion:<promotion instance id>:reward:<reward id>`, stored in `Gift::$idempotencyKey` (`VARCHAR(64)`), under `uniq_player_idempotency_key (player_id, idempotency_key)` (`Gift.php:30`). Before creating a gift the issuer looks it up with `GiftRepository::findOneByIdempotencyKey(playerId, key)` and skips silently when it exists; within one call it also skips a key it already issued, because Instant reward lists aggregator rewards twice (`InstantReward\Handler\RewardHandler.php:70-82` adds them, then every reward of the configuration again). Rewarding runs under the promotion-configuration lock (`acquireConfigLock()`, `:256-286`), so two workers never race on one key; the unique index is the backstop. Re-engagement creates a new instance (`reengagePlayer()`, `:168-178`), hence a new key: the next rewarded instance gets its own gift.

- Deposit tier redelivery is already stopped by `isDepositAlreadyRewarded()`; the key covers the rest.
- Refer a friend flushes the referrer's role before the referee's (`:252-253`) and swallows the referee's failure (`:152`). The next event replays both roles; the referrer's key, built on the referrer's instance, already exists, so no second gift.

**`bonus_offer_allowed = false`.** Unchanged. The reward validator `Validator\Reward\BonusOfferAllowedValidator` throws `BonusOfferNotAllowedException` before the handler runs (`:27`, `validators.yml:130-140`, all types but Refer a friend), and Refer a friend leaves the role `engaged` without reaching `offerRewards()` (`processPlayerRewardFlow()`, `:241-246`, flag read at `:121` and `:134`). Since gifts are issued only where bonuses are, the flag blocks the gift exactly as it blocks the bonuses: no special handling.

**Activity.** A new Doctrine subscriber, `App\AppBundle\EventListener\Job\PromotionGiftActivitySubscriber`, extends `JobLibrary\EventListener\AbstractCRUDJobEmittingSubscriber` like `GiftEventSubscriber`: on every inserted `Gift` with a `sourcePromotionId` it builds one `UserActivityJob`, dispatched through `Celesta\MessengerHelperBundle\PostResponseMessageDispatcher` after the flush (in the worker, on `WorkerMessageHandledEvent`). Only insertions emit; manual and scenario gifts (no `sourcePromotionId`) emit nothing here, since the backoffice sends theirs. A reprocess that creates no gift sends no activity. No `gift_claimed` exists or is sent.

| Field | Value |
|---|---|
| `event` | `UserActivityJob::EVENT_GIFT_OFFERED` (`gift_offered`) |
| `sourceType` | `UserActivityJob::SOURCE_TYPE_PROMOTION` (`promotion`, [CLS-4768](https://celesta.atlassian.net/browse/CLS-4768)) |
| `sourceUserId` | the promotion configuration id (`Gift::getSourcePromotionId()`) |
| `additionalData` | `player_id`, `domain_id`, `gift_id`, `reward_configuration_id`, `name`, `value` (the gift amount, string), `currency`, `reason_id`, `reason_name`, `description` (`null`) |

The keys after `domain_id` are the ones celesta-backoffice sends for a manual gift (`GatewayBundle/Manager/UserActivityJobManager::dispatchGiftOfferJob()`), so the backoffice log renders both alike; celesta-activity extracts `player_id` and `domain_id` from `additionalData` (`internal/messaging/user_activity_handler.go:158`). No `company_id` (promotion does not know it; celesta-activity treats it as optional) and no promotion instance id.

**Transport.** celesta-promotion routes no `UserActivityJob` today (`config/packages/messenger.yaml:24-27`). New transport `activity_sqs`, on the Kubernetes SQS account like `promotion_bonus_sqs` (`<<: *base_sqs_queue_config`, `queue_name` overridden), queue parameter `sqs_activity_queue: "%env(string:SQS_QUEUE_PREFIX)%activity"`, serializer `messenger_helper.serialization.serializer` as celesta-game and celesta-crm use for their `activity_sqs_kubernetes`. In every environment promotion's `SQS_QUEUE_PREFIX` is the prefix of the activity queue (`celesta-prod-1-` in prod-1, where activity reads `celesta-prod-1-activity`), so no new environment variable.
**Statistics.** `GiftEventSubscriber` already emits a `GiftEventJob` on every gift insert and status change, whatever the origin (`:32-45`): no change.

**Rewarding limits.** `updateStatusesAndCounters()` (`:97-127`) and the player promotion limits are untouched; the instance counts once, as today.

**Code this branch needs from its siblings.** `RewardConfiguration::getOfferingReason()` and `RewardOfferingReasonRepository::getReasonIncludingDeleted()` exist only on `CLS-4743` (PR #602); `Gift::setSourcePromotionId()` on `CLS-4770`; the `celesta-constants` pin with `RewardConstants::TYPE_GIFT` and the gift reward save path on `CLS-4771`. All stay unmerged until the story is accepted, so the branch merges them in, as `CLS-4744` merged `CLS-4743` (`55bc8998a`).

## Edge Cases & Error Handling

- **Wallet failure on a bonus of the same tier** (`V2Exception`, `:239-247`): no gift persisted, since the issuer runs after the bonus loop. A later run of the same rewarding creates one gift only, because of the key.
- **The same rewarding run twice** (a duplicate delivery of the same job, or a later event for the same instance): one gift, one activity. Deposit tier is also stopped by `isDepositAlreadyRewarded()`.
- **Configuration soft-deleted while the promotion is enabled:** skipped and logged, no exception; the instance is still `rewarded`. A bonus reward whose configuration is soft-deleted still fails as today when its proxy loads in `RewardOfferService` (not changed here).
- **`bonus_offer_allowed` false:** no gift and no bonus, as today: the reward validator stops the rewarding before the handler (Deposit tier, First bet insurance, Instant reward, instance left `engaged`), and Refer a friend leaves the role `engaged` without reaching `offerRewards()`. The gift follows the bonuses when the flag turns true and a later event rewards the instance.
- **Two gift rewards on the same configuration in one tier:** two keys (one per reward), two gifts.
- **Re-engagement after rewarding:** new instance, new key, a new gift on its own rewarding.
- **Deploy order:** with [CLS-4771](https://celesta.atlassian.net/browse/CLS-4771) live and this not, a tier holding a gift throws in `RewardAmountCalculator::calculate()` and its bonuses fail too; both deploy in the same group.

## Acceptance criteria

- Deposit tier, First bet insurance and Instant reward: on `rewarded`, each gift reward of the matched tier or rule (configuration X) creates one `claimed` gift for the player with X's `name`, `offerAmount`, `currency`, reason (none when X has none) and `sourcePromotionId` = the promotion configuration id. Refer a friend: the gift goes to the role's recipient (referrer or referee), one per recipient.
- Composition: only gift → 1 gift, no bonus; gift + bonus → both; two gifts in one tier → 2 gifts; only bonus → exactly today's bonuses, statuses and counters.
- Player with no wallet currency → the gift is created in the promotion currency, the bonus is skipped as today; player with only another currency → the gift is created, the bonus fails as today.
- Stock reached on X → the gift is created and counted by `countByRewardConfiguration()`.
- X disabled or deleted at rewarding → no gift, one `warning` log with the reason, the tier's bonuses issued, instance `rewarded`, no exception.
- Reprocessing after a wallet failure on a bonus of the same tier creates one gift only; Refer a friend replayed after the referee failed does not duplicate the referrer's gift.
- `bonus_offer_allowed` false → no gift and no bonus, instance (Refer a friend: the role) left `engaged`, as today.
- Editing X after rewarding does not change the gifts already created.
- `updateStatusesAndCounters()` and the player promotion limits count the instance as today.
- One `GiftEventJob` per gift insert and status change, unchanged.
- Exactly one `UserActivityJob` `gift_offered` per promotion gift, `sourceType` `promotion`, `sourceUserId` = the promotion configuration id, `additionalData` as under "Activity"; none for manual or scenario gifts; no `gift_claimed`.
