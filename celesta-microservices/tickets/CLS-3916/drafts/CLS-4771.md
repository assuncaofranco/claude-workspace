# CLS-4771 — {D} [promotion] Gift reward type in promotion rewards: validation, player route omits it

Sub-task: https://celesta.atlassian.net/browse/CLS-4771 · Parent: https://celesta.atlassian.net/browse/CLS-3916 · Repository: celesta-promotion

## Overview

A promotion reward today is always a bonus: its `type` is one of `RewardConstants::TYPES` minus what each promotion configuration type allows (`PromotionConfigurationBundle/*/Form/Type/RewardType.php::getAllowedTypes()`), and `RewardSubscriber` rejects any reward that points at a gift reward configuration ("A gift reward configuration cannot be a promotion reward.").

This makes `gift` a reward type of Deposit tier, First bet insurance, Refer a friend and Instant reward (not Multiplus), saved through the same `POST`/`PATCH` reward routes, directly and inside reward aggregators. A gift reward names one enabled gift reward configuration of the promotion's domain and currency, and carries no `quantity` and no `options`. The backoffice reward routes return gift rewards like any other; the player route `GET /player/{playerId}/promotion-configurations` leaves them out, so the brand site never shows a gift reward.

Creating the gift when an instance is rewarded is CLS-4772, in this repository, deployed in the same group.

## Architecture & Design

**Save path, unchanged in shape.** `RewardController::postReward`, `patchReward` and `postRewardForAggregator`, and `RewardAggregatorController` `POST /reward-aggregators` (through each type's `RewardAggregatorType::getRewardEntryType()`), all build the per-type `RewardType`, which extends `AbstractRewardType` and attaches `RewardSubscriber` on `POST_SUBMIT` (priority 900, before validation). Every change on the save side is in the four allowed-type lists and in `RewardSubscriber`; the aggregator routes inherit it.

**Allowed types.** `getAllowedTypes()` of `DepositTier`, `FirstBetInsurance`, `ReferAFriend` and `InstantReward` `RewardType` gains `RewardConstants::TYPE_GIFT`; `Multiplus` does not, so `Assert\Choice` keeps answering 400 on `type` there. The hand-written `type` enum of the matching `Base*RewardType` OpenAPI schema gains the same value.

**`RewardSubscriber::resolveRewardSource`, gift rules.** The reward type is read from the `type` field's data (`$form->get('type')->getData()`), not from `Reward::getType()`, which is typed `string` and throws on a `POST` without `type`. On `PATCH` the `type` field is disabled and its data is the stored type. The existing flow is kept, and the gift rules slot into it:

1. Both `rewardConfigurationId` and `bonusModelId` sent → unchanged: "Only one of rewardConfigurationId or bonusModelId may be provided." on `rewardConfigurationId`. A gift reward accepts either key, as every other type does.
2. Neither field submitted (a `PATCH` that leaves them out) → unchanged early return; the stored configuration stays.
3. Source id `null` (a `POST` without an id, or a `PATCH` that sends `null`): bonus types unchanged (configuration and bonus model cleared); a gift reward → "This value should not be blank." on `rewardConfigurationId`.
4. `RewardConfigurationRepository::getRewardConfiguration(domainId, id)` returns `null` → unchanged "The selected reward configuration does not exist." on the field that carried the id. This covers another domain (the query filters `rc.domainId`) and a soft-deleted configuration (the `softdeleteable` filter is enabled in `config/packages/doctrine.yaml`).
5. Type pair:
   - bonus reward type, gift configuration → unchanged "A gift reward configuration cannot be a promotion reward.";
   - gift reward type, configuration whose type is not `RewardConfigurationConstants::TYPE_GIFT` → new "The selected reward configuration is not a gift." on the field that carried the id.
6. Gift reward only:
   - configuration status not `RewardConfigurationConstants::STATUS_ENABLED` → new "The selected reward configuration is disabled." on the field that carried the id;
   - configuration currency differs from `PromotionConfiguration::getCurrency()` → "Reward currency does not match promotion currency." on the field that carried the id (the message the existing reward currency constraints use).
7. Accepted → unchanged: `setRewardConfiguration($configuration)` and `setBonusModelId($id)`, so the stored row has the same shape as any other reward.

Every rejection returns before the configuration is set on the reward, so the class-level currency constraints on `Reward` (`DepositTierRewardCurrencyConstraint`, `FirstBetInsuranceRewardCurrencyConstraint`, `ReferrerRewardCurrencyConstraint`) see no configuration and do not add a second error.

**`quantity` and `options` on a gift reward.** In the same subscriber, after the source checks: a gift reward whose submitted `quantity` is not `null` gets "A gift reward does not take a quantity." on `quantity`; one whose submitted `options` is a non-empty array gets "A gift reward does not take options." on `options`. An empty `options` (`{}` or `[]`) is accepted. Only submitted fields are checked, so a `PATCH` that leaves them out passes. Two gift rewards in one tier or rule are two rewards, each checked on its own; nothing counts gifts per tier.

**Not added.** No offering status rule (a gift configuration has no offering period). No status rule and no new currency rule for bonus types. No change to `RewardAmountCalculator` or any `RewardHandler` (CLS-4772).

**Read side, backoffice.** The backoffice reads rewards through `GET .../promotion-configuration/{id}/rewards` (`reward_list`), `GET .../reward/{id}` (`reward_get`) and `GET .../reward-aggregators`, all serialized by `Reward::jsonSerialize()`: `id`, `type`, `bonusModelId` (= `getRewardSourceId()`, the reward configuration id when set), `quantity`, `options`. A gift reward comes out as `{id, type: "gift", bonusModelId: <gift configuration id>, quantity: null, options: {}}` with no code change. `GET /promotion-configurations` (`promotion_configuration_list`) and `GET /promotion-configuration/{id}` return no rewards at all and are not touched.

**Read side, player.** `GET /player/{playerId}/promotion-configurations` builds its `rewards` in `PromotionConfigurationService::createPlayerPromotionConfiguration` through `RewardNormalizer::normalizeRewards()`, its only caller. `normalizeRewards()` leaves gift rewards out of every group's `items`. An aggregator whose rewards are all gifts still produces its group, with `aggregatedBy` and `items: []`, so a tier with only a gift reward is returned with no rewards. The standalone group (no aggregator) is emitted only when it has at least one non-gift reward, as today it is emitted only when non-empty. `RewardNormalizer::normalize()` is unchanged.

**Potential winnings.** `PotentialWinningsCalculator::computeParcel()` returns `null` for a type it does not list (`default => null`), and `sumRealAndBonusAmounts()` skips a `null` parcel, so a gift reward adds nothing. No change.

**OpenAPI.** `Reward.type` is `enum: RewardConstants::TYPES` (`Reward.php:37`) and lists `gift` once the library carrying `RewardConstants::TYPE_GIFT` is required. The four `Base*RewardType` schemas list it by hand (task 3). `RewardDTO.type` has no enum. `public/open-api.json` is not versioned; `make openapi` regenerates it.

## Edge Cases & Error Handling

- **Deployed without CLS-4772.** `RewardAmountCalculator::calculate()` throws `InvalidArgumentException` for `gift` (`default` arm), and `Standard/Handler/RewardHandler::issuePlayerBonuses()` catches only `InvalidRewardConfigurationException`, `BonusCurrencyNotEnabledException` and `V2Exception`. Once a gift reward can be saved, rewarding any instance whose tier or rule holds one fails as a whole: the bonuses of that tier are not offered either. In Refer a friend the `catch (Exception)` of `ReferAFriend/Handler/RewardHandler::processReward()` turns it into a failed `RewardResponse`. CLS-4771 and CLS-4772 therefore deploy in the same group; if CLS-4771 goes alone, no gift reward may be saved until CLS-4772 is out.
- **Gift configuration disabled or deleted after the save.** Not a save rule; the reward stays. A soft-deleted configuration keeps the `reward_configuration_id` (`onDelete: SET NULL` acts only on a hard delete). Handling at rewarding time is CLS-4772.
- **Refer a friend referee.** Referee bonus rewards may be in another currency than the promotion (no constraint today; `bo_user_creates_reward_aggregator_raf_role.feature` asserts it). A referee gift must be in the promotion currency, like every gift reward.
- **Currency rule and the class-level constraints.** For Deposit tier, First bet insurance and Refer a friend referrer, a gift in another currency gets one error from `RewardSubscriber`, not a second from the `Reward` class constraints, because the configuration is never set on the reward.
- **`type` cannot change on `PATCH`.** The `type` field is disabled on `PATCH`, so a bonus reward cannot become a gift reward or the reverse; that stays as it is.
- **OpenAPI `Post*RewardType` requires `options`.** The schemas list `options` as required while the form never required it, for every type; a gift request without `options` is accepted. Unchanged here.
- **Multiplus with `type: gift`.** The subscriber runs before validation and may add a gift-rule error next to the `type` choice error; the response is 400 either way and the client is told on `type`.
- **Library alias.** The `as 1.369` alias is checked against the latest celesta-constants tag before review and again before release, and raised if taken.

## Acceptance criteria

- `POST`/`PATCH` of a reward with `type: gift`, directly and inside reward aggregators, is accepted for Deposit tier, First bet insurance, Refer a friend (referrer and referee) and Instant reward; Multiplus answers 400 on `type`.
- A gift reward that names an enabled gift reward configuration of the same domain and the same currency as the promotion configuration, by `rewardConfigurationId` or by `bonusModelId`, returns 200; `GET .../reward/{id}`, `GET .../rewards` and `GET .../reward-aggregators` return it with `type: gift` and the configuration id in `bonusModelId`.
- A gift reward pointing at a `free`, `deposit` or `free_rounds` configuration returns 400 on `rewardConfigurationId`.
- A bonus reward type pointing at a gift configuration returns 400 with "A gift reward configuration cannot be a promotion reward."
- A disabled gift configuration returns 400 on `rewardConfigurationId`; a soft-deleted one or one of another domain returns 400 "The selected reward configuration does not exist."
- A gift configuration in another currency than the promotion configuration returns 400 on `rewardConfigurationId`; bonus reward types gain no new currency or status rule.
- A gift reward with no configuration id, a non-null `quantity` or non-empty `options` returns 400 on that field; two gift rewards in one tier are accepted.
- `GET /player/{playerId}/promotion-configurations` returns no item of `type: gift`; a tier whose only reward is a gift is returned with `items: []`.
- `PotentialWinningsCalculator` is unchanged and ignores gift rewards.
- The OpenAPI `Reward.type` enum and the Deposit tier, First bet insurance, Refer a friend and Instant reward reward request schemas list `gift`; the Multiplus one does not.
- Every existing reward type saves and reads exactly as before.

## Decisions

- **Which key carries the gift configuration id on save?** — `rewardConfigurationId` or `bonusModelId`, as for the other types; both at once keeps today's "Only one of" error · answered by Lucas Franco, 2026-11-17
- **Deploy order with CLS-4772?** — Same deploy group · answered by Lucas Franco, 2026-11-17
- **Is the gift configuration's offering status a save rule?** — No; a gift configuration has no offering period · answered by Lucas Franco, 2026-11-17
- **A gift reward sent with `quantity` or non-empty `options`: rejected or ignored?** — Rejected with 400 on the field; the backoffice never sends them, and an explicit error keeps the stored row free of values nothing reads · answered by Lucas Franco, 2026-11-17
- **On the player route, a tier whose only reward is a gift: kept with no items, or dropped?** — Kept with `aggregatedBy` and `items: []`; the parent says such a tier "shows no reward", and the tier's thresholds stay visible · answered by Lucas Franco, 2026-11-17
- **Does the currency rule apply to a Refer a friend referee gift, though referee bonuses may be in another currency?** — Yes; every gift reward is in the promotion currency, as the parent's picker and rewarding criteria say · answered by Lucas Franco, 2026-11-17
