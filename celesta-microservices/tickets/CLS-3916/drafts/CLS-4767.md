# CLS-4767 — {A} [constants] Add the gift promotion reward type

Sub-task: https://celesta.atlassian.net/browse/CLS-4767 · Parent: https://celesta.atlassian.net/browse/CLS-3916 · Repository: celesta-constants

## Overview

`Lancaster\Constants\Promotion\RewardConstants` defines the reward types a promotion rule can carry: `future_deposit`, `free_bonus`, `free_round`, `match_deposit` and `match_bet`, all listed in `TYPES`. Gift exists only as a reward configuration type (`RewardConfigurationConstants::TYPE_GIFT = 'gift'`, CLS-3247), not as a promotion reward type.

This adds `RewardConstants::TYPE_GIFT = 'gift'` and lists it in `TYPES`, so celesta-promotion (CLS-4771) and celesta-backoffice (CLS-4774) can reference the gift reward type from the shared library instead of hardcoding the string. CLS-3916 makes gift a reward type in Deposit tier, First bet insurance, Refer a friend and Instant reward.

## Architecture & Design

- `TYPE_GIFT` is a literal `'gift'`, declared like the other `TYPE_*` constants of the class (untyped `public const`). It is not an alias of `RewardConfigurationConstants::TYPE_GIFT`: the two classes name different things (the type of a promotion reward and the type of a reward configuration) and already differ elsewhere (`free_round` / `free_rounds`, `free_bonus` / `free`).
- `TYPES` is the whole set of reward types, not the set a given promotion configuration type accepts. Which configuration types accept `gift` (all but Multiplus) is decided in each consumer: celesta-promotion's `getAllowedTypes()` in each `PromotionConfigurationBundle/*/Form/Type/RewardType.php`, and celesta-backoffice's `TypeResolver::PROMOTION_CONFIGURATION_TO_REWARD_TYPE_MAP` and `REWARD_TYPE_MAP`. No per-configuration list exists in this library and none is added.
- `self::TYPE_GIFT` is appended at the end of `TYPES`, so the position of every existing entry is unchanged.
- Readers of `RewardConstants::TYPES` on the consumers' `master`, and what adding `gift` does to each once the consumer requires this change:

  | Consumer | Reader | Effect |
  |---|---|---|
  | celesta-promotion | `src/AppBundle/Entity/Reward.php:37` `#[OA\Property(enum: RewardConstants::TYPES)]` | OpenAPI `Reward.type` enum lists `gift`. Documentation only: request validation uses the per-configuration `getAllowedTypes()` lists through `Assert\Choice` in `AbstractRewardType`, which do not reference `TYPES` |
  | celesta-backoffice | `src/GatewayBundle/Normalizer/Promotion/RewardNormalizer.php:12,24` OpenAPI enum | OpenAPI reward `type` enum lists `gift`. Documentation only |
  | celesta-backoffice | `src/GatewayBundle/Manager/ConstantManager.php` | OpenAPI (line 915) and runtime: `getConstants()` reflects every class of the library, so the constants endpoint returns `promotion.rewardConstants.typeGift = 'gift'` and `gift` in `promotion.rewardConstants.types` |
  | celesta-gateway | `src/Promotion/Transformer/RewardTransformer.php:15` OpenAPI enum | OpenAPI reward `type` enum lists `gift`. Not a sibling sub-task of CLS-3916 |

  Validation is not widened anywhere: celesta-promotion rejects `gift` through `Assert\Choice(getAllowedTypes())`, and celesta-backoffice's `TypeResolver::resolveFormType()` falls back to `DefaultType` (validation error) for a type missing from `REWARD_TYPE_MAP`.
- No Go service reads this class.

## Edge Cases & Error Handling

Once a consumer requires this change, from the branch or from the released tag, and before that consumer's own gift sub-task lands:

- **celesta-promotion.** The OpenAPI `Reward.type` enum advertises `gift`, but `POST`/`PATCH` of a reward with `type: gift` is rejected by `Assert\Choice` in every configuration type. No reward of type `gift` can therefore exist, so `RewardAmountCalculator::calculate()` (whose `match` throws `InvalidArgumentException` on an unknown type) and `PotentialWinningsCalculator::computeParcel()` (`default => null`) are never reached with `gift`. Handling `gift` in both belongs to CLS-4771 / CLS-4772.
- **celesta-backoffice.** The constants endpoint returns `promotion.rewardConstants.typeGift` and `gift` in `promotion.rewardConstants.types`. celesta-backoffice-front does not read `rewardConstants` (its promotion reward options are hardcoded), so no Gift option appears in the promotion form from this change alone. `ConstantControllerTest` only asserts `rewardConstants` is present and non-empty, so it keeps passing. A reward request with `type: gift` gets the validation error of `DefaultType` until CLS-4774 maps it.
- **celesta-gateway.** When it next requires a version of the library that includes this change, its player-facing OpenAPI enum in `RewardTransformer` lists `gift`, while the parent puts gift rewards out of `GET /promotion-configurations`. Documentation drift only; no runtime change.
- **Version alias.** Consumers require this branch as `dev-CLS-4767 as 1.369` (latest tag `v1.368`, at `0623f926`). Any other merge to `master` before this one takes `v1.369`; the alias is checked against the latest tag before review and again before release, and raised if taken.
- **Order of `TYPES`.** Appending keeps every existing index; a consumer comparing the exact list (none found on `master` of celesta-promotion or celesta-backoffice) would need updating.

## Acceptance criteria

- `RewardConstants::TYPES` is `['future_deposit', 'free_bonus', 'free_round', 'match_deposit', 'match_bet', 'gift']`.
- No other class in the library changes.
