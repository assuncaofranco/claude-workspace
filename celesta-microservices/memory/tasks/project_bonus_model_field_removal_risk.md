## Context

Wallet's `BonusModel` entity (`celesta-wallet/src/BonusBundle/Entity/BonusModel.php`) and several `BonusSubBalance`/`ArchiveSubBalance` fields (`celesta-wallet/src/SubBalanceBundle/Entity/BonusSubBalance.php`) are legacy — superseded by `RewardConfiguration`/`Bonus` in celesta-promotion (see [[project_custom_attributes_reward_configuration]] for the BonusModel→RewardConfiguration migration lineage). Plan: keep both systems live for ~3 months after the new system is stable, then delete the entity/columns from wallet. User's framing: don't worry about legacy-only code (it gets deleted with the replaced endpoints), only worry about code that (a) is genuinely part of the new promotion-integrated flow and (b) would break if a given field/entity is removed.

## Verification methodology (important — this caught 2 false alarms, and one false negative)

Before flagging any wallet code path as "will break when we remove field/entity X for promotion-origin bonuses," check:
1. **"There's a parallel promotion-side endpoint" is NOT sufficient to mark legacy code safe — check whether the legacy endpoint itself is still called unconditionally.** Originally reasoned that celesta-gateway exposing `/bonuses` (→ wallet, legacy) and `/reward/bonuses` (→ celesta-promotion, new) as separate routes made `BonusSubBalanceRepository::createBonusesQueryBuilder()`'s INNER JOIN on `bonusModel` safe to ignore. **CORRECTED 2026-08-19 (see full audit below): this was wrong.** Gateway's `/bonuses` route is NOT flag-gated and NOT going away — it always hits wallet's `BonusController::getBonusesAction`, which calls this INNER JOIN unguarded. Since the join structurally excludes any row with `bonusModel = null`, **every promotion-origin bonus is already invisible in this listing today**, in production, right now — not a future removal risk. The "legacy-only by design" test only proves the code *category* is legacy; it says nothing about whether that legacy code path is still reachable and still expected to return complete data.
2. **Is the guard condition even reachable for promotion-origin data?** `GiveBonusOnDepositListener::checkBonusValid()` looked like it wrongly rejected promotion bonuses (`bonusModel === null`) — conclusion (safe) confirmed, but the ORIGINAL mechanism cited was wrong: it's not about `getDepositOfferedBonusById()`'s `STATUS_OFFERED` filter. Re-verified 2026-08-19: `PaymentTransactionJobHandler.php:219-333` (AppBundle) wraps **all three** bonus-on-deposit resolutions (`$bonusModel`, `$bonus`, `$bonuses`) in `if (! $shouldRouteBonusToPromotion && ...)` — with the flag ON, no `BonusToClaim` is ever created, so `GiveBonusOnDepositListener` has nothing to process. Right conclusion, wrong reason in the original write-up — the flag gate lives one layer up the call chain from where it looked gated.

Do not trust a subagent's "NEEDS REVIEW"/"live bug" flag without personally tracing the actual call chain back to something that fires unconditionally in production (not gated by a status/flag/route that's legacy-exclusive) — but also do not trust a "safe" verdict without confirming the *entry point* itself is flag-gated or dead, not just that a parallel new-system route exists alongside it.

## Field classification (celesta-wallet `BonusSubBalance`/`ArchiveSubBalance`)

**Load-bearing — do NOT remove without rewriting new-system code first** (confirmed by reading `ClaimHandler.php`/`RefundHandler.php` directly: they read/write these on `POST /api/domain/{domainId}/wallet/{ownerId}/bonus-transaction`, an always-on per-player endpoint, no flag gate):
`status`, `model`, `wageringMultiplier`, `gameplayRestrictionGameIds`

**Getter called unconditionally but value is always null/unused for promotion bonuses — safe to remove, but touch the call site**:
`bonusModel` (relation), `claimedAt`, `statusSetAt`

**No confirmed new-system usage — safest to drop**:
`amountLimit`, `sourceUserId`, `freeRoundsRoundCount`, `offeringPeriodTo`, `promotionId` (BonusSubBalance's own field, distinct from BonusModel's own `promotionId`), `validityPeriodTo` (minor latent risk: `GameTransactionManager::splitFreeRounds` reads it unguarded, currently only reachable via legacy free rounds)

**Whole `BonusModel` entity**: legacy-only, deleted wholesale with `BonusModelController`/`BonusModelManager`/offer-flow condition classes/FreeRoundConfiguration subclasses — see full breakdown in conversation, not repeated here.

## Structural prerequisite (blocks ALL field removals, not field-specific)

`celesta-wallet/src/AppBundle/Command/TransferSubBalanceToArchiveCommand.php` hardcodes every one of these columns by name in raw SQL (`SELECT`/`INSERT` moving rows between `sub_balance` and `archive_sub_balance`). Dropping *any* of these columns from the tables without first updating this command's column list breaks the archive/restore cron with a SQL error. Also fix while there: the `--restore --type=bonus/cash` filter uses `bonus_model_id IS NOT NULL/IS NULL` instead of the `discr` column (which the forward archive path correctly uses) — this misses/wrongly-sweeps promotion-origin bonus rows during restore.

## Confirmed real but orthogonal to the removal decision

`SportsbookBundle/EventListener/Sensor/BonusDepositListener.php` — fires on transaction TYPE (`TYPE_BONUS_DEPOSIT` + `STATUS_SUCCESS`), not gated by status, so it DOES run for promotion-origin bonuses on ANJ-licensed domains — and skips Sensor compliance reporting when `bonusModel === null`. This is a pre-existing compliance gap that exists *today*, independent of any future field removal (removing the field doesn't newly break this — it's already silently not working for promotion bonuses). Worth flagging to compliance/product separately.

**UPDATE 2026-08-19: this one is now FIXED in current code.** `BonusDepositListener.php:86-102` now has a fallback via `PromotionService::getBonusData()` (network call to celesta-promotion when `bonusModel` is null), with logging and a safe return if Promotion doesn't respond — same pattern as `TransactionBetWagerListener`/`TransactionWinWagerListener` below. No longer an open item. Kept here for history; see the sibling gap in `BonusBetManager.php` below, which is the same regulatory data (Sensor `bonusName`) but did NOT get this fix.

**Second instance of the same pattern, found 2026-08-19 after the user asked to re-check it:** `AppBundle/EventSubscriber/WalletTransactionEventSubscriber.php:94` — `setBonusConfigurationId($bonusSubBalance?->getBonusModel()?->getId())`. Already null-safe (`?->`), so **not** a crash risk on field/entity removal — different in kind from what this investigation was hunting for. But it IS the same "silently blind for promotion bonuses today" pattern: traced the consumer chain — `WalletTransactionEventJob` → celesta-statistics `WalletEventBatchItem`/`WalletTransactionEventJobHandler` → permanent column `event_wallet_transaction.bonus_configuration_id` (KPI/reporting), and separately celesta-backoffice's player transaction view (`GatewayBundle/Normalizer/Player/TransactionNormalizer.php:85-86`, `bonusConfigurationId`/`bonusConfigurationName` sourced from `bonus_model_id`/`bonus_name`). Confirmed via grep: no `reward_configuration_id` equivalent exists anywhere in celesta-statistics. So for every promotion-origin bonus transaction, both the BI/KPI pipeline and the backoffice operator's transaction view already lose bonus-configuration attribution today, with no fallback — same class of gap as the Sensor listener, same verdict (orthogonal to removal safety, not a blocker, but worth flagging to analytics/backoffice stakeholders separately). This was missed in the original 2026-08-03 pass (never grepped for reporting/analytics consumers of `getBonusModel()` specifically) and was surfaced but not flagged as a risk in a later CRUD-mapping pass (2026-08-19) until the user explicitly asked to double-check it — lesson: when auditing a getter for "safe to remove" call sites, explicitly check every call site against the *analytics/reporting* consumer class, not just the request/response and workflow-guard classes.

## REFRAMED GOAL (2026-08-19) — this is not "will it crash," it's "will it silently stop working"

User corrected the framing of this whole investigation: the point was never just to avoid crashes on BonusModel removal. There are two categories of every `getBonusModel()` call site in celesta-wallet:
- **Category 1 — already stops running when `shouldRouteBonusToPromotion()` is ON** (flag-gated, or structurally unreachable for promotion-origin data because it filters by a `bonusModelId`/status that promotion bonuses never have). Safe — becomes dead code as the migration completes, no action needed.
- **Category 2 — keeps running regardless of the flag**, and reads something from `BonusModel` that has no equivalent yet on `BonusSubBalance`/from celesta-promotion. These are the ones that matter: once BonusModel is actually removed, whatever id/name/date they read today (already `null` for promotion-origin bonuses right now) disappears for good — silently, in whatever downstream system consumes it (KPI pipeline, Sensor/ANJ compliance report, bonus listing API, bonus consumption order). **The goal is not just "don't break," it's "keep working" — each Category 2 finding needs either the flag added, or a real fetch of the equivalent id/value from celesta-promotion's `RewardConfiguration`/`Bonus`.**

Full exhaustive audit (every `getBonusModel()` call site in celesta-wallet, ~30 sites across ~20 files) done 2026-08-19. Findings below, ranked by actual business severity (not file order):

### 🔴 P0 — already live and wrong in production today, independent of any future removal
- **`BonusSubBalanceRepository::createBonusesQueryBuilder()` (~line 1177)** does `join('b.bonusModel','bm')` — **INNER JOIN, not LEFT JOIN**. Feeds `getBonuses()`, `getFilteredBonuses()`, `getBonusesAggregate()`. Called with **no flag guard** from `BonusController::getBonusesAction`/`getBonusesAggregateAction`, which is what celesta-gateway's unconditional `/bonuses` route hits. Effect: **every promotion-origin bonus (bonusModel already null today) is entirely absent from this listing** — not a null field, the whole row is excluded by the join. This directly contradicts the original (now-corrected) verification-methodology note above. Needs: turn into LEFT JOIN + rewrite `applyBonusesFilter`'s `bm.type/model/status/displayName/currency/id` filters to fall back to `BonusSubBalance`'s own `rewardType`/`model`/`bonusId` fields when `bm` is null.

### 🟠 P1 — real business-logic correctness risk (money/gameplay), not just reporting
- **Bonus consumption order for promotion-origin bonuses may be wrong.** `BonusListener.php:61,85` only sets `claimedAt`/`validityPeriodTo` when `getBonusModel() !== null` — for promotion bonuses these stay null forever (by design, per `ClaimHandler`/`GameTransactionManager.php:325` comment "Rewards claimed through Promotion never set validityPeriodTo", and `BonusSetClaimedAtListener.php:35-38`). Two order-by-claimedAt call sites are NOT mitigated: `SubBalanceRepository::getOrderedActiveSubBalances()` (PHP `<=>` sort, null sorts as "smallest", used in `GameTransactionManager.php:96` — real bet processing) and `BonusSubBalanceRepository::getOrderedActiveBonusSubBalances()` (SQL `ORDER BY claimedAt ASC`, MySQL puts NULL first, used in `BonusBetManager::splitTransaction`). If which-bonus-gets-debited-first is decided by this ordering, promotion-origin bonuses may systematically jump the queue (or always sort last, depending on direction) versus their actual claim time. Needs product/backend confirmation of intended behavior, then either populate `claimedAt` unconditionally (it doesn't actually need `bonusModel` — only `validityPeriodTo` does) or give `BonusSubBalance` its own always-populated claimedAt-equivalent.
- **Free-round cancellation on the game gateway may not happen for promotion-native bonuses.** `BonusListener.php` onFlush CANCELED-transition branch (~lines 97-131) calls `GameClient::cancelFreeRound()` using `bonusModel->getFreeRoundConfiguration()->getGameIds()` — null-guarded (no crash) but not flag-gated, and celesta-promotion's own `RefundHandler` (the thing that actually cancels a promotion-native bonus) does not appear to call the game gateway itself. **Unverified**: does celesta-promotion cover this cancellation on its own side? If not, a player could keep an active free round after their bonus is "canceled." Flagged as needing a cross-service check with the promotion side before closing.

### 🟡 P2 — real, silent, but reporting/compliance-only (same class as the two already-known KPI/Sensor gaps)
- **`SportsbookBundle/Manager/BonusBetManager.php:35`** — sensor `bonusName` sent on every sportsbook bet made with a bonus; reads `bonusModel?->getName()`, no fallback. Null for every promotion-origin bonus bet, unconditionally. Same regulatory data class as `BonusDepositListener.php`, which already got the `PromotionService::getBonusData()` fallback — this sibling did not. Straightforward fix: apply the same pattern.
- **`AppBundle/Entity/Transaction.php` `jsonSerialize()` (~line 611-613)** — `bonus_name`/`bonus_model_id` in the transaction API payload (feeds `WalletTransactionEventSubscriber` and direct transaction API responses) are null for promotion-origin bonus transactions, no fallback field on the entity today.
- **`BonusBundle/Validator/Constraints/FreeRoundStartedConstraintValidator.php:24-28`** — the "can't cancel a free round already started at the provider" check is silently skipped entirely for promotion-origin bonuses (early-returns on `bonusModel === null`). Not flag-gated; runs on `patchBonusAction` form validation.

### 🟠 P1 — RECLASSIFIED 2026-08-19 (was wrongly filed as P3, see below): reachable today via a manual ops command
- **`AppBundle/Manager/BonusManager::isFreeRoundsCancelable()` (line 41-44)** returns `true` ("cancelable") unconditionally whenever `bonusModel === null`, without checking whether the bonus is actually a free-rounds type with a round `STARTED` at the game provider. Originally filed as P3 ("no live caller reaches this for promotion bonuses") — **that was wrong.** Cross-checking CLS-1068's own Wallet inventory (which lists `bonus:cancel` as one of Wallet's cron/ops commands) led to actually reading it: `AppBundle/Command/CancelBonusCommand.php` (`bonus:cancel`, a manual CLI run by ops/support with `--bonus_id --owner_id --domain_id`, **no flag gate at all**) calls `$this->bonusManager->isFreeRoundsCancelable($bonus)` directly on whatever `BonusSubBalance` id is passed, then sets `STATUS_CANCELED` if the check says yes. If an operator runs this against a promotion-origin free-rounds bonus with an active round at the provider, the wallet marks it canceled while the round may still be running there — a real player-facing inconsistency, not just a latent trap. Needs: mirror the fix pattern already used elsewhere (network fallback to `PromotionService`/celesta-promotion equivalent, or reject/require explicit confirmation for bonuses with no `bonusModel`) before this command is used against promotion-origin bonuses.
- **Lesson reinforced**: `transaction:adjust-bonus-balance` (`AdjustBonusBalanceCommand`), the other Wallet command in CLS-1068's inventory, was also checked and does NOT touch `BonusModel` at all — confirmed irrelevant to this specific risk category, correctly excluded.

### 🟢 P3 — currently unreached (no live caller hits the fragile branch), but a trap for the next person who adds a caller
- `BonusSubBalanceRepository::compareBonusesBy` order-by-`offerPeriodFrom` — null-safe, but the null-handling branch (`return -1` whenever either side is null) is not a stable comparator, causing inconsistent sort order whenever promotion bonuses are mixed into a list sorted by this field.
- `BonusSubBalanceRepository::getSubBalanceAttribute` groupBy key — minor, key loses a numeric prefix (`"_123"` vs `"45_123"`) for promotion bonuses; still unique, low impact.

### Full Category-1 (confirmed safe, no action) list
`BonusOfferedListener`, `RewardTypeResolver`, `ManualBonusOfferedTransactionalEmailEventSubscriber`, `ManualBonusOfferedListener`, `GiveBonusOnDepositListener`+`BonusModelManager::claimBonus` (via `PaymentTransactionJobHandler` flag gate, corrected mechanism above), `PaymentTransactionJobHandler:253-254`, `TransactionWinWinningsListener` (reference-correct pattern: `?->getModel() ?? $bonusBalance->getModel()`), `TransactionBetWagerListener`/`TransactionWinWagerListener` (reference-correct pattern: network fallback to `PromotionService::getBonusData()`), `BonusDepositListener` (now fixed, see above), `OccurrencesInRecurrencePeriodCondition`, `BonusModelDeletionListener`, `ExpireBonusOfferCommand`, `ExpireBonusValidityCommand`, `RefreshBonusModelStateCommand`, `BonusModelSetOfferingStatusListener`, `BonusSubBalanceRepository::getBonus()` singular (real LEFT JOIN, correctly used by `patchBonusAction`), `BonusController::bonusesClaimAction` ids-branch, `unionBonuses` (dead code, no caller).

## Methodology correction (2026-08-19, user-driven): "doesn't crash" ≠ "safe"

User pushed back hard on the "Category 1 = flag-gated or early-return = safe" framing: the actual bar is not "avoids a 500" — it's "the functionality keeps working, somewhere, for promotion-origin bonuses" (either wallet does it correctly using the flag/a promotion lookup, or celesta-promotion has genuinely taken over the behavior). A validator that silently skips its check is not "safe," it's a silently-missing feature, UNLESS the equivalent check demonstrably exists elsewhere for the bonuses that now route around it. This reopened two items that had been marked safe on weaker grounds (early-return / flag-gate alone, without confirming a real substitute):

- **`FreeRoundStartedConstraintValidator` (wallet) — RE-CONFIRMED SAFE, but for the right reason now.** celesta-promotion has its own independent equivalent: `App\AppBundle\Service\RewardBonusManager::isFreeRoundsCancelable(Bonus $bonus)` (`src/AppBundle/Service/RewardBonusManager.php:27-62`) — checks `rewardConfiguration->getType() !== TYPE_FREE_ROUNDS` (return true), else queries `GameClient::getFreeRounds()` for `STATUS_STARTED` rounds, same caching pattern (`FREE_ROUNDS_CANCELABLE_FOR_BONUS_ID_%s`, TTL 3600s) as wallet's version. Wired into `ApiBundle/Form/Type/RewardBonusType.php:30` via `new FreeRoundStartedConstraint()`, validated on `PATCH .../reward/bonus/{bonusId}` (`RewardController::updateRewardBonusStatus`) — the actual endpoint promotion-origin bonus cancellations go through. The check isn't skipped, it moved.
- **P1 "free-round cancellation at the game gateway may not be covered for promotion-native bonuses" — RESOLVED, CONFIRMED SAFE.** celesta-promotion's own `AppBundle/EventListener/ORM/BonusListener::cancelFreeRound()` (`:170-204`) calls `$this->gameClient->cancelFreeRound($rewardConfiguration->getDomainId(), $gameId, $bonus->getId())` directly (Promotion's own GameClient, own `Bonus`/`RewardConfiguration`), triggered on the same CANCELED-transition detection as wallet's version, with its own error handling/logging (catches `V2Exception`, logs, does not block the cancel). Promotion does not rely on wallet's `BonusListener` for this at all for its own bonuses — genuinely independent, verified implementation. **Remove from the open-risk list.**
- **Also directly re-verified (not just recalled from an earlier subagent report) while re-checking the above**: `BonusOfferedListener` and `ManualBonusOfferedTransactionalEmailEventSubscriber` both exist in celesta-promotion (`src/AppBundle/EventListener/Job/`), structurally mirroring wallet's versions field-for-field, same `NotificationJob`/`TransactionalEmailJob` types, gated by the same flag in the opposite direction — the code comment literally says "a defensive guard mirroring the equivalent check on Wallet's side." Genuine parity, confirmed by direct read, not assumed from a docblock claim.

**Standing rule going forward**: before marking anything "Category 1 / safe" in this investigation, the bar is finding the actual substitute implementation in celesta-promotion (file + method), not just confirming wallet's side doesn't error. "It's flag-gated" or "it returns early" only tells you wallet stopped doing it — it does not tell you whether anyone else picked it up. Items in the existing Category-1 tables that were classified this way *without* a confirmed promotion-side substitute (e.g. `BonusModelDeletionListener` cascade-cancel → `RewardConfigurationDeletionListener` refund parity, `GiveBonusOnDepositListener` → `DepositRewardClaimService::claimOnDeposit`, the three Expire commands → their promotion-side namesakes) were checked by a thorough subagent earlier in this investigation with specific file/line citations, but not re-verified by direct read in *this* pass — treat them as high-confidence, not yet at the same verification bar as the four items above.

**Applied this same bar (2026-08-19) to the original `WalletTransactionEventSubscriber`/KPI finding — it holds up, genuinely unresolved, NOT a false alarm.** Searched explicitly for a substitute the way the free-round items had one: `grep -rln "JobLibrary\\Job\\Statistics" celesta-promotion/src` → zero hits (celesta-promotion emits nothing to celesta-statistics, directly or otherwise). `grep -rln "promotion" -i celesta-statistics/src` → zero hits (celesta-statistics has no awareness celesta-promotion exists — no ETL, no replica, no cross-service join). So unlike the free-round cases, there is confirmed NO parity here: `bonus_configuration_id` in `event_wallet_transaction` has no substitute anywhere for promotion-origin bonuses. Partial mitigating detail: the same job's `bonus_id` field (`WalletTransactionEventSubscriber.php:93`, `getBonusId()`) IS populated for promotion-origin bonuses — but celesta-statistics has no mechanism to resolve that id back to a `reward_configuration`, so the raw id is present but practically unusable for aggregation/reporting by campaign. On the backoffice side (`TransactionNormalizer.php:85-86`), the gap is softer: an operator can still see bonus attribution via the separate `/reward/bonuses` (promotion) listing screen — it just isn't joined into the same transaction-history view, a completeness/UX gap rather than the KPI pipeline's total data loss.

## User challenged 3 of the 5 "real problems" as moot given target architecture (2026-08-19) — verified, 2 of 3 still stand

User proposed: (1) `GET /bonuses` in wallet "doesn't make sense anymore," listing will be controlled by Promotion, so the P0 INNER JOIN bug doesn't matter; (2) `claimedAt` should be set in Promotion and sent to Wallet — asked whether I'd verified this; (3) bonus cancel is no longer done in wallet, Promotion does it and sends a request to apply to the sub-balance. Asked: if correct, is the KPI/transaction finding (P2 #5) the only one still real? **Verified each directly — answer is no, 2 of 3 still stand:**

1. **`GET /bonuses` (P0) — claim REFUTED, endpoint is very much alive.** Found `celesta-gateway/_specs/CLS-2205.md` ("Fix OOM in GET /bonuses"), dated from a production incident on **2026-08-10** — 9 days before this conversation. A player with ≥6,200 bonus records crashed the endpoint with a 64MB OOM. The fix (streaming response + paginating the outbound Wallet call) is real, recent engineering investment *in keeping this exact wallet-backed path alive and performant*. The ticket explicitly puts "Any change to celesta-wallet" and "`App\Promotion`'s bonus controller" as **out of scope**, deferring wallet-side improvement to "a separate ticket against that service" — not eliminating the path. This is strong, dated evidence the team's actual near-term plan is to keep Wallet's `/bonuses` as the live source of truth, not retire it in favor of Promotion. It also independently touches the *exact* method our P0 finding is about (`BonusSubBalanceRepository::getAllBonuses()`) for an unrelated (OOM) reason, without noticing the INNER-JOIN completeness bug — meaning the team was recently in this code and still didn't catch it. **P0 stands, arguably strengthened.**
2. **`claimedAt` sent from Promotion to Wallet (P1) — claim describes the RIGHT fix, but it isn't built yet.** Verified directly: wallet's `ApiBundle/Model/Request/Claim.php` DTO has no `claimedAt` field at all (only action, bonusId, currency, amount, model, gameplayRestrictionGameIds, wageringMultiplier, rewardType). `ClaimHandler::applyClaim()` (`BonusBundle/BonusTransaction/Handler/ClaimHandler.php:74-84`) does not set it. celesta-promotion's `BonusListener::postWalletBonusTransaction()` (`AppBundle/EventListener/ORM/BonusListener.php:236-263`, the method that actually calls `WalletClient::postBonusTransaction()` on claim) sends `action/bonusId/currency/amount/model/rewardType/gameplayRestrictionGameIds/wageringMultiplier` — **no `claimedAt`**. ## CLS-1068 — the ticket this all traces back to (does NOT cover this audit's scope)

User asked (2026-08-19) whether https://celesta.atlassian.net/browse/CLS-1068 covers the Category-2/P0-P3 findings above. Read the full ticket text: **it does not, by design.** CLS-1068 ("Feature flag to start using promotion endpoints db instead of wallet db") is scoped entirely to the *routing layer* — which service Gateway/Backoffice call for each bonus HTTP operation (list/offer/claim/cancel/model-CRUD). Its own "Out of scope" section explicitly excludes "Removing/retiring the bonus code in Wallet" and "Migrating the monetary ledger... out of Wallet into Promotion." The ticket's "Wallet MS — source being vacated" section (controllers, crons, ORM-listener stack, emitted events) is investigative inventory of what Wallet currently does — not a to-do list for this ticket. **Confirmed via code (all 4 services' `FeatureFlagService.php` docblocks cite CLS-1068 by number):** this ticket IS the origin of the single global flag `move_bonus_to_promotion` used everywhere in this investigation. ## MAJOR FINDING (2026-08-03) — celesta-promotion's automated reward engine still runs entirely on wallet's BonusModel

This overturns the earlier framing that `BonusModelController`/`BonusModel` (wallet) is purely legacy scaffolding being fully replaced. It is not — it is the **live, sole mechanism** by which celesta-promotion's automated reward-configuration engine grants bonuses today.

- `App\AppBundle\Entity\Reward` (celesta-promotion, `celesta-promotion/src/AppBundle/Entity/Reward.php`) has exactly one way to reference a bonus: `bonusModelId` (`#[ORM\Column(name: 'bonus_model_id', ...)]`). No `rewardConfigurationId`/`bonusId` alternative field exists on this entity — this is not a partial migration, it is the only mechanism.
- All 5 concrete reward-type handlers (`PromotionConfigurationBundle/{FirstBetInsurance,Multiplus,InstantReward,DepositTier,ReferAFriend}/Handler/RewardHandler.php`) extend `AppBundle/PromotionConfiguration/Standard/Handler/RewardHandler` and all call (directly or via the inherited `issuePlayerBonuses()`) `WalletClient::postOfferBonusModel()` → wallet's legacy `POST /api/domain/{domainId}/bonus-model/{bonusModelId}/owner/{ownerId}/offer` (`BonusModelController`). Confirmed by reading each handler's `processReward()`/`processPlayerRewardFlow()`.
- Reward-configuration *validation* in backoffice also depends on it: `FirstBetInsuranceRewardCurrencyConstraintValidator`/`ReferrerRewardCurrencyConstraintValidator`/`DepositTierRewardCurrencyConstraintValidator`/`MultiplusRewardCurrencyConstraintValidator` are Symfony constraints attached directly to the `Reward` entity; they call `WalletService::getCachedBonusModel()` → wallet's `GET /bonus-model/{id}` to check currency/domain match, catching `V2Exception` as a validation failure. If wallet's `BonusModelController` is deactivated, saving/editing a Reward of these 4 types in backoffice fails validation outright.

**Practical implication:** deactivating wallet's `BonusModelController`/`BonusModel` entity without first migrating `Reward.bonusModelId` (celesta-promotion) to reference `RewardConfiguration` instead breaks: (1) real-time bonus issuance for all 5 reward types (silently — `V2Exception` is caught and only logged), and (2) all backoffice create/edit of Reward configs for FirstBetInsurance/Multiplus/DepositTier/Referrer types (loud — validation error). This is the highest-severity finding in this whole investigation; the wallet-side field/entity removal plan should not proceed until this dependency is migrated.

**Separately confirmed still-new-system** (uses wallet's *new* `POST /bonus-transaction` `BonusTransactionController`, not `BonusModel`): `celesta-promotion/src/AppBundle/EventListener/ORM/BonusListener.php` (`postWalletBonusTransaction()`, fires on insert/update of celesta-promotion's own `Bonus` entity), `celesta-promotion/src/AppBundle/Service/BonusService.php` (refund), `celesta-promotion/src/AppBundle/EventListener/ORM/RewardConfiguration/RewardConfigurationDeletionListener.php` (refund on deletion). Not yet traced: what actually creates a `Bonus` (celesta-promotion) row in the first place, if not the `Reward`/`RewardHandler` chain — needs follow-up to understand whether these two mechanisms are fully separate reward-granting paths or whether one feeds the other.
