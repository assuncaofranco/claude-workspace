# CLS-3316 reward offering reasons

**Feature:** configurations, manual and bulk offers, promotion rewards and scenario bonus actions carry a `reasonId`; deleted and other-brand reasons behave as decided in the plans.

## Setup
- First local run 2026-11-17 (see the notes below for what it changed). Run only after the coordination releases the backoffice and promotion stacks, with promotion #602 (CLS-4743), backoffice #3336 (CLS-4745) and scenario #319 (CLS-5130) deployed on the target.
- `python3 -I gen.py` regenerates the collection; `./run.sh` runs it once, whole, then step 9 (`ENV=pp1 ./run.sh` runs the collection only). Credentials come from the vault at run time. Newman 6 or later, `jq`.
- Step 9 is local only: the promotion container (`PROMOTION_CONTAINER`, default `promotion.php`) must be up from the branch with CLS-4743 and CLS-4744.
- Steps 10-12 (scenario runtime door) are local only: the scenario container (`SCENARIO_CONTAINER`, default `scenario.php`) must be up from the CLS-5130 branch, with segment, promotion, crm, backoffice, the shared MySQL and local SQS up. One stack per service on the machine.
- Order matters: captured ids do not survive between Newman runs, so never run a folder alone.

## Steps
1. Folder 1: BO token, another brand, reasons A, B, Y, Z, W, V (live) and X (created, deleted); the list shows A and B, not X; a reason of another brand.
2. Folder 2: configs with `reasonId` A plus legacy `reason`, none, legacy only; refused: unknown, deleted, other brand, 0; read; legacy filter still finds them; edit to B, without the key, echoed as the front sends it, null, back to A; gift; deposit; free rounds.
3. Folder 3: config with Y, Y deleted; read, edit keeping Y, edit without `reasonId`, edit to X refused.
4. Folder 4: manual offers (B over A, none, null, Y deleted-own); refused (unknown, X, other brand, -1); bonuses read back; config edited after the offers, bonuses keep theirs.
5. Folder 5: three bulk CSV runs, config with A, with none, with Z deleted; each bonus has the config's reason.
6. Folders 6a-6c: three instant_reward promotions (A, none, W deleted); player opts in; bonuses have the config's reason.
7. Folder 7: scenario saves with A, null, none; refused: unknown, other brand, deleted X, 0; scenario holding V keeps it after V is deleted, switching to X refused; graph edit to B.
8. Folder 8: scenarios deleted.
9. Folder 9: enable the legacy-only config, offer one bonus on it and one on `rcNone`, read back that they have no reason.
10. Folder 10 (DEV-ONLY): reason U; a static segment holding the test player; three configs (`rcR1` reason A, `rcR2` reason A, `rcR3` none); three enabled scenarios, cron every minute, segment condition, bonus action: `scR1` node reason B, `scR2` node without reason, `scR3` node reason U, then U is deleted and `scR3`'s graph is saved again keeping U.
11. `run.sh`, between the two Newman runs: `scenario:trigger:cron-scheduled-event <domain>`, then `messenger:consume scenario_event_sqs scenario_action_sqs --time-limit=45`.
12. Folder 11 (DEV-ONLY, second Newman run): `rcR1` has one bonus with reason B; `rcR2` one bonus with no reason; `rcR3` one bonus with reason U and its name; the three scenarios are deleted.
13. `run.sh`, after both Newman runs: `reward-offering-reason:migrate-legacy` with the cutoff set to now (UTC): dry run (output says nothing written, database unchanged), real run (exit 0), second real run (`Bonuses updated: 0.`).
14. `run.sh`, read-only SELECTs: configs with a legacy key and no `reasonId` (and their bonuses) got the `goodwill` reason; the gift config stayed without; every reason already set stayed.

## Notes
- PO-runnable: the collection (folders 1-9, BO and gateway only); ids are found through the API. DEV-ONLY, not PO-runnable: folders 10-11 with their console command and queue consumer (steps 10-12), and step 9 (console command and database reads). On pp1 `run.sh` skips folders 10-11: the scenario cron jobs and workers run there on their own, and a `* * * * *` scenario would offer a bonus every minute.
- Step 9 writes through the command only, never by SQL; every SELECT is one line. The command is brand-wide: it also backfills every other legacy config and bonus of the domain that exists in the local database, so run it on a throwaway stack. The cutoff is taken after Newman ends, so all bonuses of the run are inside it: `bM2` and `bM2b` (offered without a reason on `rcA`) end with rcA's reason (CLS-4744 Q4: until the cutoff nobody chose "none"), while bonuses that already had a reason keep it.
- Scenario runtime door (steps 10-12): the trigger is the real console command, nothing is written to a database. It is the trigger with the fewest services: a `cron_scheduled` event has no players, so the audience comes from a segment condition on a static segment that holds the test player, and no event has to arrive on SQS from segment, crm or wallet (`enter_segment`, `withdrawal_request` and the others would). Services up: scenario (php, the command and a consumer of its queues), segment (creates the segment and holds the player), promotion (the offer; it asks crm for the player's currency), crm, backoffice, shared MySQL and local SQS. Not needed: wallet, game, gateway, Elasticsearch (dynamic segments only; confirm on the first run).
- The command fires every enabled scenario of the domain whose cron is due, not only ours: the fixtures have `* * * * *`, so their actions run too. Use a throwaway stack. Our scenarios are deleted right after the check, so nothing keeps firing.
- Cells: S1 the node's reason wins over the configuration's (B over A); S2 a node without a reason gives a bonus without one although the configuration has A; S3 a scenario that holds U, deleted after the save, still offers with U (promotion accepts a deleted reason of the domain on a scenario offer, CLS-4743) and the bonus keeps U with its name. Step 14's backfill runs after folder 11, so S2's bonus is checked before the command gives it A (CLS-4744 Q4).
- The first run confirms: whether the command handles the cron event in its own process (CLAUDE.md says so; the consumer also listens to the event queue in case it does not), the segment create body (`type: static`, empty `segmentCriterias`), and that the three configs are accepted as scenario targets (enabled, manual, same currency).
- Source of every cell: the parent's acceptance criteria, then the plans' Decisions and `sdd.md`. The criterion a decision changes is named in that request's description (`CRITERION CHANGED`):
  - offer with the configuration's OWN deleted reason: the AC rejects deleted reasons on an offer, CLS-4743 accepts this one (200, bonus stores it);
  - scenario save with a deleted reason: accepted only when the stored scenario already holds it (CLS-5130), a new scenario with it is refused;
  - legacy `reason` still forwarded and returned next to `reasonId` (CLS-4745 Q2, removal is CLS-4748), and the legacy filter still finds new configs.
- Not covered, and why:
  - automatic (segmentation) and deposit claims: out of the four doors asked; CLS-4743 Behat covers them;
  - CLS-4744 beyond one brand: the seed only for the keys used, a reason with another name on a config is not spread (Q8), the lock and `--batch-size`; the BigQuery name (CLS-4747) is the ETL's;
  - a configuration whose stored legacy key is outside the 31 (needs a row written to the database);
  - reasons list for users with a single permission (needs BO users with isolated grants).
- Assumptions to confirm on the first run: `dbal:run-sql` prints the `RESULT=` value; BO paths are `bonus_configuration`, `reward_configuration/gift`, `bulk_action` and `scenario` as in the backoffice code, not the `reward-configuration` paths in `postman-reference.md`; the instant_reward opt-in rewards at once; the BO reasons list hides deleted reasons; scenario create returns `nodes[].options`.
- Bonuses are never cancelled and configs never disabled: ids carry the `runTag`, and the player gets about 12 test bonuses per run.
- First local run, what it corrected (2026-11-17):
  - Newman does not export captured variables with `--export-collection`: the collection mirrors them to the globals after each request and `run.sh` reads `--export-globals`.
  - The BO user needs `ROLE_OAUTH2_PS_REWARD_OFFERING_REASON_UPDATE`, granted by migration `Version20261102000000`, which `make init` does not run: execute that one migration in the BO container on a fresh stack.
  - Promotion's PUT replaces the whole configuration: without `status` the configuration comes back disabled, so every PUT in the collection sends `status: enabled`.
  - A new scenario is inactive (`isActive` false) and the cron command skips it: folder 10 activates the three scenarios with `PATCH scenario/settings/{id}`.
  - Nothing consumes the BO bulk-action queue locally: `run.sh` runs `messenger:consume backoffice_bulk_action_sqs` during the first Newman run.
  - The scenario queues also hold stale messages and the fixture scenarios' actions: `run.sh` drains in rounds of 45 s until both queues are empty.
  - Fixture scenarios 14, 15 and 16 have an `enter_segment` node with no segment filter: the append of the test player to our static segment fires them, and scenario 15 LOCKS the player (status `locked`, reason `kyc_not_provided`). The bonuses of the run are not affected, but the next run's manual offers (folder 4) fail with "Player is not eligible ... status locked". Folder 4 now starts with an idempotent preparation: `PREP GET player status` reads it and `PREP DELETE status_stack` runs only when it is `locked` (`DELETE` answers 403 on a player that is not locked, so it cannot run unconditionally), so a re-run does not depend on this note. By hand: `DELETE /api/gateway/domain/1/player/1/status_stack` with body `{"message": "unlock"}` (status goes back to `lead`).
  - The deposit configuration needs `claimingEventCondition` with `depositAmountMin` and `depositAmountMax`; the domains list takes no `status` filter; the legacy-reason search takes `status` (one value) and is narrowed by `search` with the run tag, because the 100-row page fills up over runs; reason names are limited to 64 characters.
  - Local stack: segment needs its nginx container, an image with PHP 8.5, vendor from its lock file and its migrations run; the gateway player token goes through celesta-auth (`authweb.docker`), which needs the `oauth2_refresh_token` table.
