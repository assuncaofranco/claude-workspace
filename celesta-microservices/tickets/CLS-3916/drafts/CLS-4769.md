# CLS-4769 — {B} [activity] Accept the promotion activity source type

Sub-task: https://celesta.atlassian.net/browse/CLS-4769 · Parent: https://celesta.atlassian.net/browse/CLS-3916 · Repository: celesta-activity

## Overview

celesta-activity stores each consumed `UserActivity` message in the `user_activity` collection. `UserActivityHandler.handleBuffer` copies the message's `SourceType` and `SourceUserID` onto the stored `model.UserActivity` as received: ingestion checks no source type (the `SourceTypes` list in `celesta-go-helper`'s `messenger/message/user_activity.go` is commented out). On the read side, `constants.AllSourceTypes` is the allow-list the `user_activity_source_types_field` rule checks `filter[sourceTypes]` against, on `GET /api/user-activities` and `POST /api/user-activities/aggregate`; today it holds `player`, `system`, `application`, `company`, `user`, `seon`, `scenario` and `fraud`.

[CLS-3916](https://celesta.atlassian.net/browse/CLS-3916) has promotions create gifts on rewarding, with exactly one `gift_offered` activity per gift, attributed to the promotion. celesta-promotion ([CLS-4772](https://celesta.atlassian.net/browse/CLS-4772)) sends it with the new source type `promotion` ([CLS-4768](https://celesta.atlassian.net/browse/CLS-4768), `UserActivityJob::SOURCE_TYPE_PROMOTION`) and the promotion configuration id as `source_user_id`. `gift_offered` is already a safe, filterable event here ([CLS-4033](https://celesta.atlassian.net/browse/CLS-4033)). Such a message would already be stored with its payload; what fails is the filter, which rejects `filter[sourceTypes]=promotion` with a 400. This sub-task makes `promotion` a filterable source type.

## Architecture & Design

- **Who sends it.** celesta-promotion, through `UserActivityJob` on the message bus: event `gift_offered`, `source_type` `promotion`, `source_user_id` the promotion configuration id, and `player_id` and `domain_id` in `additional_data`, which `UserActivityHandler` already extracts into the stored document.
- **Who reads it.** The back office's `POST /api/gateway/logs`, which passes `sourceTypes`, `sourceIds` and `event` through to this service: the player Logs (a player id and an event list) and the BO Logs filters ([CLS-4775](https://celesta.atlassian.net/browse/CLS-4775)). This service's `AllSourceTypes` is its only check on the source type.
- **Filter only.** The change is the allow-list entry and the two enum lists; ingestion, the whitelist, the repository's `setMatch(f, "source_type", …)` and `source_user_id` handling are untouched. `gift_offered` stays in `AllEvents` and `SafeEvents` as CLS-4033 left it.
- **`source_user_id` is not namespaced.** A promotion configuration id and a Backoffice user id can be equal; selecting one promotion's entries means sending `sourceIds` together with `sourceTypes=promotion`, as the scenario execution log does with `scenario`.
- **Payload not validated.** The `additional_data` keys are CLS-4772's to decide. The fixtures and tests use illustrative keys and assert pass-through, not a shape.
- **Where each test bites.** Fixtures are written to Mongo directly and never pass through ingestion, so storing is covered by the messaging test and filtering by the API cases over the fixtures. The messaging subtest passes on master too, since ingestion accepts any source type; it pins that behaviour. The `promotion` filter cases are the ones that fail without this change.
- **No new code path.** The pattern of `fraud` ([CLS-2582](https://celesta.atlassian.net/browse/CLS-2582), commit `c5fef2a7`): a constant, an `AllSourceTypes` entry, the `filter[sourceTypes]` enum, the `Items Enum:` comment, fixtures and tests.
- `public/assets/swagger.json` is git-ignored and generated at build; it is not committed.

## Edge Cases & Error Handling

- **Deploy window.** A promotion `gift_offered` that arrives before this deploy is stored with `source_type` `promotion` and its payload, because ingestion checks no source type and the event is already safe; it only cannot be filtered by source type until this ships. No row is lost and none needs repair.
- **Same id, two sources.** `source_user_id` `7301` can be a promotion configuration and a Backoffice user at once; `sourceIds` without `sourceTypes` returns both, as it does today for scenario and user ids.
- **Unknown source types.** Still rejected by `user_activity_source_types_field`; `AllSourceTypes` gains only `SourceTypePromotion` (task 10).
- **Missing or null values.** `reason_id` `null` (a gift configuration with no reason) is stored as sent.
- **`player_id` and `domain_id`.** Extracted from `additional_data` by the existing coercion in `UserActivityHandler`; one player per gift, so one document per message.
- **Other source types for `gift_offered`.** The Backoffice-sourced (`user`) entries are unchanged and still returned by `sourceTypes=user`.
- **Storage move in flight.** [CLS-3804](https://celesta.atlassian.net/browse/CLS-3804) (PR #515) moves storage to MySQL, with fixtures under `database/fixtures/`. Whichever of the two merges second moves the two fixtures of task 5 to where the other left them; its `source_type` column is `VARCHAR(64)`, so `promotion` needs no schema change.

## Acceptance criteria

- A `gift_offered` message with `source_type: promotion` and a promotion configuration id as `source_user_id` is stored as one document with that source type and id, and `additional_data` identical to what was sent.
- `GET /api/user-activities?filter[sourceTypes][]=promotion` returns 200 and the promotion-sourced entries; adding `filter[sourceIds][]=<configuration id>` returns that promotion's entries only.
- `GET /api/user-activities?filter[event][]=gift_offered&filter[playerIds][]=<player id>` — the player Logs' event filter — returns the player's promotion-sourced entry.
- `POST /api/user-activities/aggregate` with `filter.sourceTypes: ["promotion"]` returns 200 and their count.
- `GET /api/user-activities?filter[sourceTypes][]=<unknown>` returns 400.
- `promotion` is in the `filter[sourceTypes]` enum of the generated OpenAPI document.
