Learned while working [[project_cel9206_vibrez_rds_resize]], but none of this is specific to Vibrez or to that ticket — applies to any RDS instance-class change in a Terraform repo with `db_blue_green_update_enabled = true`.

**Check Performance Insights compatibility before proposing/attempting a downsize to a small/micro burstable class.** `db.t4g.small`, `db.t4g.micro` (and the `t3` equivalents) do not support Performance Insights — AWS rejects the change with `InvalidParameterCombination`, but only once you actually try to apply it, not at plan time. If the target instance currently has `performance_insights_enabled = true`, that's a real trade-off to raise with whoever owns the ticket *before* attempting the apply, not something to discover mid-deployment.

**A failed mid-flight Blue/Green update leaves orphaned AWS resources that Terraform won't clean up or resume on retry.** `db_blue_green_update_enabled = true` isn't a tracked Terraform resource — it's ephemeral orchestration inside the provider's update logic for that one `apply` call. If that call errors out (e.g. an incompatible target config), the Blue/Green Deployment object and its Green replica are left behind in AWS. Consequences:
- **Retrying `apply` won't resume it** — Terraform has no memory of the stray deployment, and AWS only allows one active Blue/Green Deployment per source instance, so a naive retry fails again with a *different* error ("deployment already exists").
- **Clean it up manually first**, regardless of which way the ticket's decision goes: `aws rds delete-blue-green-deployment --blue-green-deployment-identifier <id> --delete-target`.
- **The Green target usually inherits `deletion_protection = true`** from the same module config as the source — `--delete-target` fails until you separately `aws rds modify-db-instance --db-instance-identifier <green-id> --no-deletion-protection --apply-immediately` on the **Green** instance specifically. Never touch the real source instance's deletion protection to work around this.
- **A failure "updating Green environment" happens before switchover** — the real (Blue/source) instance is untouched. Confirm directly with `aws rds describe-db-instances` on the source id rather than assuming from the Terraform error text alone.

**`-target=<module or resource address>` is the right way to scope both `plan` and `apply` in a repo where apply is manual and infrequent** (see [[reference_vibrez_terraform_docker]] — no CI here). Without it, an apply run days or weeks after several unrelated PRs merged to master would sweep in all of that pending drift at once, not just the one change the ticket is about.

**A second, different failure mode hit the same CEL-9206 trial** (2026-09-10, after the Performance Insights fix): the Green replica's replication broke *after* the second reboot (the one applying the actual `instance_class` resize), not during the config-apply step. CloudWatch's `/aws/rds/instance/<green-id>/error` log showed the sequence clearly — first reboot (disabling Performance Insights) recovered replication fine, but the second reboot (the resize itself) left the Green unable to recover: `Error looking for file after .../relaylog.NNNNNN`, then a wall of `MY-013124: Replica failed to initialize applier metadata structure from the repository` repeating every ~60s, never self-healing. Terraform's own `apply` eventually surfaced this itself (no need to force-kill it) as `SwitchoverBlueGreenDeployment ... DB instance ... is not in available state`, after ~44 minutes. Same cleanup recipe applied again (disable deletion protection on Green, `delete-blue-green-deployment --delete-target`). **Root cause found (2026-09-10, confirmed against AWS docs — not a one-off):** AWS's own [Blue/Green best practices for MySQL](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/blue-green-deployments-best-practices.html) say `innodb_flush_log_at_trx_commit = 2` is only ever meant to be *temporary* on a green environment, must be reverted to `1` before switchover, and — verbatim — *"If an unexpected shutdown or crash occurs with the temporary parameter value, rebuild the green environment to avoid undetected data corruption."* In `vibrez-prod` that parameter is **permanent** (plus `sync_binlog = 100`), added by CEL-9081 on 2026-08-21, and the Green inherits the blue's parameter group. The full chain: Blue is Multi-AZ → AWS creates the Green as Multi-AZ too (documented behaviour) → Terraform changes `instance_class` *after* the Green is built → that triggers a Multi-AZ failover **on the Green** → MySQL sees an unexpected halt → with non-durable flush settings the replication applier metadata doesn't survive → `MY-013124`, Green unrecoverable. Independently corroborated by HackerRank's writeup of the identical error, *"caused due to an unexpected server halt that was triggered by Multi-AZ failover on the green instance"*.

This also explains why Blue/Green **worked** on this same instance on 2026-04-24 (the current prod instance is that deployment's green — its `InstanceCreateTime` is 2 minutes after that green's log stream starts): CEL-9081's tuning didn't exist yet, so the parameter group still had durable defaults and the same failover was survivable.

**So: any Blue/Green on a database whose parameter group permanently carries non-durable flush settings is expected to break the moment anything restarts the green.** Either use a direct resize (no green, no replication to lose), or follow AWS's recipe — set `innodb_flush_log_at_trx_commit=1`/`sync_binlog=1` before, restore after.

**Diagnostic habit worth keeping:** read CloudWatch `/aws/rds/instance/<green-id>/error` early when something looks stuck. Neither the Terraform CLI's "Still modifying..." counter nor the console's status column explains *why*. Note the log group survives the instance's deletion, but honours its own retention (30 days) — the April greens' log groups still exist with zero retrievable events, though their stream metadata (first/last event timestamps) is still enough to date past attempts.

**A resize that hangs for hours with no error events is probably AWS lacking capacity for the target instance class in that AZ.** Confirmed on 2026-09-11 (CEL-9206): a console `ModifyDBInstance` to `db.t4g.small` at 09:02 UTC did its Multi-AZ failover at 09:07 and then sat in `modifying` for six hours with zero events, `PendingModifiedValues` unchanged, and Enhanced Monitoring still reporting 3.75 GiB (i.e. the machine that took over was the *old* standby, still a `medium` — AWS switches over first, then needs the new hardware). It completed on its own at 15:01, five minutes after a `CreateNetworkInterface` by the `SLRManagement` service-linked role appeared in CloudTrail, which is capacity finally showing up. AWS confirmed afterwards that they simply did not have the instance available.

What this means operationally: there is nothing to do from our side, no way to cancel (RDS has no cancel-modification API, and the instance refuses any other modification while `modifying`), and the database keeps serving normally throughout. `eu-west-3` is a small region and `t4g` a popular family, so capacity stalls are more likely there than in eu-west-1. Don't burn half a day diagnosing config: if the request was accepted, the failover happened, and events go silent, suspect capacity and wait.

**A commit message claiming a revert removed something is not proof that it did.** Verify with `git show <hash> -- <file>` before trusting it — see the CEL-9177 incomplete revert in [[project_cel9206_vibrez_rds_resize]] for a real example of this exact gap.
