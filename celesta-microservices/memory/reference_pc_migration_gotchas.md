Found while auditing the old machine for [[project-pc-migration-2026]]:

- `~/.ssh/config` has two Host blocks with a path bug: `bastion-celesta-preprod` and `bastion-celesta-staging` both reference `IdentityFile ~/.ssh/<name>.pem`, but keys actually live in `~/SSH/<name>.pem` (capital, a separate folder). `bastion-celesta-preprod.pem` exists there so just needs the path corrected; `bastion-celesta-staging.pem` was searched for everywhere on the old machine (`~/.ssh`, `~/SSH`, `~/2ssh`, loose home root, Downloads, Desktop, Documents) and does not exist anywhere — it was likely never saved to disk. User declined to fix the config during the audit ("por enquanto não") — ask again rather than silently fixing.
- `~/SSH` (capital, not `~/.ssh`) is the real key store (37 `.pem` files), created 2025-02-20 following a colleague's (Virgile) on-call handover notes, not an arbitrary choice. `~/2ssh/` and a couple of loose `.pem` files directly in `$HOME` are stale earlier attempts — safe to leave behind, not carried over.
- Claude Desktop + Claude Code CLI both have an MCP server called "senior-architect" configured (`~/.claude_desktop_config.json` and top-level `mcpServers` in `~/.claude.json`) pointing at `/home/lucas/Desktop/personal-projects/mcp-celesta/venv/bin/python3`. That project folder is code, so it was intentionally NOT included in the migration bundle — it needs to be brought/recloned separately and its venv recreated, and the hardcoded path fixed if the username/home differs on the new machine.
- Deliberately excluded from the migration folder (too sensitive to bundle without an explicit ask): `~/Documents/Chrome Passwords.csv` (full plaintext Chrome password export), `~/Documents/1Password/1Password Emergency Kit *.pdf`, `~/Documents/1Password/1PasswordExport-*` (full vault export). If needed on the new machine, copy manually.

**Update 2026-08-11 (checked on the new machine, /Users/l.franco, macOS):** Restore actually happened on 2026-08-10 — `~/.ssh`, `~/SSH` (37 pem files, matches source count), `~/.aws`, `~/.kube`, `~/.config/k9s`, and `~/.claude/` (CLAUDE.md/RTK.md/settings.json/hooks/commands/memory) were all copied and verified present. Hooks path in settings.json already correctly rewritten to `/Users/l.franco` (was `/home/lucas` on old machine — old machine was Linux, new one is macOS, different username too: lucas → l.franco).
- **AWS MFA session expires independently of the migration** — `celesta-global-mfa` profile (session token from the `aws-mfa` flow) goes `ExpiredToken` after its TTL, and `celesta-preprod-1`/`celesta-staging-1`/`celesta-prod-1`/etc. all assume-role off it. Every EKS context in `~/.kube/config` execs `aws eks get-token` via one of those chained profiles, so kubectl/Lens/k9s all fail cluster auth once the MFA session dies — looks like "kube config missing" but the file and contexts are fine (`celesta-global`/`celesta-global-long-term` static keys still work). Fix is always the same: user re-runs their `aws-mfa` login (needs their MFA device) — not something fixable by editing files.
- `~/.zshrc` / shell aliases were **never captured in the original audit** — the migration `dotfiles/` folder only ever had `.gitconfig`, `.npmrc`, `.gitignore_global`, `.git-credentials`, `hosts-custom.txt`. This is a gap in the source audit, not a restore bug. Confirmed on new machine: no `.zshrc`/`.bashrc`/`.aliases` exist anywhere, only a bare `.zprofile` (Homebrew + JetBrains Toolbox PATH). Needs manual pickup from the old machine while still accessible.
- `bastion-celesta-staging` ssh config entry still points at the wrong folder (`~/.ssh/` instead of `~/SSH/`) on the new machine too, and the key file itself is still nowhere to be found (pre-existing gap, unchanged from old machine — not new breakage).
- `mcp-celesta` project + the "senior-architect" MCP server entry are **not present at all** on the new machine (`~/.claude.json` has no such entry, `~/Desktop/personal-projects/mcp-celesta` doesn't exist) — this was flagged as needing separate reclone but hasn't been done yet.

**Update 2026-08-11 part 2 — resolved/clarified:**
- Installed `aws-mfa` (broamski's pip tool) via `pipx install aws-mfa`, since Homebrew's Python blocks bare `pip install` (PEP 668 externally-managed-environment) — `brew install pipx && pipx ensurepath && pipx install aws-mfa` is the working recipe. `pipx ensurepath` also created a fresh `~/.zshrc` (new machine had none) with just the PATH export — this is now the right file to append the user's restored aliases into once fetched from the old machine.
- The exact refresh command, verified against the installed package's source (`awsmfa/__init__.py` suffix logic), not guessed: `aws-mfa --profile celesta-global --short-term-suffix mfa`. This reads the long-term keys from `celesta-global-long-term` (default `-long-term` suffix) and writes the session into `celesta-global-mfa` (the profile every `celesta-preprod-1`/`staging-1`/`prod-1`/etc. profile assumes-role from). Device ARN is picked up automatically from `aws_mfa_device` already set on `celesta-global-long-term`. Prompts interactively for the Google Authenticator code — user has to run it themselves.
- Removed `diversos/home-root/.claude_desktop_config.json` (mcp-celesta MCP config) from the local `migracao-pc-novo` folder at user's request — genuinely personal, confirmed by user.
- **Correction — `diversos/documents-aws/AWS` is NOT personal**, despite loosely mixing in a "Quanta" account: Quanta (954607206481) is the OLD *work* AWS account (no k8s), lrgi-global (851725549872, behind `celesta-global`/`celesta-global-mfa`) is the NEW *work* account (has k8s) — repos are being migrated between them gradually. See [[reference-infra-repos]] for the account mapping. Do not treat "Quanta" as personal again — left that file untouched.
