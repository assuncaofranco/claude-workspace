# CLS-4756 — {B} [backoffice] Expose every combined request ID on transaction report lines

Sub-task: https://celesta.atlassian.net/browse/CLS-4756 · Parent: https://celesta.atlassian.net/browse/CLS-1214 · Repository: celesta-backoffice

## Overview

The Finance transaction report is `POST /api/gateway/domain/{domainId}/finance/transaction_reports`
(`TransactionReportController::getTransactionReportsAction()`). It reads the lines from statistics
`GET /api/bi/transaction_movement` through `StatisticsClient::getTransactionMovements()` and maps each one in
`TransactionReportNormalizer::normalize()`, which serves the single `withdrawRequestId` from the statistics key
`withdraw_request_id`. A combined payout pays several withdraw requests, and the report line shows only one of them.

Statistics ([CLS-4754](https://celesta.atlassian.net/browse/CLS-4754)) adds `withdraw_request_ids` to every element of
`GET /api/bi/transaction_movement`. It holds the stored list on a combined payout, otherwise
`[withdraw_request_id]` when that is not null, otherwise `null`. The rule applies to every movement type, so a
`withdraw_request` movement returns `[its own id]`. This sub-task serves that value as `withdrawRequestIds` on each
report line, next to `withdrawRequestId`, and documents it in OpenAPI. `withdrawRequestId` is unchanged; its removal is
[CLS-4758](https://celesta.atlassian.net/browse/CLS-4758).

## Architecture & Design

**Pass-through.** `normalize()` adds `'withdrawRequestIds' => $transactionReportData['withdraw_request_ids'] ?? null`
right after `withdrawRequestId`. The value is served exactly as statistics returns it: no derivation from
`withdraw_request_id`, no check on the movement type, no re-ordering. Statistics validates the list when it writes it
(CLS-4754). A response without the key returns `null`, which covers the deploy window before CLS-4754 and a statistics
rollback. The `?? null` read mirrors `fee` and `mid` in the same method.

Example: three report lines, as served:

    { "type": "withdraw", "withdrawRequestId": 4290150, "withdrawRequestIds": [4290150, 4292746, 4301966], ... }
    { "type": "withdraw", "withdrawRequestId": 4332503, "withdrawRequestIds": [4332503], ... }
    { "type": "deposit",  "withdrawRequestId": null,    "withdrawRequestIds": null, ... }

**OpenAPI.** `TransactionReportResponse` gains `withdrawRequestIds` right after `withdrawRequestId`: `type: 'array'`,
items `integer`, `nullable: true`, example `[4290150, 4292746, 4301966]`. The property mirrors `rewards` in
`TransactionReportRewarding`, the existing integer-list property in this file.

**Test fixture.** `MockCurlClientRequestsTrait::$statisticsTransactionMovementsData` gains
`"withdraw_request_ids":null` after `"withdraw_request_id":null`, so the shared statistics mock carries every key
statistics serves. The response without the key is tested in `TransactionReportNormalizerTest`, whose
`transactionMovement()` helper does not carry it.

**Precedents, and choices without one.**

| Choice | Existing reference |
|---|---|
| Optional statistics key read with `?? null` | `fee`, `mid` in `TransactionReportNormalizer::normalize()` |
| Integer-list property in OpenAPI | `rewards` in `TransactionReportRewarding` |
| Statistics value served unchanged | every other key in `normalize()` apart from `internalId` and `wageringPercent` |
| A list field served next to its single-value field with the same lead ID | **No precedent** in this response; it lasts until CLS-4758 removes `withdrawRequestId` |

Not changed: the request side (`normalizeRequest()`, `FilterType`, `QueryType`), the count, PSP and MID endpoints,
`StatisticsClient`, the rewarding lookup.

## Edge Cases & Error Handling

- **Statistics before CLS-4754, or rolled back**: the key is absent and the line serves `withdrawRequestIds` `null`,
  with `withdrawRequestId` unchanged. The report keeps working and there is no derivation from `withdrawRequestId`.
- **Line with no request** (deposit, refund, adjustment, initial balance): statistics returns `null` and the line
  serves `null`.
- **Single payout, or a payout synced before CLS-4754**: statistics returns `[withdraw_request_id]`, and it is served
  as is.
- **`withdraw_request` movements**: excluded by statistics' default `notTypes`. When a caller asks for that type
  through `filter.types`, the line serves statistics' `[its own id]` unchanged; there is no special case here.
- **Order and content of the list**: served as statistics returns it (ascending, validated on write by CLS-4754).
- **Size**: at most about 60 IDs per line (payment's `VARCHAR(512)`), on a page of at most `limit` lines; nothing to
  bound here.

## Dependencies

- Depends on [CLS-4754](https://celesta.atlassian.net/browse/CLS-4754) (statistics): it serves `withdraw_request_ids`
  on `GET /api/bi/transaction_movement`. There is no code dependency: deployed first, this serves `null` until
  statistics ships.
- Blocks [CLS-4757](https://celesta.atlassian.net/browse/CLS-4757) (backoffice-front): it shows `withdrawRequestIds`
  on the report payout lines and must handle `null`.
- Related to [CLS-4753](https://celesta.atlassian.net/browse/CLS-4753) (payment),
  [CLS-4755](https://celesta.atlassian.net/browse/CLS-4755) (wallet) and
  [CLS-4758](https://celesta.atlassian.net/browse/CLS-4758) (backoffice, removes `withdrawRequestId` from the lines).
- Deploy order of the story: payment, statistics, wallet, backoffice, front.

## Out of Scope

- Removing `withdrawRequestId`: [CLS-4758](https://celesta.atlassian.net/browse/CLS-4758).
- Filtering or searching the report by request ID.
- The withdrawal request screens (showing the other requests of a payout is out of the parent's scope).

## Decisions

- **What does a line with no request return?** `withdrawRequestIds: null`, passed through from statistics. Decided by Lucas.
- **What happens when the statistics response has no `withdraw_request_ids` key (deploy window or rollback)?** Read
  `withdraw_request_ids ?? null`, with no derivation from `withdrawRequestId`. Decided by Lucas.
- **Does this change Proteus or the statistics mock in celesta-qaa-proteus?** No. The controller and normalizer tests
  cover the pass-through. Decided by Lucas.
