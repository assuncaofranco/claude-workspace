# CLS-5130 — {C} [scenario] Accept an optional reasonId on the bonus action and forward it to promotion

Sub-task: https://celesta.atlassian.net/browse/CLS-5130 · Parent: https://celesta.atlassian.net/browse/CLS-3316 · Repository: celesta-scenario

## Overview

Today a bonus `offer_reward` action node carries `rewardType`, `rewardConfigurationId`, `amount`, `freeRoundsRoundCount` and `description` (`OfferBonusOptionsType`, `allow_extra_fields: false`), and `OfferRewardBonusActionJobHandler` posts `amount`, `freeRoundsRoundCount`, `currency`, `sourceScenarioId` and `idempotencyKey` to promotion's `POST /api/domain/{domainId}/player/{playerId}/reward-configuration/{id}/offer` through `PromotionClient::offerReward()`. A node sent with `reasonId` is rejected as an extra field.

[CLS-4743](https://celesta.atlassian.net/browse/CLS-4743) (celesta-promotion PR #602) gives bonuses their own reason: on an offer with `sourceScenarioId`, promotion stores the request's `reasonId`, or no reason when the request has none, never the configuration's. On such an offer it accepts any reason of the domain, deleted ones included, and refuses an unknown or other-brand reason with a 400 validation error at `reasonId`.

This sub-task gives the bonus node an optional `reasonId`, as the gift node has since [CLS-4781](https://celesta.atlassian.net/browse/CLS-4781). Scenario validates the `reasonId` of both the bonus and the gift node against the brand's reward offering reasons when the scenario is saved, as it already validates `rewardConfigurationId`, sends it on each bonus offer only when the node has one, and keeps turning promotion's refusal of an unknown or other-brand reason into a skipped offer, as the gift node does.

## Architecture & Design

**Node options.** `OfferBonusOptionsType` gains `reasonId`: `IntegerType`, `'required' => false`, `Assert\Positive` and a new `CustomAssert\RewardOfferingReason`. `reasonId: null` and an absent `reasonId` are both valid, and neither is stored: the SUBMIT listener, where the options are reduced to the form's fields, drops the `reasonId` key when its value is null, so a missing key and a null are one stored shape. A boolean becomes `UNTRANSFORMABLE_VALUE` like the other scalar fields. `rewardType` is unchanged, so `ActionNodeSubscriber::resolveOfferRewardFormType()` still picks the bonus form.

**Gift node.** `OfferGiftOptionsType` gets the same `CustomAssert\RewardOfferingReason` on its `reasonId`, after `Assert\Positive`, so a gift node follows the same rules as a bonus node. Its `reasonId` stays optional, `null` stays accepted and, as on the bonus node, a null is not stored.

**Why a null is not stored.** `ScenarioController::putScenarioGraphAction` keeps the stored node rows (ids, and the runs in progress on them) only when the submitted graph snapshot (`Scenario::getGraphSnapshot()`, the nodes' `jsonSerialize()` without position) equals the stored one. A bonus node saved before this deploy has no `reasonId` key; if every submit stored `reasonId: null`, the first save after the deploy of any scenario with a bonus node, even one that only moves a node, would differ, rebuild the nodes and orphan the runs in progress. With the key dropped when null, an unchanged node compares equal. The job handlers already treat a missing key and a null alike: they send `reasonId` only when it is a positive integer. The snapshot comparison itself is not changed.

Gift nodes saved after CLS-4781 may already hold `reasonId: null`, and they are not rewritten. A submit of such a node now drops the key, so the snapshot differs once: the first graph save of a scenario holding one rebuilds its nodes, and the nodes saved by that save no longer carry the null, so later saves compare equal.

**Validation at save.** `RewardOfferingReasonValidator` follows `RewardConfigurationValidator`: the guards of `docs/rules/code/validators.md`, a non-positive value left to `Positive`, the scenario taken from the form root, nothing checked when the scenario has no domain. It then reads the reasons of the scenario domain from promotion's `GET /api/domain/{domainId}/reward-offering-reasons`, which lists every reason of the domain with its `deletedAt`, deleted ones included. Promotion has no endpoint that reads one reason, and the list is per domain, so a reason of another brand is absent from it like an unknown one.

- not in the list (unknown or another brand): violation `This value is not a valid reward offering reason.`;
- in the list with a `deletedAt`: accepted when the stored scenario already holds that reason on one of its `offer_reward` nodes, otherwise violation `This reward offering reason is deleted.`;
- in the list without a `deletedAt`: accepted.

A graph save rebuilds every node (`NodeDataMapper::mapFormsToData()` creates a new node from the submitted data, and `putScenarioGraphAction()` keeps the stored rows only when nothing but positions changed), so a node has no identity across saves and "the action's own reason" is read at scenario level: the `reasonId` values of the scenario's `offer_reward` nodes as stored in the database, read with a new `NodeRepository::getOfferRewardReasonIds()`. The submit has replaced the nodes in memory but nothing is flushed yet, so the query returns the stored options. A scenario being created has no id and holds no reason.

The list is read once per domain and the stored reasons once per scenario, each cached in the validator for the request, as `CurrentDomainTagValidator` caches its lookups. The stored reasons are read only when a submitted reason is deleted.

Cost: one extra promotion call per save that has at least one bonus or gift node with a `reasonId`, whatever the number of such nodes; one extra database query on top of it only when one of those reasons is deleted. Saves with no reason make no extra call. A promotion failure propagates as the `V2Exception` and nothing is saved, as a failure of the configuration lookup does today.

**Request body.** `OfferRewardBonusActionJobHandler` adds `reasonId` to the data passed to `PromotionClient::offerReward()` only when the node has a positive one, as `OfferRewardGiftActionJobHandler::getGiftData()` does. A node without a reason, including every node saved before this change, sends no `reasonId`, and promotion stores no reason on the bonus even when its configuration has one. `getOfferData()` keeps its shape, because `getRewardConfiguration()` and the offered activity entry read it.

**Reason refusals.** A reason deleted after the node was saved is still accepted on a bonus offer, which gets it: there is no refusal to handle for that case. The handling below stays for the reasons promotion still refuses, an unknown or other-brand one (a node edited outside the API, or data out of step between the two services). Promotion answers a reason it does not find for the domain with `400 {"message": "Validation Failed", "errors": {"reasonId": ["This reason does not exist."]}}` and no `code` (`FormResponseSubscriber`). Today the bonus handler rethrows every code-less 400 as a rejected request. The gift handler's `isNodeReferenceRefusal()` moves into `PromotionOfferTrait` as `isValidationErrorOnlyAt(V2Exception $e, array $paths): bool` and the skip rule into the same trait as `isSkippedOffer(V2Exception $e, array $nodeReferencePaths): bool`, so both handlers share it: `isValidationErrorOnlyAt` is true when the status is 400 and the body's `errors` is a non-empty array with no key outside `$paths`. The gift handler calls it with its `['rewardConfigurationId', 'reasonId']`, unchanged in behaviour; the bonus handler calls it with `['reasonId']`. Such a refusal is a skipped offer: one `reward_offer_skipped` entry per player, with promotion's message as the skip reason and a null skip code. A 400 with errors at other paths, alone or with `reasonId`, stays a rejected request and is rethrown.

**Offered activity entry.** Unchanged: `reason` stays the configuration's legacy `reason` key read before the offer.

## Edge Cases & Error Handling

- **Bonus nodes saved before this change** have no `reasonId` in their options: no reason is sent and their bonuses have none, until a BO user saves the node with one.
- **First graph save of an existing bonus node after the deploy**: its options gain no `reasonId` key, so the graph still equals the stored one and the node rows, with their ids and the runs in progress on them, are kept when only positions change.
- **Gift nodes already holding `reasonId: null`** (saved after CLS-4781): the first graph save of a scenario holding one rebuilds its nodes once, because the submitted node has no `reasonId` key; later saves compare equal. Comparing with null keys dropped would fix it but touches the shared snapshot comparison, which this change does not change.
- **Reason deleted after the node was saved**: the next save of that scenario accepts it, and promotion accepts it on each offer, so the bonuses created afterwards still get it.
- **Reason promotion does not find for the domain at offer time** (a node edited outside the API, or data out of step between the two services): each player of the job is skipped with promotion's message.
- **Deleted reason the scenario holds on another node**, bonus or gift: accepted on any bonus node of that scenario.
- **Scenario created with a deleted reason**, including a copy of a scenario that holds one: rejected.
- **Brand with no reasons**: every `reasonId` is rejected; a node without a reason saves.
- **Promotion unreachable while the reasons are read**: the `V2Exception` propagates, nothing is saved.
- **Reason refusal together with a validation error at another path**: rethrown, as a rejected request.
- **Deploy order**: either order is safe. Before promotion's CLS-4743, promotion's offer form drops `reasonId` as an extra field and the bonus is created without a reason; before this change, scenario sends none. The reasons list already exists on promotion's master.
- **Replay of a job**: unchanged; the idempotency key `<scenarioId>:<jobId>:<playerId>` makes promotion answer with the original bonus, without checking the reason again.

## Acceptance criteria

- A bonus `offer_reward` node saves with `reasonId` set to a non-deleted reason of the scenario domain, with `reasonId: null` or without it; the stored options carry `reasonId` when it is a positive id and no `reasonId` key otherwise.
- A bonus node with an unknown reason, a reason of another domain, or a deleted reason the stored scenario does not hold is rejected with a 400 at `nodes.<position>.options.reasonId`, and nothing is saved.
- A graph save keeping a deleted reason that the stored scenario holds succeeds.
- A non-positive, non-integer or boolean `reasonId` is rejected with a 400.
- For each player of a bonus job, scenario posts `reasonId` only when the node has one.
- A 400 from promotion with errors only at `reasonId` gives one `reward_offer_skipped` entry per player with promotion's message and no code; other refusals are handled as today.
- A gift `offer_reward` node saves with an active `reasonId`, with `reasonId: null` or without it, stored without a `reasonId` key in the last two cases. An unknown reason, a reason of another domain, or a deleted reason the stored scenario does not hold on any of its `offer_reward` nodes is rejected with a 400 at `nodes.<position>.options.reasonId`, and nothing is saved; a deleted reason the scenario holds is accepted.
- Gift job handling is unchanged.
- `public/open-api.json` describes the bonus `reasonId` and its validation examples, and `make openapi` passes.

## Decisions

- **How is the bonus node's `reasonId` validated when the scenario is saved?** — Against promotion's `GET /reward-offering-reasons` for the scenario domain, in a constraint on the field, as `rewardConfigurationId` is validated against promotion at save: unknown or other-brand rejected, deleted rejected unless the scenario already holds it. Promotion has no single-reason read, and the list carries `deletedAt` · answered by Lucas Franco, 2026-11-16
- **What is "the action's own reason" when nodes are rebuilt on every graph save?** — Any reason the stored scenario holds on one of its `offer_reward` nodes, read from the database: a node has no identity across saves, and the specification states the rule per scenario ("scenarios using it keep it") · answered by Lucas Franco, 2026-11-16
- **One message for every refused reason, or one per cause?** — One per cause, with its own error code, as `RewardConfiguration` does: `This value is not a valid reward offering reason.` and `This reward offering reason is deleted.` · answered by Lucas Franco, 2026-11-16
- **Promotion refuses the reason at offer time: skip or rethrow?** — Skip each player with promotion's message and no code, as the gift node does; the check moves from the gift handler to `PromotionOfferTrait` so both handlers share it · answered by Lucas Franco, 2026-11-16
- **Does the gift node's `reasonId` get the same save-time validation?** — Yes: the gift node validates `reasonId` at save like the bonus node, because the parent rejects an unknown, deleted or other-brand reason on a scenario · answered by Lucas Franco, 2026-11-17 (replaces the earlier decision to keep `Positive` only)
- **Is a null `reasonId` stored on the node?** — No: a stored null makes the graph snapshot differ from nodes saved before, so the first save rebuilds the nodes and drops runs in progress; missing and null are the same to the job handlers · answered by Lucas Franco, 2026-11-17
