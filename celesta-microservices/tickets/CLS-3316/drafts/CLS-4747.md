# CLS-4747 — {B} [etl] reward_bonus reason taken from the bonus's reward offering reason

Sub-task: https://celesta.atlassian.net/browse/CLS-4747 · Parent: https://celesta.atlassian.net/browse/CLS-3316 · Repository: celesta-etl

## Overview

The `promotion_reward_bonus` job (`src/etl/triggers.py`, `cron="18 * * * *"`) runs `promotion.reward_bonus.bigquery_copy_mysql_to_global` and rebuilds BigQuery `global.reward_bonus` from scratch every hour: it walks `bonus` in fixed `id` windows, joins `reward_configuration` and `free_round_configuration`, and `get_final_query` replaces the whole table in one `TRUNCATE` + `INSERT` transaction. The column `reward_configuration_reason` is `rc.reason`, the configuration's current legacy key. Editing a configuration therefore rewrites the reason of every past bonus in BigQuery on the next run, which is the problem CLS-3316 fixes.

[CLS-4743](https://celesta.atlassian.net/browse/CLS-4743) gives each bonus its own nullable `bonus.reason_id` (`INT`), a foreign key to `reward_offering_reason(id)`; `reward_offering_reason` is soft deleted through `deleted_at` and holds a `name` of up to 64 characters. [CLS-4744](https://celesta.atlassian.net/browse/CLS-4744) seeds every legacy configuration key as a reward offering reason per brand, named exactly as the key, and backfills `bonus.reason_id` from the bonus's configuration. This sub-task makes `reward_configuration_reason` the name of the bonus's own reason, as stored and without line breaks, deleted reasons included, and empty when the bonus has no reason. The column keeps its name, position and type, so `global.reward_bonus` keeps its schema and existing readers keep working; they are told that the value is now the bonus's own reason.

## Architecture & Design

- **Source of the reason.** The outer `SELECT` reads the reason from a new `LEFT JOIN reward_offering_reason ror ON b.reason_id = ror.id`, mirroring the `LEFT JOIN free_round_configuration frc` already in the same query. The join has no condition on `ror.deleted_at`: a deleted reason keeps its row and its name, the same way the query already exports bonuses of soft-deleted configurations (`rc.deleted_at` is selected, never filtered). It has no condition on the domain either: promotion only stores a reason of the bonus's own brand (`RewardOfferingReasonResolver` looks the reason up by id and domain). `rc.reason` is no longer read by this sync, and there is no fallback to it.
- **Text written.** `REPLACE(ror.name, '\n', '')`, the form `src/etl/utils/microservices/game/game/bigquery_copy_mysql_to_global.py` uses for `g.name`. A reason name is free text from the backoffice, and the CSV load (`BigQuery.export_data_csv`, `src/etl/utils/helpers/bigquery.py`) does not set `allow_quoted_newlines`, so one name with a line break would fail the load of the whole table. Migrated reasons are named exactly as the legacy key, so a migrated bonus keeps the text it has today with no conversion.
- **Schema.** `ops/sync.py` takes the schema from the live BigQuery table (`get_table_schema_to_json`) and writes the CSV by position, so the expression replaces `rc.reason` in the same slot, between `reward_configuration_free_rounds_game_id` and `reward_configuration_status`. No column is added, renamed or retyped, and nothing changes in celesta-terraform-bi.
- **Pagination.** `bonus.reason_id` is added to the `b` CTE. The `min_id` / `max_id` window over `bonus.id` and `should_exit_loop` are unchanged; a `LEFT JOIN` cannot drop rows, so the window logic is not affected.
- **Release order.** `.github/workflows/ci.yml` `auto_deploy` deploys `master` to `staging-1`, `prod-1` and `prod-2` on merge, so merging is the deploy. The query reads `bonus.reason_id`, which exists only after CLS-4743's migration, and every bonus has an empty reason until CLS-4744's backfill has run. The story's release manifest therefore places this pull request after a manual step that verifies CLS-4743's migration and CLS-4744's backfill in all three environments, and before [CLS-4746](https://celesta.atlassian.net/browse/CLS-4746) reaches production. This is an ordering constraint only; no code in this repository depends on it.

## Edge Cases & Error Handling

- **Bonus without a reason** (`bonus.reason_id` `NULL`): the `LEFT JOIN` finds nothing and `REPLACE(NULL, ...)` is `NULL`, so the column is written exactly as a configuration without a reason is written today. This applies even when the bonus's configuration still has a legacy `reason`: there is no fallback to it.
- **Deleted reason:** joined like any other, so the bonus keeps showing its name.
- **Configuration edited after the offer:** the bonus's `reason_id` does not change, so its BigQuery reason does not change on the next run.
- **Duplicate names in a brand** (a brand's own `Compensation` next to the seeded `compensation`): each bonus shows its own reason's name as stored; the two texts stay distinct.
- **Name with a line break:** the break is removed before the CSV is written, so the load cannot fail on it.
- **Manual offers and scenario bonuses:** up to CLS-4744's cutoff, right before CLS-4746 goes live, CLS-4744's backfill gives them their configuration's reason like any other bonus, so they show it. After the cutoff, a manual offer carries the reason the user picked, or none, and a scenario bonus the scenario's own reason, or none (CLS-3316: "a scenario without a reason gives none"); a bonus with none gets an empty reason, where today it would show the configuration's key.
- **Legacy key with no seeded reason:** a bonus whose configuration key was not seeded or linked gets no `reason_id` and an empty reason. The pre-merge dry run reports that brand with a key it would seed and configurations or bonuses without a reason, and the merge waits until every brand shows `would seed none` and 0 without.
- **Merged before CLS-4743's migration:** MySQL rejects `b.reason_id` as an unknown column, every hourly run fails and `global.reward_bonus` stays at its last copy (the failure is in the fetch, before the truncate). The release order prevents it.
- **Merged after the migration but before the backfill:** every run rewrites the whole table, so every bonus shows an empty reason until the backfill has run, then the next run restores them. The release order prevents it.
- **Run in progress when the deploy lands:** `get_final_query` replaces the table in one `BEGIN TRANSACTION … COMMIT`, so the table is either the previous copy or the new one.
- **Cost of the join:** one primary-key lookup per bonus row in each `id` window; `reward_offering_reason` holds a few rows per brand. The 3300 s timeout is not touched.

## Decisions

- **Is `reward_configuration_reason` the reason's name as stored, or the name converted to the legacy key form (`lower`, spaces → `_`)?** The name as stored, line breaks removed: `REPLACE(ror.name, '\n', '')`. The parent specification is the source ("BigQuery has the bonus's reason name; for migrated bonuses the name equals the previous slug"), and CLS-4744 seeds the legacy reasons named exactly as the key, so migrated bonuses keep their text with no conversion. The sub-task's line asking for the legacy key form is outdated. · answered by Lucas Franco, 2026-11-16
- **When does this branch merge relative to CLS-4743's migration, CLS-4744's backfill and CLS-4746, and does the query fall back to the configuration's legacy key?** It merges only after CLS-4743's migration and CLS-4744's backfill are verified in `staging-1`, `prod-1` and `prod-2`, and before CLS-4746 reaches production; there is no fallback to `rc.reason`. The query stays a straight read of the bonus's reason, which is what the criteria ask; a fallback would let a configuration edit rewrite the BigQuery reason of every bonus without one, the bug CLS-3316 removes. This is a release-order requirement for the story's release manifest, not a code change. · answered by Lucas Franco, 2026-11-16
- **Does the bonus's reason stay in `reward_configuration_reason`, or go to a new BigQuery column?** It stays in `reward_configuration_reason`, same position and type, now holding the bonus's reason. No new column and no celesta-terraform-bi change; the readers found by the `INFORMATION_SCHEMA` check in Testing Strategy are told of the change. · answered by Lucas Franco, 2026-11-16
- **Do the `reward_configuration` and `promotion_reward_configuration` syncs also move to the reason name in this sub-task?** No. They stay as they are; whether configuration-level tables need the reason name is a question for the product owner on the parent. · answered by Lucas Franco, 2026-11-16
