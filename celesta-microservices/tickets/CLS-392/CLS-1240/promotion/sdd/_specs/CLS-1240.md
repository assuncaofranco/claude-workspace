# Spec: Winnings Bonus Model for Promotion-System Bonuses

**Ticket:** `CLS-1240`
**Branch:** `CLS-392-CLS-1240`
**Services:** `celesta-wallet`, `celesta-promotion`
**Type:** Feature
**Status:** `draft`

---

## Summary

Make the **`winnings`** bonus model work end-to-end for bonuses originated in the Promotion system
(`bonusModel = null`), the same way it already works for legacy wallet bonuses.

For a winnings bonus there is **no wagering requirement**: the bonus amount itself is non-withdrawable
"fuel", but **what the player wins while playing it turns into real (withdrawable) money immediately**.

The "win → real" money movement stays in the **wallet** (where it already exists). This ticket
ensures a promotion-originated winnings bonus flows through that machinery correctly, and that the
Promotion side recognizes and forwards the `winnings` model without imposing wager rules.

---

## Background

- Bonus models (identical constant in both repos — `winnings`):
  - `celesta-promotion`: `Lancaster\Constants\Promotion\RewardConfigurationConstants::MODEL_WINNINGS`
  - `celesta-wallet`: `Lancaster\Constants\Wallet\BonusModelConstants::MODEL_WINNINGS`
  Both are in their respective `MODELS` arrays, so `winnings` is already an accepted choice.

- **Wallet already implements winnings turn-to-real** in
  `src/BonusBundle/EventListener/ORM/TurnToReal/TransactionWinWinningsListener.php`:
  on a `TYPE_BONUS_WIN` (success) whose sub_balance has `model = winnings`, it
  (a) reverts `played → claimed` when the win > 0, and
  (b) creates a `TYPE_BONUS_WITHDRAW` for the win amount → the win becomes withdrawable.
  This listener gates on the `model` string only — it does **not** depend on the `BonusModel`
  entity (`getBonusModel()`), so in principle it already fires for promotion bonuses.

- CEL-7576 introduced the promotion-system bonus path (`bonusModel = null`). CLS-851 handled the
  `played → bonusBalance` decrement; alongside it (same branch) the Promotion claim was extended to
  send `wageringMultiplier` so the **wager** model works for promotion bonuses. **CLS-1240 is the
  equivalent guarantee for the `winnings` model** — which, unlike wager, needs no extra config field.

- The Promotion claim already forwards the model:
  `BonusListener::postWalletBonusTransaction` sends `'model' => $rewardConfiguration->getModel()`.

## Functional Requirements

| FR | Description |
|----|-------------|
| **FR1** | A reward configured with `model = winnings` must be claimable via Promotion and create a wallet `sub_balance` with `model = winnings`. |
| **FR2** | When the player wins while playing a winnings bonus, the win amount must turn into real (withdrawable) money immediately via `BONUS_WITHDRAW` — with **no** wagering requirement. |
| **FR3** | A `winnings` reward configuration must **not** require `wageringMultiplier` (it is irrelevant to winnings). |
| **FR4** | If a winnings bonus was set to `played` and a win then arrives, the bonus reverts to `claimed` in the wallet, and that status change syncs back to Promotion (CLS-849 mechanism). |
| **FR5** | The Promotion `Bonus` workflow must allow the resulting `claimed ↔ played` transitions a winnings bonus can go through. |
| **FR6** | Legacy bonuses (`bonusModel` set) and other models (`wager`, `upper`, `direct`) must be completely unaffected. |

---

## Acceptance Criteria

- A promotion-originated winnings bonus, when the player wins, produces a `BONUS_WITHDRAW` in the
  wallet equal to the win amount, crediting the withdrawable balance — without any wagering being met.
- Creating/offering a `winnings` reward does not demand a `wageringMultiplier`.
- A `played` winnings bonus that receives a win reverts to `claimed` in the wallet and the Promotion
  bonus reflects `claimed` (via the existing async sync).
- All existing tests in both services continue to pass (PHPUnit + Behat).

---

## Open Questions

- **Max win for winnings?** The wallet's winnings listener applies **no** max-win ceiling (only the
  `wager` model does, via `maxWinMultiplier`). Confirm with PO whether winnings should stay uncapped
  (assumed yes). If a cap is wanted, it is out of scope here and needs its own ticket.
- **Does it already work?** The wallet listener appears model-agnostic to `getBonusModel()`, so the
  flow may already work for promotion bonuses end-to-end. The plan's first task is to verify this; if
  it already works, CLS-1240 becomes a validation + tests + schema-documentation ticket.

---

## Testing Guidelines

Create/extend tests for the new path (without going too heavy):

- **Wallet** (`tests/Bonus/PromotionBonusFlowTest.php` or a sibling): claim a winnings bonus via the
  promotion path → place a winning game transaction → assert a `BONUS_WITHDRAW` is created for the win
  amount and the withdrawable balance increases; assert `played → claimed` revert when applicable.
- **Promotion**: assert a `winnings` reward configuration is accepted without `wageringMultiplier`,
  and that the claim payload carries `model = winnings`.
