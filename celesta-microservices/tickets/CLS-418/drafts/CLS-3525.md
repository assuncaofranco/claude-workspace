# CLS-3525 — {A} [payment] Return payment-information payin KPIs from Statistics

Sub-task: https://celesta.atlassian.net/browse/CLS-3525 · Parent: https://celesta.atlassian.net/browse/CLS-418 · Repository: celesta-payment

## Overview

`GET /domain/{domainId}/player/{playerId}/payment-information` (`PaymentInformationController::getPaymentInformation()`)
loads the `player` row through `PaymentInformationRepository::getPaymentInformation()` (`404` when there is none) and
answers `PaymentInformation::jsonSerialize()`. Two of its keys, `successfulPayinAmount` and `successfulPayinCount`, are
the columns `successful_payin_amount` (`DECIMAL(12,2)`) and `successful_payin_count` (`INT`), added by
`Version20241218102531`. No production code path in this repository writes them: `PaymentInformationSubscriber`
updates only `last_successful_*_at`, `total_deposit_amount` and `total_card_deposit_amount`, and the only writer is the
test command `TestUpdatePayInAmountCommand`. So the endpoint answers the column default for almost every player.

celesta-statistics already serves both numbers per player and currency on `GET /api/kpi/{playerId}`
(`KPIController::getKpiAction()`, `KPIResponse`), and this repository already reads them there:
`StatisticsClient::getPaymentPlayerKpi()` (`types[]=payment`) feeds `DepositFraudHelper::getExecutionTypes()` and
`PayinHelper`.

This change answers the two keys from Statistics instead of the columns (FR7), with the response unchanged in keys,
order and types (FR8). After it, nothing on the payment-information read path reads either column. Stopping the
writes and removing or renaming the columns is [CLS-3528](https://celesta.atlassian.net/browse/CLS-3528) (FR6).

## Architecture & Design

**Data flow.** Request → `MapEntity` loads `PaymentInformation` (unchanged; `404` before any outbound call) →
`CrmClient::getCustomer($playerId)` for the currency [PENDING Q1: the CRM customer's `currency`] →
`StatisticsClient::getPaymentPlayerKpi($playerId, $currency)` with no dates, so Statistics reads its all-time table
(`AbstractKpiAggregateReader::getAggregated()`, `kpi_payment_sum`) → response.

**Statistics fields.** `successfulPayinAmount` (float) and `successfulPayinCount` (int) of `KPIResponse`, computed
from `config/kpi.yaml` `successful_payin` (`sum(amount)` / `count` of `event_payment_transaction`, `type: sale`,
`status: success`) plus the initial deposit (`InitialDepositPaymentKpiHandler`). `currency` is mandatory
(`KPIRequest::$currency`, `#[Assert\NotBlank]`); a player with no rows gets `0` / `0.0` (`mapRow()` defaults).

**Precedents followed.**

- Statistics read: `StatisticsClient::getPaymentPlayerKpi()` as is, no client change (callers `DepositFraudHelper`,
  `PayinHelper`).
- Player currency: `CrmClient::getCustomer($playerId)['currency']`, as
  `PaymentConfigurationController` resolves it for the payment-configuration list when no currency filter is given.
- Clients injected as action arguments, as the other actions of `PaymentInformationBundle\Controller\ApiController`
  receive their services.
- Error handling: celesta-gateway `WalletInformationController::getWalletInformation()` (catch `V2Exception`, log
  `ErrorMessageConstants::UNKNOWN_ERROR`, throw `ServiceUnavailableHttpException` with the `V2Exception` as previous).
  [PENDING Q3] No precedent in this repository for `ServiceUnavailableHttpException`; here
  `SymfonyComponents\Subscriber\KernelExceptionSubscriber` renders any `HttpExceptionInterface` of status `>= 500` as
  `500 {"title": "Unknown error"}`, and `ErrorCodeResponseSubscriber` adds `"code": "SERVER_ERROR"`. So the endpoint
  answers `500`, a status it already answers on any unhandled failure, and no new status code appears (FR8).

**No precedent.** Appending keys to an entity's `jsonSerialize()` output inside a controller: no controller in
`src/` does it. Chosen over setting the values on the managed entity (`setSuccessfulPayinAmount()`), which would keep
the read path on the column getters and turn any later flush in the request into a write of Statistics' numbers into
the columns.

**Response.** Unchanged:

```json
{
  "domainId": 1, "playerId": 1,
  "lastSuccessfulDepositAt": "2024-10-08 00:00:00", "lastSuccessfulWithdrawAt": "2024-08-08 00:00:00",
  "totalCardDepositAmount": 130.43, "totalDepositAmount": 1000.12,
  "initialSuccessfulPayinAmount": 0,
  "successfulPayinAmount": 111.11,
  "successfulPayinCount": 1
}
```

The two keys stay last because they are the last two of `jsonSerialize()` today. Both values are cast
(`(float)`, `(int)`): Statistics answers whole amounts as JSON integers and the existing test mock
`MockCurlClientRequestsTrait::$kpiData` carries them as strings.

**Boundary.** The entity keeps its mapping of both columns, so Doctrine still selects them when it loads the row;
removing that mapping, the setters, `TestUpdatePayInAmountCommand` and the columns is CLS-3528. No constant and no
messenger job is added.

## Edge Cases & Error Handling

- **No `player` row**: `404` from `MapEntity`, as today; no CRM or Statistics call.
- **Player with no KPI rows in Statistics**: Statistics answers `0` / `0.0`; the response carries `0` / `0`, which is
  what `JsonResponse` already encodes for `0.0` today.
- **Customer without a currency**: `0` / `0`, no Statistics call [PENDING Q2].
- **Deposits in several currencies**: only the resolved currency is counted [PENDING Q1].
- **Imported player**: Statistics' amount and count include the initial deposit (`InitialDepositKpiJob`), while
  `initialSuccessfulPayinAmount` keeps coming from the local column; a reader adding both would count the initial
  deposit twice. No reader in the platform reads either key (see below).
- **Values change at deploy**: the two keys move from the column default to real Statistics values. Callers of the
  endpoint on `master`: celesta-fraud (`SeonAccountFraudRule`, `SeonLoginFraudRule`, `PlayerDataLoader`) and
  celesta-wallet (`WithdrawRequestController`). All read only `totalDepositAmount`, `totalCardDepositAmount`,
  `lastSuccessfulDepositAt` and `lastSuccessfulWithdrawAt`, and all replace the whole response with zeros on any
  exception.
- **CRM or Statistics down, or a `4xx` from either**: `V2Exception` → logged, `500` [PENDING Q3]. The curl client
  gives up after `CurlClient::REQUEST_TIME_LIMIT` (25 s), so a hanging Statistics holds the request that long.
- **Latency**: two sequential HTTP calls added to every request, on the fraud and withdraw-request paths above.
- **Deploy window**: no migration, no deploy order; CLS-3528 deploys after this.

## Open questions (not part of the plan)

**Q1. Which currency are `successfulPayinAmount` and `successfulPayinCount` read in?**

Statistics answers one currency at a time (`KPIRequest::$currency`, `#[Assert\NotBlank]`; `AbstractKpiAggregateReader`
filters `currency = :currency`). The endpoint has no currency: path `domainId` + `playerId`, and the `player` table has
no currency column. The columns it replaces were currency-less and never written in production.

- **A. The CRM customer's `currency` (recommended).** `CrmClient::getCustomer($playerId)['currency']`.
  - Why valid: `PaymentConfigurationController` resolves the player's currency this way; celesta-gateway
    `getWalletInformation()` defaults to the same customer currency (`$user->getCustomerData()['currency']`).
  - Pros: no contract change; one well-trodden call; the amount stays in one currency.
  - Cons: one CRM call per request; deposits in another currency are not counted.
- **B. A, plus an optional `currency` query parameter that overrides it.**
  - Why valid: `/wallet/information` takes an optional `currency` with the customer's as default.
  - Pros: a caller can ask for another currency.
  - Cons: request contract change (form, `OA\Parameter`); no caller needs it (none reads the two keys).
- **C. One Statistics call per wallet currency (`WalletClient::getWallets()`), counts added up.**
  - Why valid: what CLS-3524 recommends for the gateway's deposit count.
  - Pros: counts every deposit.
  - Cons: amounts in different currencies cannot be added, so the amount would still need one currency; N calls.

Recommendation: **A** — smallest change, existing precedent in this service, and nobody reads the keys today.

**Q2. What does the endpoint answer when the customer has no currency?**

`PaymentConfigurationController` falls back to the domain's currencies (`$customer['domain']['currencies']`) when the
customer's is empty; Statistics would answer `400` to an empty currency.

- **A. `0` / `0`, no Statistics call (recommended).**
  - Why valid: the sub-task asks for `0` / `0.0` when there is nothing to report, and without a currency there is no
    Statistics query to make. Not verified: whether a customer without a currency can have deposits at all.
  - Pros: no failing call, no guess.
  - Cons: hides a CRM data problem, if one exists.
- **B. The first of the domain's currencies**, as `PaymentConfigurationController` does.
  - Why valid: existing fallback in this service.
  - Pros: mirrors the precedent.
  - Cons: picks a currency arbitrarily; the result is `0` / `0` anyway for a player who never deposited.

Recommendation: **A**.

**Q3. What does payment-information do when Statistics (or CRM) fails?**

Precedent: celesta-gateway `/wallet/information` catches `V2Exception`, logs `UNKNOWN_ERROR` and throws
`ServiceUnavailableHttpException`; its own `HttpExceptionSubscriber` turns that into a `5xx` from the upstream status.
Here `KernelExceptionSubscriber` caps every `>= 500` HTTP exception to `500 {"title": ...}` (+ `"code":
"SERVER_ERROR"`). Today the endpoint answers `200`, `404`, or `500` on an unhandled failure; its OpenAPI lists `200`,
`400`, `403`. Every caller (celesta-fraud SEON rules and `PlayerDataLoader`, celesta-wallet
`WithdrawRequestController`) catches any error and sends zeros for the four local keys it reads; none reads the two
Statistics keys. Statistics being down already fails payins: `DepositFraudHelper::getExecutionTypes()` does not catch, and
`PayinController` turns the `V2Exception` into `400` "Error happened during request to the fraud MS.".

- **A. Mirror the gateway code: log, throw `ServiceUnavailableHttpException`; answered as `500` (recommended).**
  - Why valid: the parent's edge cases for the other surfaces say "the same error the endpoint returns today"; `500`
    is what this endpoint already answers on a failure, so no new status code (FR8).
  - Pros: no silent wrong number; error logged once with the cause.
  - Cons: during a Statistics outage the callers lose `totalDepositAmount`, `totalCardDepositAmount` and the two
    dates, which do not depend on Statistics, and send zeros to SEON.
- **B. Answer an explicit `503`** (`JsonResponse`, as `BouncepayProvider` does), and document it in `OA\Get`.
  - Why valid: literal "503 when the KPI source is unavailable".
  - Pros: callers can tell an upstream outage from a payment fault.
  - Cons: new status code on this endpoint, against FR8; no caller distinguishes it.
- **C. Degrade: log and answer `200` with `0` / `0` for the two keys.**
  - Why valid: `DepositFraudHelper::getWalletData()` and `getWalletBalance()` degrade to empty / zero on a wallet
    failure.
  - Pros: the four local keys keep reaching fraud and wallet during an outage.
  - Cons: the response states `0` deposits for a depositor; breaks "equal to Statistics'" (AC6) silently; a
    reviewer will read it as a swallowed error.

Recommendation: **A** — consistent with the parent's rule for the other surfaces and with no new status code; C is
the alternative if Team A prefers fraud data availability over the two counters' correctness during an outage.
