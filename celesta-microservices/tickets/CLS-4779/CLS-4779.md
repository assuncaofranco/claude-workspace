# CLS-4779 — Paytech card automatic refund (preprod-1)

**Feature:** an operator refunds a Paytech card deposit from the Backoffice with the Automatic option, and the refund status follows Paytech.

## Setup
- Deploy on pp1, before merge: payment `CLS-4933` (pulls constants `CLS-4932` from its branch) and backoffice-front `CLS-4934`.
- `./run_pp1.sh` regenerates the collection and runs it with the vault credentials.
- Run the whole collection in one go: folders share captured ids.

## Steps
1. Player deposits 20 EUR with the Paytech sandbox card (no 3DS).
2. BO finds the deposit in the transaction report: provider `paytech`, method `visa`, `success`.
3. BO automatic refund of 5, then wait for its final status.
4. BO automatic refund of the remaining 15, then wait.
5. BO automatic refund of 1 more: 400.
6. Player balance is back to the starting value.
7. Second deposit of 10, manual refund of 10: still works.
8. By hand, in the BO: the refund modal offers Automatic on the visa deposit (front, CLS-4934).

## Variables
| Variable | Example | What it is |
|---|---|---|
| `domainId` | `56` | pp1 domain with the Paytech sandbox configuration |
| `playerId` | `307847` | `lucastest`, the gateway user in the vault |
| `paytechVisaConfigurationId` | `7875` | Paytech sandbox visa payin (provider configuration 424) |
| `cardNumber` | `4000000000000408` | Paytech sandbox card, not enrolled for 3DS, approved |
| `pollMs` / `pollMax` | `5000` / `36` | refund status polling: up to 3 minutes |

Captured at runtime: tokens, `depositUid`, `depositId`, `refund1Id`, `refund2Id`, `manualDeposit*`, `refund3Id`, `balanceBefore`.

## Notes
- Everything goes through gateway and backoffice: PO-runnable, nothing DEV-ONLY.
- The console prints how long each refund stayed pending: that is the number the payin timeout (900 s) is compared against.
- A refund still pending after 3 minutes fails its step on purpose: re-run that step after 15 min, when the timeout job has asked Paytech.
- Never use provider configuration 426 on pp1: it points at Paytech production (`engine.tx.tech`). Apple Pay only exists there, so the Apple Pay rejection is not tested here (PHPUnit and Proteus cover it).
- Paytech sandbox accepts refunds up to 10000; a deposit stuck in `pending` means the Paytech webhook did not reach pp1.
