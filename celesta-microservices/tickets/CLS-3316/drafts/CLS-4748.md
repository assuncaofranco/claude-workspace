# CLS-4748 — {B} [backoffice] Cleanup: remove the legacy reason filter and the legacy reason field from reward configurations

Sub-task: https://celesta.atlassian.net/browse/CLS-4748 · Parent: https://celesta.atlassian.net/browse/CLS-3316 · Repository: celesta-backoffice

## Overview

Two legacy reason surfaces of the backoffice API go away once the front uses `reasonId` only:

- **The list filter.** `POST /api/gateway/domain/{domainId}/bonus_configurations`, `/bonus_configurations/count` and the old alias `/bonus_configurations/search` accept `filter.reasons`, a list of legacy reason keys (`loyalty_vip`, `other`…) plus `null` for "no reason". It is declared in `App\GatewayBundle\Form\Type\Bonus\BonusModel\FilterType`; `BonusModelNormalizer::normalizeFilterRequest()` calls `normalizeFilterReason()`, which turns each `null` into `NOREASON`, and the controller forwards the filter to promotion's `GET api/domain/{domainId}/reward-configurations[/aggregate]`.
- **The legacy `reason` on configuration create and edit.** `RewardConfigurationType` (`POST`/`PUT .../bonus_configuration[/{id}]`, three types) and `GiftRewardConfigurationType` (`POST`/`PUT .../reward_configuration/gift[/{id}]`) carry `reason`, a choice of `RewardConfigurationConstants::REASONS`, which [CLS-4745](https://celesta.atlassian.net/browse/CLS-4745) keeps forwarding to promotion so the current front still finds new configurations by it.

[CLS-3316](https://celesta.atlassian.net/browse/CLS-3316) moves reasons to reward offering reasons (`reasonId`). The offer form stops filtering the bonus name list by reason ([CLS-4746](https://celesta.atlassian.net/browse/CLS-4746)) and the reward configurations list drops its reason filter ([CLS-5146](https://celesta.atlassian.net/browse/CLS-5146)). This sub-task removes the filter and the legacy `reason` field from the backoffice API after both are live. Promotion keeps storing and returning the legacy `reason`; nothing in promotion changes.

## Architecture & Design

- **Filter contract.** `filter.reasons` disappears from `BonusModelFilter`. `FilterType` keeps the default `allow_extra_fields: false`, so a request that still sends `filter.reasons` gets the standard 400 validation body with `This form should not contain extra fields.` and promotion is not called. Same behaviour, and same test shape, as the removed singular `currency` filter on the bonus list (`tests/GatewayBundle/Controller/Bonus/BonusControllerTest.php::testSingularCurrencyFilterIsRejected`).
- **Filter normalizer.** `normalizeFilterRequest()` stops calling `normalizeFilterReason()`, and the method is deleted: it has no other caller in `src/`.
- **Legacy `reason` on the configuration forms.** The `reason` field is removed from `RewardConfigurationType` and `GiftRewardConfigurationType` and from their request schemas (`RewardConfigurationRequest`, `RewardConfigurationGiftRequest`). Both forms keep `allow_extra_fields: true` (`RewardConfigurationType::configureOptions()` and `GiftRewardConfigurationType::configureOptions()`), so an old client that still sends `reason` gets 200 and the key is ignored: it is not a form field, so it never reaches `$form->getData()`, the normalizers or promotion. A stored legacy key is therefore never touched by the backoffice: not set on create, not cleared on edit.
- **Forwarding code from CLS-4745.** `BonusModelController::addBonusModelAction()` and `GiftConfigurationController::putGiftConfigurationAction()` loop over `['reason', 'reasonId']` to drop a key the request does not carry. With `reason` gone from the forms the loop has one key left; it becomes the single check on `reasonId`. `BonusModelNormalizer::normalizeGiftRequest()` loses `'reason'` from its `array_intersect_key` list; its edit defaults are already `displayName` and `stock` only (CLS-4745 removed the hard-coded `'reason' => null`).
- **Responses are unchanged.** `BonusModelNormalizer::normalize()` and `normalizeListItem()` keep returning the legacy `reason` that promotion returns. Only requests lose it.
- **Translations.** The repository has no translation key for the filter. The reason keys in `translations/messages.en.yml` are `bonus.form.reason` and `bonus.form.reasonChoices.*`, the labels of the legacy configuration reason field, with no consumer in `src/`. They are removed.
- **Promotion is not touched.** Promotion keeps accepting `filter.reasons` and `NOREASON` (`RewardConfigurationRepository`, `ApiBundle\Form\Type\RewardConfiguration\FilterType`) and keeps `reason` nullable on create and edit; the backoffice simply stops sending both.
- **Callers found before removal** (`origin/master` of each repository, 2026-11-16):

  | Caller | What sends `filter.reasons` or `reason` | Covered by |
  |---|---|---|
  | celesta-backoffice-front, offer bonus form | `src/components/page-components/crm/players/player/main/OfferBonusForm.js:119`, `filter: { status, reasons: [values.reason], types }` | [CLS-4746](https://celesta.atlassian.net/browse/CLS-4746) ("Reason no longer filters the Bonus name list") |
  | celesta-backoffice-front, reward configurations list search bar | `RewardConfigurationsSearchBar.js` (`reasons` field) and `src/utils/filterConfigs/fcRewardConfigurations.js` (`reasons`, also parsed from the URL) | [CLS-5146](https://celesta.atlassian.net/browse/CLS-5146) |
  | celesta-backoffice-front, configuration create and edit | legacy `reason` select, replaced by `reasonId` | [CLS-4746](https://celesta.atlassian.net/browse/CLS-4746) |
  | celesta-e2e-tests | `export/requests/get-bonus-configuration-list-9907cd11.json`, `get-bonus-configuration-count-cc67ff6e.json`: the OpenAPI example body, no assertions, not referenced by any test case | regenerated from the OpenAPI |
  | celesta-gateway, celesta-qaa-proteus, other services | no call to the backoffice `bonus_configurations` endpoints | n/a |

## Edge Cases & Error Handling

- **Request still sending `filter.reasons`** (old front bundle in an open tab, a script): 400 with the standard validation body, promotion not called. Never a silently unfiltered list.
- **`filter.reasons: []` or `null`**: also an extra field, also 400.
- **`/bonus_configurations/search`** (old route name `bonus_configuration_search_old`): same action, same behaviour.
- **Request still sending the legacy `reason`** on configuration create or edit (old client, a script, the non-gift edit that echoes the whole configuration it read): 200, the key is ignored and never forwarded, because both forms keep `allow_extra_fields: true`. `reasonId` is forwarded when carried, as before.
- **Create without `reasonId`** (an old client that only sends `reason`): the configuration is created without a reason, since nothing sets the legacy key any more. Hence the deploy order below.
- **Edit never touches the stored legacy key**: it is neither sent nor cleared; promotion keeps it and still returns it.
- **Deploy window**: deploying before the front stops sending `filter.reasons` and `reason` turns the offer form's bonus name list, the list page reason filter and the configuration forms' reason into 400s (filter) or into reasonless configurations (`reason`). Hence the merge and deploy order below.
- **Bookmarked list URL with a `reasons` parameter**: harmless once the front no longer parses `reasons` from the URL ([CLS-5146](https://celesta.atlassian.net/browse/CLS-5146)).

## Acceptance criteria

Sub-task "done when": the bonus-model list has no reason filter, the configuration forms have no legacy reason field, and nothing calls either.

| Input | Expected |
|---|---|
| POST `/bonus_configurations`, `/bonus_configurations/search` or `/bonus_configurations/count` with `filter.reasons` | 400, `This form should not contain extra fields.`, no call to promotion |
| Same endpoints with the other filters (`status`, `ids`, `names`, `displayNames`, `search`, `types`, `segmentIds`, `currencies`) | unchanged: 200, filters forwarded to promotion |
| POST or PUT a configuration (any of the four types) with a legacy `reason` | 200, `reason` not forwarded to promotion; `reasonId` forwarded when carried |
| Generated OpenAPI, schemas `BonusModelFilter`, `RewardConfigurationRequest`, `RewardConfigurationGiftRequest` | no `reasons` / `reason` property |
| `src/` | no `normalizeFilterReason`, no `NOREASON`, no legacy `reason` form field |
