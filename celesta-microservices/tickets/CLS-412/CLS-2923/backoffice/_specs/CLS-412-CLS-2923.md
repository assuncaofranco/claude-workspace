# Spec for CLS-412-CLS-2923

branch: CLS-412-CLS-2923

## Summary

CLS-412 adds "Offer bonus" as a scenario action, and one of its acceptance criteria is that the offer
is *"visible in the player's bonus list in Backoffice, and its source identifies the scenario that
created it"*. celesta-promotion now stores and returns `sourceScenarioId` on a bonus, set when a
scenario made the offer instead of a back-office user.

The backoffice does not pass that field on. `BonusNormalizer::normalize()` rebuilds the promotion row
field by field from a whitelist, so anything outside it is dropped. Neither source field is in that
list today — not even `sourceUserId`, which promotion has carried for years. The bonus list therefore
shows no origin at all, and without this change a scenario offer reaches the operator indistinguishable
from one an operator made by hand.

## Functional Requirements
- `GET /api/gateway/domain/{domainId}/reward/bonuses` returns `sourceScenarioId` for every bonus,
  carrying promotion's value, `null` when no scenario is behind the offer.
- The same response returns `sourceUserId` on the same terms. Exposing only the scenario half would
  give the front an origin column that can name a scenario and never an operator.
- Both fields are `null` when promotion omits them, so a promotion still on the previous version does
  not break the endpoint.
- Nothing else about the response changes.

## Endpoints
- `GET /api/gateway/domain/{domainId}/reward/bonuses`: two fields added to the response and to the
  `PromotionBonusNormalized` schema.

## Doctrine Entities
- None. The backoffice stores no bonus; it proxies promotion.

## Possible Edge Cases
- A bonus offered before this epic has both fields `null`, which is honest: nothing recorded an origin
  at the time.
- Promotion refuses a request carrying both sources, so the pair cannot both be set on one row.

## Acceptance Criteria
- A bonus that promotion reports with `sourceScenarioId: 7` comes back from the backoffice endpoint
  with `sourceScenarioId: 7` and `sourceUserId: null`.
- A bonus that promotion reports with `sourceUserId: 1992` comes back with `sourceUserId: 1992` and
  `sourceScenarioId: null`.
- A promotion payload carrying neither field yields `null` for both, with no notice or error.
- `make test` shows no new failures, and `make lint` stays green.

## Open Questions
- The front still has no origin column in the bonus list. Rendering it is not in this ticket; without
  it the epic's criterion is served by the API and not yet by the screen.

## Testing Guidelines
- `tests/GatewayBundle/Normalizer/Promotion/BonusNormalizerTest.php` — one case per source, plus the
  payload that carries neither.
- `tests/GatewayBundle/Controller/Promotion/BonusControllerTest.php` asserts the whole response array,
  so the two new keys belong in its expectation.
