# Spec: CLS-2973

branch: CLS-2973
ticket: CLS-2973 — [promotion] Stop validating promotion configurations against a segment currency
epic: CLS-2053 — Have "Wallet currency" segment criteria

## Summary

`SegmentConstraintValidator::validateSegmentCurrencies()` compares each selected segment's
`currency` against the promotion configuration's currency and raises `messageInvalidCurrency`
when they differ. CLS-2053 removes `currency` from the segment, so that comparison would read a
key that is no longer in the response — `null !== 'EUR'` is true, and every promotion
configuration carrying a segment would be rejected.

The comparison was never an eligibility rule. Nothing at runtime reads a **segment's** currency —
both paths that consume segments intersect ids only:

| Path | File | What it reads |
|---|---|---|
| Offer eligibility | `AppBundle/Offer/Condition/SegmentCondition.php:25` | `array_intersect($segmentIds, $playerSegmentIds)` |
| Engagement | `AppBundle/PromotionConfiguration/Standard/Validator/Engagement/PlayerSegmentMatchValidator.php:41` | same |

Currency **is** still checked at runtime, but against the player, not the segment:
`PlayerCurrencyMatchValidator` (engagement chain, priority 40 in
`AppBundle/Resources/config/validators.yml`) rejects a player whose own currency differs from the
promotion configuration's. That gate is untouched by this ticket, has never looked at the segment,
and is what keeps a cross-currency player out of a promotion.

So the removed check was a backoffice guard-rail, not a business rule under execution. Removing it
changes no bonus grant, no player eligibility and no stored data — only which configurations the
backoffice accepts at save time.

Domain ownership still applies and stays: `validateDomainId()` is untouched.

### Ordering with CLS-2053

This ticket is independent and can ship on its own, ahead of the segment change:

- no other code in this repository reads a segment's `currency` — `SegmentClient`,
  `SegmentCondition`, `PlayerSegmentMatchValidator` and `ReferrerSegmentMatchValidator` contain
  no `currency` reference
- `composer.json` carries no `dev-` branch dependency
- every test stubs the segment locally (Prophecy for the unit tests,
  `App\Tests\Acceptance\Client\Mock\SegmentClient` for Behat)

The dependency runs the other way: CLS-2053 must not reach production before this change.

## Functional Requirements

- [ ] A promotion configuration referencing segments of a different currency is accepted.
- [ ] A promotion configuration referencing segments whose payload carries no `currency` key at
      all is accepted, with no PHP warning and no violation.
- [ ] A promotion configuration referencing a segment outside its domain is still rejected with
      `messageInvalidSegments`.
- [ ] A failure of the segment service is still reported as the existing internal-error
      violation on `segmentIds`.
- [ ] The promotion configuration keeps its own `currency` field, its validation and its
      behaviour — only the comparison against the segment goes.

## Architecture / Module Placement

Existing bundle modified: `ApiBundle` — validator and constraint only.

- `ApiBundle/Validator/Constraints/PromotionConfiguration/SegmentConstraintValidator.php` —
  `validateSegmentCurrencies()` and the `$currency` resolution removed
- `ApiBundle/Validator/Constraints/PromotionConfiguration/SegmentConstraint.php` —
  `messageInvalidCurrency` removed

No new services, entities, DTOs, endpoints, Messenger messages or migrations. No API contract
change: the request still accepts `segmentIds` and `currency`, and the response shape is
unchanged — one validation error simply can no longer occur.

## Possible Edge Cases

- **Segment payload without the `currency` key.** The reason the ticket exists. After the change
  nothing reads the key, so its absence is not observable.
- **Segment payload that still carries `currency`.** The state of the segment service today.
  Also not observable — the key is present and ignored.
- **Configuration with no currency of its own.** Already tolerated: the old code only ran the
  comparison under `if ($currency)`. Behaviour unchanged.
- **Cross-currency configuration saved during the window before CLS-2053 ships.** Newly allowed
  and intended by the epic, but visible earlier than the segment change. It grants nothing on its
  own: while a segment still carries one currency, every player in it is barred at engagement by
  the priority-40 currency gate. The configuration is simply saved and delivers to nobody, with
  no warning where the old check used to give one.
- **`currency` columns left in the Behat segment fixtures.** 38 feature files pass a `currency`
  column to `Given domain :domainId has the following segments:`. The step forwards the table
  straight to the mock, so the column becomes inert data. Left in place deliberately — see Open
  Questions.

## Variation Matrix

Every input the validator can branch on. Currency stops being a dimension — the two **A** cells
are the whole behavioural change.

| # | `segmentIds` | `domainId` | Segment payload | Before | After | Class |
|---|---|---|---|---|---|---|
| 1 | absent | set | — | no violation | same | E |
| 2 | not an array | set | — | no violation | same | E |
| 3 | array | null | — | no violation | same | E |
| 4 | empty | set | empty list | no violation | same | E |
| 5 | all in domain | set | **carries a differing `currency`** | `messageInvalidCurrency` | no violation | **A** |
| 6 | all in domain | set | **no `currency` key** | warning + `messageInvalidCurrency` | no violation | **A** |
| 7 | one outside domain | set | any | `messageInvalidSegments` | same | E |
| 8 | any | set | client throws | internal-error violation | same | E |

Cells 1-4, 7 and 8 are **E**: their path is `validate()`'s guards, `validateDomainId()` and the
`catch`, none of which this ticket touches. Cell 6 is the shape CLS-2053 produces and the reason
the ticket exists; cell 5 is today's shape under the new rule.

Coverage: every cell has a unit test except 3, which is an untouched early return with no test
before this ticket either. Cells 5 and 7 also run end to end in the Postman collection.

## Acceptance Criteria

Derived from the matrix above — one criterion per A cell, plus the E cells that must not drift.

- [ ] `messageInvalidCurrency` no longer exists in `src/` or `tests/`.
- [ ] `validateSegmentCurrencies()` no longer exists.
- [ ] Unit test: segments returned without a `currency` key produce no violation.
- [ ] Unit test: segments whose currency differs from the configuration produce no violation.
- [ ] Unit test: domain mismatch still violates `messageInvalidSegments`.
- [ ] Unit test: segment service failure still violates with the internal-error message.
- [ ] Behat: creating a promotion configuration whose segment holds another currency succeeds —
      the segment fixture must keep a `currency` column differing from the configuration's, or the
      scenario proves absence of the key instead of divergence of the value.
- [ ] `make test` green.

## Open Questions

- **Inert `currency` column in 38 Behat feature files** — deliberately out of scope. Nothing
  reads it after this change, and touching 38 files in a removal PR buries the real diff. It
  belongs with the CLS-2053 cleanup or a follow-up.
- **The window before CLS-2053 ships** — from this deploy until the segment change, the
  backoffice accepts a configuration whose segments hold a different currency, with no warning.
  Intended by the epic, but arriving earlier than the rest of it. Needs a PO acknowledgement, not
  a code change.
