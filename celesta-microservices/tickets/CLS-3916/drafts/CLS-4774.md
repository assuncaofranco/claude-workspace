# CLS-4774 — {B} [backoffice] Gift reward type in promotion reward forms

Sub-task: https://celesta.atlassian.net/browse/CLS-4774 · Parent: https://celesta.atlassian.net/browse/CLS-3916 · Repository: celesta-backoffice

## Overview

The backoffice validates promotion rewards and forwards them to celesta-promotion. `TypeResolver` (`src/GatewayBundle/Form/Type/Promotion/Reward/TypeResolver.php`) picks one form type per reward type through `REWARD_TYPE_MAP` (`future_deposit`, `match_deposit`, `match_bet`, `free_bonus`, `free_round`) and rejects a type the promotion configuration does not accept through `PROMOTION_CONFIGURATION_TO_REWARD_TYPE_MAP`. Every reward form extends `AbstractRewardType`, which carries the optional `rewardConfigurationId` and the deprecated `bonusModelId`, and attaches `BonusModelSubscriber`, which, on `POST`, loads the configuration named by whichever id was sent and rejects it unless it has the reward's configuration type, is `enabled` and is offered `manual`ly. A reward of type `gift` falls to `DefaultType` today and is rejected on `type`.

This adds the `gift` reward type: a `GiftType` form that names its gift configuration exactly as the other reward types name theirs (`rewardConfigurationId` or `bonusModelId`), accepted for Deposit tier, First bet insurance, Refer a friend and Instant reward, not Multiplus; `BonusModelSubscriber` checks the gift configuration like it checks bonus configurations; the OpenAPI document lists the gift reward in every request and response it can appear in, and the gift reward type in the constants schema. celesta-promotion (CLS-4771) owns the rest of the save rules: currency, and every check on `PATCH`.

## Architecture & Design

- **Request flow, unchanged.** `RewardController::postReward`, `postRewardForAggregator` and `patchReward`, and `RewardAggregatorController::postRewardAggregators` through `RewardCollectionType` and `RewardAggregator\RewardSubscriber::preSubmit`, all resolve the form type with `TypeResolver::resolveFormType()`. Adding `gift` to the two maps of `TypeResolver` reaches all four entry points.
- **`GiftType` mirrors `FutureDepositType`.** It extends `AbstractRewardType`, returns `RewardConstants::TYPE_GIFT` from `getRewardType()`, and adds no field on `POST` or `PATCH`: one gift per reward, so no `quantity` and no `options`. The ids are the ones `AbstractRewardType::buildForm()` adds for every type: `rewardConfigurationId` and `bonusModelId`, both `IntegerType`, `required => false`. celesta-backoffice-front (CLS-4776) sends `{"type": "gift", "bonusModelId": <gift configuration id>}`; `{"type": "gift", "rewardConfigurationId": <id>}` is accepted the same way. The form data forwarded to celesta-promotion is `{type: gift, bonusModelId, rewardConfigurationId}`, the unsent id `null`, as for `FutureDepositType`.
- **Configuration check follows the existing pattern.** `BonusModelSubscriber::REWARD_TO_BONUS_TYPE` gains `RewardConstants::TYPE_GIFT => RewardConfigurationConstants::TYPE_GIFT` (`BonusModelConstants`, which the other entries use, has no gift type; the comparison is on the configuration's `type` string, and `RewardConfigurationConstants` is already imported). `postSubmitData()` then, unchanged, validates `rewardConfigurationId` when it is not `null` and `bonusModelId` otherwise, and puts `Provided bonus model id is invalid.` on that field when the gift configuration does not exist in the URL's domain (`getRewardConfiguration` throws `V2Exception`, which covers a deleted one), has another type, is not `enabled`, or is not offered `manual`ly (gift configurations are always created `manual` by celesta-promotion's `RewardConfigurationFactory::createFromGiftRequestModel`, and its generic reward configuration request rejects `type: gift`). With neither id sent, the subscriber returns before any check, as for every type: the reward is forwarded and celesta-promotion decides.
- **`PATCH` is not checked here, for any type.** `AbstractRewardType` adds `type` only on `POST`, so the `PATCH` form data has no `type` and `BonusModelSubscriber` returns before the check. A gift reward patched to another configuration is checked by celesta-promotion only, like a bonus reward today.
- **Both ids sent.** The backoffice checks `rewardConfigurationId` and forwards both; celesta-promotion's `RewardSubscriber::resolveRewardSource()` rejects with `Only one of rewardConfigurationId or bonusModelId may be provided.` on `rewardConfigurationId`, which `FormHelper::handleV2Exception()` maps back onto the form.
- **Currency.** Not checked here: no reward type is checked for currency in the backoffice. celesta-promotion (CLS-4771) relays it as a field error that `FormHelper::handleV2Exception()` maps back onto the form.
- **Response, unchanged.** `RewardNormalizer::normalize()` returns `id`, `type` and `bonusModelId` for a type with no `case`, which is what a gift reward needs: celesta-promotion's `Reward::jsonSerialize()` returns the configuration id in `bonusModelId` (`getRewardSourceId()`). No `case` is added; only the OpenAPI `GiftRewardResponse` schema. `BaseRewardResponse` and `RewardListItem` take their `type` enum from `RewardConstants::TYPES`, so they list `gift` once the library is required.
- **Constants endpoint.** `ConstantManager::getConstants()` reflects every class of `lancasters/constants`, so `promotion.rewardConstants.typeGift` and `gift` in `promotion.rewardConstants.types` appear in `GET /api/gateway/constants` as soon as the library carrying `RewardConstants::TYPE_GIFT` is required. The code change here is the OpenAPI `PromotionConstants` schema, which lists the `rewardConstants` properties one by one.
- **Library pin.** `composer.json` requires `"lancasters/constants": "^1.367"` on `master` (lock at `v1.367`); the latest tag of celesta-constants is `v1.368`. This sub-task requires celesta-constants from the `CLS-4767` branch as `dev-CLS-4767 as 1.369` until the lead tags it.

## Edge Cases & Error Handling

- **Backoffice deployed before CLS-4771.** The backoffice accepts `type: gift` and checks the configuration; celesta-promotion's `Assert\Choice(getAllowedTypes())` rejects `gift`, and its `RewardSubscriber` rejects a gift configuration as a promotion reward (`A gift reward configuration cannot be a promotion reward.`), both as a 400 that `FormHelper::handleV2Exception()` returns as a validation error. No reward is stored. CLS-4771 deploys together with CLS-4772, so celesta-promotion accepts gift rewards only once it can also reward them.
- **CLS-4771 deployed before the backoffice.** `TypeResolver` resolves `gift` to `DefaultType`, which returns 400 on `type`. Nothing reaches promotion.
- **CLS-4776 deployed before the backoffice.** Same 400 on `type`; the Gift option cannot be saved. CLS-4774 blocks CLS-4776.
- **Gift reward with no id.** Forwarded without a configuration check, as for every reward type; on `master` celesta-promotion stores a reward with no configuration when neither id is sent. Whether a gift reward without a configuration is rejected is CLS-4771's rule.
- **Configuration disabled, deleted, outside the domain or offered automatically, at `POST`.** `BonusModelSubscriber` returns 400 `Provided bonus model id is invalid.` on the id field that was sent. A deleted or foreign configuration makes `getRewardConfiguration` fail and is reported the same way.
- **`PATCH` of a gift reward to another configuration.** Not checked here, as for every type (`PATCH` data has no `type`); celesta-promotion is the only check.
- **Configuration disabled or deleted after the save.** Not checked here; CLS-4772 skips the gift at rewarding.
- **Gift configuration in another currency.** Not checked here; celesta-promotion (CLS-4771) rejects it and the error lands on the field it names.
- **A bonus configuration id on a gift reward, or a gift configuration id on a bonus reward, at `POST`.** Type mismatch in `BonusModelSubscriber`, 400 on the id field.
- **Both `rewardConfigurationId` and `bonusModelId` on a gift reward.** The backoffice checks `rewardConfigurationId` and forwards both; celesta-promotion rejects with `Only one of rewardConfigurationId or bonusModelId may be provided.`
- **Gift reward with `quantity` or `options`.** 400, `This form should not contain extra fields.` celesta-backoffice-front sends neither for a gift.
- **Multiplus.** `TypeResolver` throws; direct `POST`/`PATCH` returns 400 with the message in `errors`, an aggregator `POST` returns it on the reward.
- **Constants pin.** `dev-CLS-4767 as 1.369` also brings `v1.368` (Paytech added to `PaymentConfigurationConstants::PAYMENT_METHODS_AUTOMATIC_REFUND`), which the constants endpoint reflects; `ConstantControllerTest` builds `paymentMethodsAutomaticRefund` from the library constant and stays green. If celesta-constants tags `v1.369` from another branch before review or release, the alias is raised to the next free version.
- **`CLS-4767` branch without the constant.** Task 1 stops if `RewardConstants::TYPE_GIFT` is not on the branch yet; the implementation waits for CLS-4767's push.

## Acceptance criteria

- `POST` of a reward with `{type: gift, bonusModelId}` or `{type: gift, rewardConfigurationId}` to a deposit tier, first bet insurance, refer a friend or instant reward promotion configuration, directly, on an aggregator or inside `POST .../reward-aggregators`, is forwarded to celesta-promotion with `type: gift` and the id as sent.
- The same request on a Multiplus promotion configuration returns 400 and is not forwarded.
- A tier, bet result or RAF role aggregator accepts a gift reward next to bonus rewards in the same `rewards` list.
- A gift reward whose configuration does not exist in the domain, is not of type `gift`, is not `enabled` or is not offered manually returns 400 on the id field that was sent and is not forwarded.
- A gift reward with `quantity` or `options` returns 400 `VALIDATION_CONSTRAINT`.
- A 400 from celesta-promotion on a gift reward (currency, CLS-4771) is returned as a validation error on the field it names.
- The response of a created or patched gift reward is `{id, type: gift, bonusModelId}`.
- `GET /api/gateway/constants` returns `promotion.rewardConstants.typeGift = 'gift'` and `gift` in `promotion.rewardConstants.types`.
- The OpenAPI document lists `PostGiftType` / `PatchGiftType` in the reward requests, `PostGiftType` in the tier, bet result and RAF role aggregator requests, `GiftRewardResponse` in `RewardResponse`, and `typeGift` in `PromotionConstants`.
- Existing reward types behave as before: the existing reward, aggregator and constants tests pass unchanged.

## Decisions

- **Which id does a gift reward carry?** — `rewardConfigurationId` or `bonusModelId`, exactly as the other reward types: `GiftType` adds no id field of its own, `BonusModelSubscriber` checks whichever is sent, and a gift with neither is forwarded unchecked, as for every type · answered by Lucas Franco, 2026-11-17
- **In which order do CLS-4771, CLS-4772 and this sub-task deploy?** — CLS-4771 and CLS-4772 together; the backoffice before or after them · answered by Lucas Franco, 2026-11-17
- **Does the backoffice check the gift configuration itself, or leave every save rule to celesta-promotion?** — It checks it at `POST` through `BonusModelSubscriber`, like bonus configurations (exists in the domain, type `gift`, `enabled`, `manual`), with the existing error message; currency stays with celesta-promotion · answered by Lucas Franco, 2026-11-17
- **Does the backoffice check the configuration on `PATCH`?** — No, as for every reward type today; celesta-promotion is the check on `PATCH` · answered by Lucas Franco, 2026-11-17
- **Does a gift reward carry `quantity` or `options`?** — No; one gift per reward, and either field is rejected as extra · answered by Lucas Franco, 2026-11-17
- **How does the response name the gift configuration of a reward?** — In `bonusModelId`, as for every reward type today; no `rewardConfigurationId` is added to the response · answered by Lucas Franco, 2026-11-17
- **Are Proteus tests added for the backoffice?** — No; no backoffice promotion suite exists, the rules are covered at celesta-promotion's contract by CLS-4771 and by this repository's HTTP tests · answered by Lucas Franco, 2026-11-17
- **Is Multiplus excluded?** — Yes, as the parent's scope says; `TYPE_MULTIPLUS` keeps `free_bonus` only · answered by Lucas Franco, 2026-11-17
